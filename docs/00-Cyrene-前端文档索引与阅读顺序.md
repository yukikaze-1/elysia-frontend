## 7. 如何判断冲突

不同问题使用不同权威来源：

| 冲突类型 | 处理方式 |
|---|---|
| 当前进度不同 | 以 doc 16 为准，其他位置改为链接或历史注记 |
| 产品范围不同 | 以最新明确决策和上位需求为准 |
| 文档与运行行为不同 | 以当前代码、运行时 Schema 和测试为事实，并修正文档 |
| 前后端字段不同 | 以后端当前 contract 和 Main adapter 为事实，更新 doc 02 |
| 阶段门槛不同 | 以 doc 12 的最新明确决策为准 |
| 历史记录与现在不同 | 历史记录不改写；新增取代记录并从索引、doc 16 指向新结论 |

安全、权限和凭据边界不能为了匹配 UI 草图或历史方案而降低。

## 8. 元数据规范

00～18 号核心文档必须在标题后提供：

```text
文档状态：维护中 / 参考 / 已归档
最后核验：YYYY-MM-DD
适用阶段：……
权威范围：……
```

含义：

- **维护中**：行为或决策变化时需要同步更新。
- **参考**：仍有设计价值，但当前实现和状态不能仅凭本文判断。
- **已归档**：保留历史证据，不再产生当前任务。

“最后核验”表示最近一次确认文档职责和顶层结论，不等于重新验证其中每条历史测试数据。

## 9. 文件名约定

- 现有核心文档保留原文件名，避免破坏大量历史链接。
- 新的长期维护文档使用稳定文件名，不在文件名追加 `v0.x`。
- 决策、验收、审计和历史快照使用 `YYYY-MM-DD-主题.md`。
- 版本、状态和最后核验日期写在元数据中。
- 大规模重命名必须在链接检查已覆盖目标文件后单独执行，不与内容修订混在一个批次。

## 10. 维护纪律

- 当前状态只写 doc 16。
- README 和 CLAUDE.md 不保存批次日记、测试数字或机器会话断言。
- doc 10/12 中已有的带日期状态注记视为历史快照；新状态只链接 doc 16。
- 关键路线变更必须同时写入 doc 12 和带日期决策记录。
- 验收记录必须包含平台、前后端 SHA、模式、步骤、结果和已知限制。
- 历史文档不静默改写；错误通过勘误或取代记录说明。
- 文档改动提交前运行 `pnpm docs:check`。
