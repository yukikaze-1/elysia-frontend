## 1. 项目背景

Cyrene Desktop 是一款面向个人用户的跨平台 AI 桌面客户端。

产品的核心不只是提供常规 AI 聊天界面，还需要在用户授权的前提下，代表远程 AI Agent 调用桌面客户端的本地能力，例如：

- 读取用户选择的文件；
- 修改或创建本地文件；
- 截取屏幕或指定窗口；
- 获取客户端及操作系统信息；
- 执行其他经过明确授权的本地任务。

客户端与 AI 后端采用前后端分离架构。AI Agent、模型调用、记忆、任务规划和数据库运行在远程服务器；Electron 客户端负责聊天交互、Live2D 展示、本地能力执行、权限控制和结果回传。

Electron 使用 Chromium 和 Node.js 构建跨平台桌面应用，可运行于 Windows 和 Linux；其主进程与渲染进程分离的模型适合将聊天 UI 与本地系统能力隔离。具体版本、兼容范围和许可要求在实施阶段以官方资料为准。

## 2. 产品定位

### 2.1 一句话定义

一个带有 Live2D 角色、能够连接远程 AI Agent，并在用户授权下操作本地环境的跨平台桌面聊天客户端。

### 2.2 Demo 阶段目标

Demo 的目标不是完成一个功能齐全的商业产品，而是验证以下核心闭环：

1. 用户能够与远程 AI 进行流式聊天；
2. Live2D 角色能够正常加载，并根据 AI 状态作出基础反应；
3. Agent 可以调用统一工具系统，并明确区分 Backend、Desktop 和可选 Local Worker Runtime；
4. 后端工具可以在服务端执行并向前端公开必要状态，Desktop 工具只能由客户端校验、授权和执行；
5. 客户端能够完成文件读取、文件写入和截图；
6. Desktop 工具结果能够安全地返回远程 Agent，重连不会重复产生副作用；
7. Windows 和 Ubuntu 可以共享同一套主要客户端代码。

### 2.3 Demo 成功标准

Demo 被视为成功，需要至少完成以下演示：

> 用户向 AI 提问 → AI 流式回答 → AI 请求读取本地文件 → 客户端显示授权窗口 → 用户同意 → 客户端读取文件并返回 → AI 根据文件继续回答。

以及：

> 用户要求 AI 分析当前屏幕 → 客户端请求截图授权 → 用户选择屏幕或窗口 → 客户端截图并上传 → AI 返回分析结果。

## 3. 目标用户

Demo 阶段以单用户、个人桌面环境为主，不考虑企业多租户场景。

典型用户具有以下需求：

- 在 Windows 或 Ubuntu 上使用 AI；
- 希望聊天体验接近 QQ 等成熟即时通信软件；
- 希望 AI 拥有持续的角色形象和互动表现；
- AI 后端运行在远程服务器；
- 希望 AI 在明确授权后帮助处理本地文件或屏幕内容；
- 重视对本地权限、隐私和操作风险的控制。

## 4. 产品设计原则

### 4.1 聊天优先

聊天是客户端的主功能。即使 Live2D、本地工具或部分桌面能力不可用，普通聊天仍应能够继续使用。

### 4.2 用户拥有最终控制权

远程服务器只能提出本地工具请求，不能直接获得本地电脑权限。

涉及用户数据或系统状态的操作，必须由客户端进行：

- 参数验证；
- 路径验证；
- 权限判断；
- 用户确认；
- 实际执行；
- 结果审计。

### 4.3 前后端协议明确

远程后端不得向客户端发送任意 JavaScript、Python、Shell 或 PowerShell 代码并要求执行。

所有本地操作都必须属于客户端预先注册的结构化工具。

### 4.4 渐进式能力扩展

Demo 首先实现少量、边界明确的本地工具。后续再逐步增加剪贴板、程序启动、终端、浏览器自动化等能力。

### 4.5 Live2D 不阻塞核心功能

Live2D 加载失败、显卡不支持或用户关闭角色显示时，客户端应自动降级为静态头像或纯聊天界面。

## 6. 整体界面设计

### 6.1 主窗口结构

Demo 默认采用类似 QQ 的“四区布局”：左侧导航、会话列表、当前聊天，以及按需展开的右侧 Live2D 栏。也可以表述为“导航 + 三个内容栏”，不得再笼统称为三栏而遗漏 Live2D：

```text
┌────────┬──────────────────┬─────────────────────────────┬──────────────────┐
│ 导航栏 │ 会话列表         │ 当前聊天                    │ Live2D 角色      │
│        │                  │                             │                  │
│ 头像   │ 搜索/新建        │ 顶部标题                    │ 角色展示区域     │
│ 聊天   │                  │                             │                  │
│ 任务   │ 会话 A           │ 消息列表                    │ 状态提示         │
│ 设置   │ 会话 B           │                             │                  │
│        │ 会话 C           │ 输入区域                    │ 快捷交互按钮     │
└────────┴──────────────────┴─────────────────────────────┴──────────────────┘
```

建议宽度：

- 导航栏：56～64 px；
- 会话列表：240～300 px；
- 聊天区域：自适应，最小约 500 px；
- Live2D 区域：300～420 px；
- 主窗口建议最小尺寸：1100 × 700；
- 小尺寸窗口下，Live2D 区域自动折叠；
- 用户可以手动隐藏会话栏或 Live2D 栏。

### 6.2 导航栏

导航栏至少包含：

- 当前用户或角色头像；
- 聊天；
- 任务与工具记录；
- 设置。

Demo 阶段“任务与工具记录”页面展示客户端实际知道的公开工具事件，并可按 Backend、Desktop、Local Worker 过滤。Backend 只展示后端主动公开的摘要；Desktop/Local Worker 展示本地权限、状态和脱敏结果，不能把客户端摘要宣称为后端完整审计。

### 6.3 会话列表

每个会话项展示：

- 会话标题；
- 最后一条消息摘要；
- 最后更新时间；
- 当前生成状态；
- 未读或错误标记；
- 右键菜单。

右键菜单至少支持：

- 重命名；
- 删除；
- 置顶可列为 P1。

会话标题可以由后端生成；后端未返回标题时，使用用户第一条消息的前若干字符。

### 6.4 聊天区域

聊天区域由三部分组成：

1. 顶部会话栏；
2. 中部消息列表；
3. 底部消息输入框。

顶部会话栏显示：

- 当前会话标题；
- 当前服务器连接状态；
- 当前实际模型、心情与会话 Token 总量；
- 搜索当前会话消息；
- 打开统一聊天历史查看器，并可直接进入图片/视频资源分类；
- Live2D 显示/隐藏按钮；
- 更多操作菜单。

## 7. 聊天功能需求

### 7.1 消息类型

客户端至少支持以下消息类型：

```text
user          用户消息
assistant     AI 回复
system        系统状态消息
tool          本地工具调用卡片
```

错误优先附着在失败的消息、附件或工具调用上；只有确需进入历史的系统级错误才使用 `system` 消息，不定义独立的 `error` 消息角色。

消息数据结构需要允许后续扩展：

- 文本；
- 图片；
- 视频；
- 文件；
- 音频；
- Emoji 与表情包；
- 工具调用；
- 引用消息；
- 推理过程摘要；
- Inner Voice；
- Public Reply；
- 自定义组件。

后端将一次 AI 回复按句切分并连续流式发送时，前端必须把这些句子视为同一条逻辑 Assistant 回复，而不是多条独立消息。所有分段共享 `responseId/messageId`、头像、时间、模型、心情、消息操作区和 Token 统计；不同分段只保留自己的顺序、通道、内容类型和流式状态。

### 7.2 文本输入

输入框需要支持：

- 多行输入；
- `Enter` 发送；
- `Shift + Enter` 换行；
- 粘贴文本；
- 从系统文件管理器拖拽一个或多个文件到聊天区域；
- 拖入时显示投放区域，松开后加入待发送附件列表，不立即上传或发送；
- 字数或 Token 估算可列为 P1；
- 当前生成过程中继续编辑下一条消息；
- 普通录音输入和实时语音会话作为“直接语音输入”，生成音频输入或语音会话，不把 STT 结果写入文字草稿；
- 按住说话进行“输入法转写”，松开后只把最终文字写入输入框；
- 转写完成后先进入输入框，不自动发送。

输入区域按钮：

- 添加文件；
- 表情与表情包；
- 麦克风；
- 按住说话转文字；
- 截图；
- 发送；
- 生成过程中显示“停止”。

### 7.3 流式输出

远程后端返回流式内容时，客户端需要：

- 持续追加内容；
- 自动显示生成状态；
- 支持 Markdown 增量渲染；
- 避免每个 Token 都触发完整消息重绘；
- 用户停留在消息底部时自动滚动；
- 用户主动向上滚动后，暂停强制自动滚动；
- 显示“回到底部”按钮；
- 支持用户停止当前生成。
- 将同一消息的 `inner_voice` 与 `public_reply` 分别累计并分区展示；
- 允许两种内容交错到达，但保持服务端提供的全局分段顺序；
- UI 以全局分段时间线渲染：只合并相邻的同通道分段，不把后到的 Inner Voice 移到回复顶部；
- 使用同一 `responseId` 将多个句子分段稳定归并为一条逻辑回复；
- 分段完成不代表整条回复完成，只有 `response.completed` 才结束该回复；
- 回复完成后显示本条输入、输出和总 Token；生成期间可显示暂定统计。

流式连接异常后：

- 已收到的内容不得丢失；
- 消息显示“连接中断”；
- 提供重新生成或继续按钮；
- 不应导致整个客户端白屏或崩溃。

### 7.4 Markdown 支持

AI 消息至少支持：

- 标题；
- 段落；
- 有序和无序列表；
- 引用；
- 表格；
- 行内代码；
- 代码块；
- 超链接；
- 粗体和斜体。

代码块支持：

- 语言标记；
- 语法高亮；
- 一键复制；
- 横向滚动；
- 长代码折叠可列为 P1。

出于安全考虑：

- 禁止执行 Markdown 内嵌 HTML；
- 禁止执行脚本；
- 外部链接点击前进行协议验证；
- 默认使用系统浏览器打开外部链接。

### 7.5 消息操作

用户消息支持：

- 复制；
- 重新发送；
- 删除可列为 P1。

AI 消息支持：

- 复制；
- 停止生成；
- 重新生成；
- 播放语音；
- 折叠 Inner Voice；
- 单独复制 Public Reply 或复制完整消息；
- 查看本条回复使用的实际模型、心情和 Token；
- 打开回复所引用的图片、视频和音频；
- 点赞/踩可列为 P1。

### 7.6 会话历史

Demo 可以由远程后端保存会话历史。

客户端需要：

- 获取会话列表；
- 获取指定会话消息；
- 使用游标向上懒加载更早消息，并保持当前可视锚点；
- 按会话标题和摘要搜索历史会话；
- 在当前会话或全部会话内搜索消息并跳转到原消息；
- 分页获取会话中的图片、视频和音频资源；
- 打开独立聊天历史查看器，按日期及“全部、图片/视频、表情、文件、音频、链接”分类查看；
- 新建会话；
- 删除会话；
- 在断线重连后恢复当前会话；
- 避免将完整历史重复写入本地日志。

客户端可缓存最近会话，以改善启动体验，但远程后端仍作为主要数据源。原“搜索消息”和“会话资源窗口”整合进聊天历史查看器；资源项显示资源时间、来源消息和下载/打开状态，且不得与本地绝对路径绑定。

## 8. Live2D 功能需求

### 8.1 技术方案

优先使用 Live2D Cubism SDK for Web，并通过独立适配层接入 Vue 页面，避免聊天业务直接依赖具体 SDK API。

优先评估当前可用的 Cubism SDK for Web 版本。基于 Chromium 的 Electron 渲染环境适合承载 Web SDK；正式分发前必须确认 SDK、Cubism Core、模型及动作资源的版本兼容性与许可要求。

建议结构：

```text
Live2DView
    ↓
Live2DController
    ↓
Live2DAdapter
    ↓
Cubism SDK for Web
```

后续如更换渲染封装，不应影响聊天和状态管理模块。

### 8.2 模型加载

P0 至少支持两个已安装且通过校验的模型配置，以验证模型切换和失败回退。

模型资源至少包括：

- `.model3.json`；
- `.moc3`；
- 纹理；
- 动作文件；
- 表情文件；
- 物理设置；
- 姿势及其他模型配置。

模型加载状态：

```text
unloaded
loading
ready
failed
disabled
```

加载失败时：

- 显示静态头像；
- 提供重新加载；
- 在日志中记录原因；
- 不影响聊天功能。

### 8.3 基础动作

P0 至少实现：

- 待机动作；
- 自动眨眼；
- 呼吸效果；
- 头部或视线轻微跟随鼠标；
- 点击角色触发一个预设动作；
- AI 说话时切换为说话状态。

### 8.4 角色状态

需要定义统一的角色状态，不直接在业务代码里写具体动作文件名：

```text
idle        空闲
listening   等待用户或接收输入
thinking    AI 正在思考
speaking    AI 正在输出或播放语音
happy       积极情绪
sad         低落情绪
surprised   惊讶
error       发生错误
```

角色状态由聊天状态、后端事件或 TTS 播放状态驱动。

映射示例：

```text
后端开始生成      → thinking
首段内容到达      → speaking
音频开始播放      → speaking + mouth_sync
生成完成          → idle
工具等待确认      → listening
工具执行失败      → error
```

### 8.5 表情和动作协议

后端可以返回角色表现建议：

```json
{
  "expression": "happy",
  "motion": "greeting",
  "priority": 2
}
```

客户端必须校验：

- 表情是否存在；
- 动作是否存在；
- 优先级是否合法；
- 是否允许打断当前动作。

后端不能直接传入本地动作文件路径。

### 8.6 口型同步

Demo 采用基础音量驱动方案：

- 获取正在播放的 TTS 音频音量；
- 将音量映射到 Live2D 嘴部张合参数；
- 对音量变化进行平滑处理；
- 音频停止时逐渐闭嘴。

Demo 暂不要求：

- 精确音素识别；
- 字词级口型；
- 摄像头输入；
- 麦克风实时 MotionSync。

精确 MotionSync 可以在后续版本评估；实施前应独立确认相关组件的许可、性能和 Linux 环境兼容性。

### 8.7 Live2D 设置

用户可以配置：

- 显示或隐藏角色；
- 角色音量；
- 角色缩放；
- 角色位置；
- 鼠标跟随开关；
- 自动动作开关；
- 渲染帧率：自动、30 FPS、60 FPS；
- 性能模式。

设置需要持久化到客户端本地。

## 9. 本地能力系统

### 9.1 系统定位

本地能力系统是 Electron 客户端中独立于聊天界面的受控执行层。

```text
远程 Agent
    ↓ WSS
工具请求路由
    ↓
权限检查
    ↓
用户确认
    ↓
本地工具执行器
    ↓
结果过滤
    ↓ WSS / HTTPS
远程 Agent
```

### 9.2 P0 工具

#### `desktop.file.select`

由用户主动打开系统文件选择器。

参数示例：

```json
{
  "multiple": false,
  "filters": [
    {
      "name": "Text",
      "extensions": ["txt", "md", "json", "py"]
    }
  ]
}
```

返回：

- 用户选择的路径；
- 文件名称；
- 文件大小；
- MIME 类型或扩展名。

#### `desktop.file.read`

读取用户选择或已经授权的文件。

限制：

- Demo 默认只读取文本文件；
- 默认最大文件大小建议为 2 MB；
- 二进制文件不直接作为文本读取；
- 读取前验证路径；
- 检测文件是否已经被删除或替换；
- 返回内容前进行大小限制。

#### `desktop.file.write`

创建或修改文本文件。

执行前显示：

- 目标路径；
- 操作类型：新建或覆盖；
- 修改内容；
- 原文件和新文件差异；
- 请求原因。

用户操作：

- 允许一次；
- 拒绝；
- 取消当前 AI 任务。

写入要求：

- 优先使用临时文件后原子替换；
- 写入前检查原文件哈希；
- 文件已被外部修改时停止覆盖；
- 保留失败信息；
- Demo 阶段不提供无确认批量覆盖。

#### `desktop.screen.capture`

支持：

- 选择一个屏幕；
- 选择一个窗口；
- 取消截图。

返回：

- 图片宽高；
- 图片格式；
- 客户端生成的附件 ID；
- 可选的缩略图。

限制：

- 每次截图都需要用户确认；
- Demo 不支持静默截图；
- Demo 不支持连续录屏；
- 上传远程服务器前明确提示图片会被发送给 AI。

Linux Wayland 环境应优先使用操作系统提供的屏幕选择和授权流程，不能假设 Windows、X11 和 Wayland 的捕获行为完全一致。

### 9.3 本地工具请求格式

建议采用统一协议：

```json
{
  "type": "tool.call",
  "call_id": "call_123",
  "conversation_id": "conv_123",
  "tool": "desktop.file.read",
  "runtime": "desktop",
  "arguments": {
    "path": "/home/user/project/README.md"
  },
  "reason": "读取项目说明，以回答用户的问题",
  "risk_level": "medium",
  "approval_authority": "client",
  "expires_at": "2026-08-03T12:00:00Z"
}
```

客户端返回：

```json
{
  "type": "tool.result",
  "call_id": "call_123",
  "runtime": "desktop",
  "success": true,
  "result": {
    "content": "...",
    "size": 1024
  },
  "duration_ms": 26
}
```

失败返回：

```json
{
  "type": "tool.result",
  "call_id": "call_123",
  "runtime": "desktop",
  "success": false,
  "error": {
    "code": "PERMISSION_DENIED",
    "message": "用户拒绝了文件读取请求"
  }
}
```

### 9.4 权限确认窗口

确认窗口至少显示：

- 请求操作；
- 请求来源；
- 当前会话；
- 操作原因；
- 目标文件、目录、窗口或屏幕；
- 将被发送到服务器的数据；
- 风险提示。

P0 操作选项：

```text
允许一次
在工具允许范围授权时：允许指定目录或受控命令模板
拒绝
```

范围授权必须显示工具、目录或命令模板、参数约束、后端身份、有效期，并可在设置页撤销。路径或域名黑名单始终优先。

### 9.5 任务取消

以下情况需要取消本地工具请求：

- 用户点击拒绝；
- 用户关闭确认窗口；
- 请求超时；
- 会话被删除；
- WebSocket 断开；
- 后端主动取消；
- 应用退出；
- 参数校验失败。

取消结果需要回传服务端，避免 Agent 无限等待。

### 9.6 操作审计

客户端保存最近的本地操作记录：

- 时间；
- 会话；
- 工具名称；
- 目标资源；
- 是否获得授权；
- 是否成功；
- 执行耗时；
- 错误类型。

默认不得在日志中保存：

- 完整文件内容；
- 截图内容；
- 认证 Token；
- 用户消息全文；
- 密钥和密码。

## 10. 客户端与服务端通信

### 10.1 通信方式

建议采用混合方式：

```text
HTTPS / REST
├── 登录或认证
├── 获取会话列表
├── 获取历史消息
├── 上传和下载附件
└── 客户端配置

WSS / WebSocket
├── 用户消息
├── AI 流式回答
├── 生成状态
├── Live2D 状态事件
├── 本地工具请求
├── 本地工具结果
└── 心跳与取消
```

Demo 也可以先全部使用 WebSocket，但消息协议仍应按类型分层。

### 10.2 客户端注册

客户端连接后提交能力信息：

```json
{
  "type": "client.hello",
  "client_id": "desktop_abc123",
  "client_version": "0.1.0",
  "platform": "windows",
  "arch": "x64",
  "capabilities": [
    "desktop.file.select",
    "desktop.file.read",
    "desktop.file.write",
    "desktop.screen.capture"
  ]
}
```

服务端不得调用客户端未注册的能力。

### 10.3 WebSocket 状态

客户端需要显示：

```text
connecting
connected
reconnecting
offline
authentication_failed
server_error
```

断线重连要求：

- 使用指数退避；
- 设置最大重试间隔；
- 网络恢复后自动重连；
- 重连时携带最后确认的事件序号；
- 避免重复执行本地工具；
- 待确认工具请求在重连后不得自动执行。

### 10.4 消息顺序与幂等

每个事件应包含：

- 事件 ID；
- 会话 ID；
- 消息 ID；
- 时间戳；
- 可选序列号。

工具调用必须使用唯一 `call_id`；生成请求仍可使用独立的 `request_id`，两者不得混用。

同一个 `call_id` 被重复发送时：

- 已完成：返回之前的结果摘要；
- 执行中：返回执行中状态；
- 已拒绝：保持拒绝状态；
- 不得重复写入文件或重复截图。

## 11. Electron 客户端架构

### 11.1 进程划分

#### Renderer 渲染进程

负责：

- Vue 页面；
- 聊天界面；
- 会话列表；
- Live2D 渲染；
- 权限确认 UI；
- 设置界面；
- 本地任务记录展示。

渲染进程不得直接访问 Node.js 文件系统。

#### Preload

负责：

- 通过 `contextBridge` 暴露有限的桌面 API；
- 校验 Renderer 请求格式；
- 封装 IPC 调用；
- 不暴露原始 `ipcRenderer`。

示例概念接口：

```typescript
interface DesktopApi {
  selectFile(options: SelectFileOptions): Promise<SelectedFile>;
  respondPermission(input: PermissionResponse): Promise<void>;
  getAppInfo(): Promise<AppInfo>;
  openExternal(url: string): Promise<void>;
}
```

#### Main 主进程

负责：

- 应用生命周期；
- 创建窗口；
- IPC；
- 系统文件选择器；
- 文件读写；
- 截屏；
- 权限状态；
- 本地工具执行；
- 日志；
- 系统能力；
- 与远程服务的关键安全边界。

Demo 应启用上下文隔离和进程沙箱，并避免向不可信 Renderer 暴露 Node.js 能力；即使处于验证阶段，也应按正式应用的安全边界实现。

建议配置原则：

```text
nodeIntegration: false
contextIsolation: true
sandbox: true
webSecurity: true
```

## 12. 安全需求

### 12.1 远程内容隔离

- 不加载远程服务器返回的任意 HTML 页面；
- AI Markdown 必须经过清理；
- 禁止内嵌脚本；
- 禁止 `eval`；
- 禁止远程代码进入主进程；
- Renderer 不得拥有 Node.js 完整权限；
- IPC 通道使用显式白名单；
- IPC 参数必须进行运行时校验。

### 12.2 文件安全

每次文件操作至少检查：

1. 路径是否合法；
2. 路径规范化后是否变化；
3. 是否位于用户授权范围；
4. 是否通过符号链接跳出授权目录；
5. 文件是否过大；
6. 文件类型是否允许；
7. 是否属于敏感路径；
8. 写入前文件是否被外部修改。

默认敏感路径示例：

```text
~/.ssh
~/.gnupg
~/.aws
~/.config 下的密钥文件
浏览器用户数据目录
系统凭据目录
.env
凭据和 Token 文件
```

Demo 可以采用警告和禁止相结合的策略。

### 12.3 截图隐私

截图确认窗口需要明确说明：

- 将截取哪个屏幕或窗口；
- 图片是否会上传远程服务器；
- 图片将用于什么任务；
- 用户可以取消。

不得：

- 应用启动后自动截图；
- 在后台周期性截图；
- 将截图用于当前任务以外的用途；
- 未经确认长期保存截图。

### 12.4 凭据存储

服务器认证信息不得以明文写入普通 JSON 配置文件。

Windows 优先使用系统凭据能力；Linux 优先接入 Secret Service。Demo 若暂时无法实现，应至少：

- 将凭据和普通设置分离；
- 不输出到日志；
- 不发送给 Renderer；
- 清晰标注为需要在正式版本修复的安全债务。

### 12.5 服务端身份校验

客户端应：

- 默认只连接 HTTPS/WSS；
- 验证 TLS 证书；
- 禁止忽略证书错误；
- 验证服务端协议版本；
- 认证失败后停止自动重试；
- 不允许远程服务器动态替换客户端代码。

自定义模型 Endpoint 同样视为不可信出站目标：远程地址默认只允许 HTTPS；本机 HTTP 仅在显式“本机 Provider”模式下允许；需要校验 DNS、实际连接地址、重定向、私网/云元数据地址、域名黑名单和自定义 Header，跨域重定向不得携带模型密钥。

## 13. 设置页面

Demo 设置页面包含：

### 13.1 模型服务设置

- LLM、STT、TTS 三类 Model Profile；
- Provider、模型、声音和模型执行位置；
- 凭据配置状态；
- 连接、最小推理、语音识别测试和 TTS 试听；
- 切换当前 Profile；
- 新增、复制、编辑和删除自定义 LLM、STT、TTS Profile；
- 自定义 Profile 至少包含类型、显示名称、模型 ID、兼容协议、服务地址、可选能力参数和凭据引用；

- 认证 Token；
- 连接测试；
- 当前连接状态；

### 13.3 聊天与语音设置

- Enter 发送开关；
- 自动滚动；
- 代码块字体大小；
- 是否自动播放 TTS。
- 普通录音输入；
- 实时语音会话；

- 语音活动检测。

- 输入法转写专用 STT Profile 与隐私策略；

普通/实时语音输入属于直接语音交互：可以显示 STT 字幕，但字幕不进入可编辑文字草稿。只有“按住说话转文字”会修改聊天输入框。

### 13.4 Live2D 与外观设置

- 启用 Live2D；
- 切换已安装 Live2D 模型；
- 缩放；
- 位置；
- 帧率；
- 鼠标跟随；
- 动作开关；
- 口型同步开关。
- 字体缩放；
- 代码字体大小；
- 强调色；

### 13.5 安全与权限设置

- 当前可用本地能力；
- 沙盒目录；
- 路径黑名单；
- 域名黑名单；
- 权限审批历史；
- 已授权目录；
- 已授权命令模板；
- 授权范围、来源、有效期和撤销；
- 黑名单优先于沙盒和历史授权。

### 13.6 开发与诊断设置

- WebSocket 事件日志；
- Live2D 状态；
- 客户端能力列表；
- 工具调用测试；
- 打开日志目录；
- Renderer DevTools。
- 开发者模式开关；
- 前端日志目录；
- 导出脱敏诊断信息；
- 生产构建默认关闭开发者模式。

## 14. 错误处理

客户端需要覆盖以下错误：

| 错误          | 用户表现          |
| ----------- | ------------- |
| 服务器无法连接     | 顶部显示离线状态并允许重试 |
| 认证失败        | 提示重新配置凭据      |
| 流式输出中断      | 保留已有内容并提供重试   |
| Live2D 加载失败 | 降级静态头像        |
| 文件不存在       | 工具卡片显示失败原因    |
| 文件被外部修改     | 停止写入并提示冲突     |
| 用户拒绝权限      | 通知后端并继续聊天     |
| 截图被系统取消     | 视为用户取消，而非程序异常 |
| 工具请求超时      | 自动取消并回传超时     |
| Renderer 崩溃 | 尝试恢复窗口并记录日志   |
| 服务端协议不兼容    | 阻止高风险工具调用     |

错误提示需要对普通用户友好，同时日志保留可定位问题的错误码。

### 15.2 Message

```typescript
interface Message {
  id: string;
  responseId?: string;
  conversationId: string;
  role: "user" | "assistant" | "system" | "tool";
  content: MessageContent[];
  assistantSegments?: AssistantSegment[];
```

## 16. 非功能需求

### 16.1 性能目标

Demo 阶段目标：

- 普通电脑上聊天滚动无明显卡顿；
- Live2D 开启时不明显阻塞消息流式显示；
- Live2D 可以根据负载从 60 FPS 降至 30 FPS；
- 单个会话显示至少 200 条消息时仍可正常操作；
- 收到流式事件后，UI 尽快更新，避免明显批量延迟；
- 文件读取和网络上传不得阻塞 Renderer 主线程；
- 空闲内存占用以不超过约 500 MB 为优化目标，而非 Demo 阻断标准。

### 16.2 稳定性

- Live2D 异常不导致聊天崩溃；
- 单次工具执行异常不导致 WebSocket 关闭；
- 断线重连不重复执行写文件操作；
- 应用异常退出后能够恢复最近会话；
- 所有异步操作均应具有超时和取消机制。

### 16.3 跨平台

P0 验证环境：

```text
Windows 10/11 x64
Ubuntu 22.04 LTS x64
Ubuntu 24.04 LTS x64
```

允许平台实现存在差异，但上层工具协议保持统一。

例如：

```text
desktop.screen.capture
```

在 Windows 和 Linux 下可以使用不同实现，但服务端不应感知底层差异。

### 16.4 可维护性

- Main、Preload、Renderer 类型定义共享；
- 网络协议具有版本号；
- 使用运行时 Schema 校验外部数据；
- 本地工具使用注册表机制；
- Live2D 使用适配层；
- 禁止在 Vue 组件中直接散落 IPC 调用；
- 所有工具拥有独立测试；
- 高风险操作必须有自动化负面测试。

## 20. 主要风险

### 20.1 Live2D 许可和资源许可

风险：

- SDK、Cubism Core、模型和动作资源可能具有不同许可；
- 开源发布、免费分发和商业分发的要求可能不同。
- AI/Chatbot 与可切换、可扩展角色应用可能适用专门的发布分类；不能仅依据个人或小规模使用推定豁免。

处理：

- SDK 接入前确认 LICENSE；
- 模型资产单独记录来源和授权；
- 对外发布前按 Live2D 官方 AI/Chatbot 与 Expandable Applications 流程确认是否需要审核或出版许可；
- 不将未获授权的模型提交公开仓库；
- 构建流程区分代码和受限资产。

### 20.2 Ubuntu 屏幕捕获差异

风险：

- X11 和 Wayland 的屏幕捕获流程不同；
- Wayland 通常需要系统 Portal 和用户选择；
- 不同桌面环境行为可能不同。

处理：

- 将截图工具抽象为平台适配器；
- 先验证 Ubuntu 22.04 实际桌面环境；
- Demo 接受系统弹出的选择窗口；
- 不追求静默捕获。

### 20.3 远程 Agent 权限风险

风险：

- Agent 生成错误工具参数；
- 提示词注入诱导客户端读取敏感文件；
- 重复消息导致重复执行；
- 服务端被入侵后滥用客户端权限。

处理：

- 本地权限层不可绕过；
- 不信任服务端参数；
- 高风险操作逐次确认；
- 路径和工具白名单；
- 请求幂等；
- 操作审计；
- Demo 不开放 Shell。

### 20.4 Electron 资源占用

风险：

- Live2D、长消息列表和多个窗口同时运行时资源占用增加。

处理：

- Demo 仅创建一个主窗口；
- Live2D 支持关闭和降帧；
- 长消息采用分段或虚拟滚动；
- 避免在隐藏窗口继续高帧率渲染；
- 对模型纹理和动画资源进行优化。

## 22. 初版产品决策建议

为了避免 Demo 范围失控，v0.1 建议暂时采用以下默认决定：

```text
平台：
先保证 Windows 可用，同时维护 Ubuntu 兼容性；
阶段结束前完成一次 Ubuntu 打包验证。

布局：
默认四区布局（导航、会话、聊天、右侧 Live2D），Live2D 栏可折叠且不得覆盖聊天。

认证：
服务器地址 + Token，不制作完整登录注册系统。

通信：
REST 获取历史，WebSocket 处理聊天流和工具调用。

Live2D：
至少两个可切换的已安装模型配置，基础动作和音量口型，不做摄像头追踪。

模型服务：
设置页管理内置和自定义 LLM、STT、TTS Profile，支持新增、编辑、类型化测试和切换，不回显密钥；输入法转写拥有独立开关，并可单独选择一个兼容的 STT Profile。

语音：
支持普通录音输入、实时语音会话和按住说话转文字。前两者属于直接语音交互，识别字幕不写入文字草稿；只有按住说话转文字会把最终文字写入输入框且不自动发送。输入法转写复用兼容 STT Profile，其执行位置可为 Backend、Local Worker 或受控的本机前端适配层，首版开放范围待确认。

本地文件：
只操作用户选择的文本文件。
写入前必须确认并显示修改内容。

截图：
每次由用户确认，允许选择屏幕或窗口；
上传前明确说明截图将发送给远程 AI；
不支持静默截图、连续截图或录屏。

权限：
提供允许一次、受控范围授权和拒绝；
设置页管理沙盒目录、路径/域名黑名单、审批历史、已授权命令和目录；
黑名单优先，所有范围授权可撤销。

工具：
客户端实现 `desktop.file.select`、`desktop.file.read`、`desktop.file.write`、`desktop.screen.capture`；
后端工具和统一 Tool Registry 按补充需求同步实现；
不开放任意 Shell、PowerShell 或 Bash 字符串；`desktop.command.run` 不属于默认 P0，只有单独确认进入 Demo 后才注册本地受控模板。

数据：
会话历史以远程服务为主要数据源；
客户端只缓存最近会话、界面设置和脱敏后的执行记录。

审计：
所有 Runtime 的工具调用使用统一 `call_id`、状态和审计记录；
日志不得保存 Token、完整文件内容、截图内容或敏感参数。
```

以上默认决定用于启动 Demo，不代表正式版本的最终产品约束。Review 后如有调整，应同步更新功能范围、协议、安全模型和验收标准。
