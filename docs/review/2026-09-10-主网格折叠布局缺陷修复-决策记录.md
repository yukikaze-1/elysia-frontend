# 主网格折叠布局缺陷修复（2026-09-10）

**记录日期：** 2026-09-10

**文档状态：** 生效中

**触发：** 真机启动后截图显示「会话列表跑到右下角、角色面板错位」——会话栏出现在窗口最右侧一列（压在角色栏上），角色面板则被压扁。

**结论：** 是**真实布局缺陷**，不是截图缩放/视口误读。根因在 `gridTemplateFor`，且**被一条断言旧行为的单元测试长期合法化**。

---

## 1. 现象与实测数据

真机 1200×760（Electron，mock 后端），点击「折叠会话列表」后：

| 量 | 折叠前 | 折叠后（缺陷态） | 折叠后（手动补 `display:none`） |
|---|---|---|---|
| `grid-template-columns` | `60px 260px 540px 340px` | `60px 479px 340px` | 同左 |
| 计算列 | 4 列 | **5 列** `60px 479px 340px 0px 221px` | 5 列 |
| `.cy-conversations` | x=60 w=260 | **x=979 w=221** | w=0 |
| `.cy-main`（聊天） | w=540 | **w=579**（本应 800） | w=800 |
| `.cy-live`（角色栏） | y=0 h=760 | **y=0 h=617**（被压扁） | **y=0 h=760** |

第四行是关键：手动补上 `display:none` 后布局**立即完全恢复**，证明肇因就是该元素仍参与布局。

---

## 2. 根因

`gridTemplateFor`（`src/renderer/src/layout/effective-layout.ts`）旧实现按「隐藏区不生成对应列」生成模板：

```ts
const conv = effective.conversationShown ? `${effective.conversationWidth}px` : null
const cols  = [nav, ...(conv ? [conv] : []), 'minmax(0, 1fr)', ...(live ? [live] : [])]
const areas = ['nav', ...(conv ? ['conv'] : []), 'chat', ...(live ? ['live'] : [])].join(' ')
```

即折叠时列与**区域名**一起消失。但 `.cy-conversations`（`CyConversationList` 根元素）始终带 `grid-area: conv`，**只要它在任一时刻仍参与布局**，CSS Grid 的规则就是：

> 带名项指向不存在的区域 → 该声明无效 → 退回**自动放置** → 落进隐式列

隐式列宽度为 `auto`（由内容决定），于是它撑成 221px、被放到最右列；同时它自身高度撑满，把同一行的 Live2D 面板压缩。这正是截图现象。

### 2.1 为什么长期没被发现

`computeEffectiveLayout` 的推导**完全正确**（`conversationShown=false` 是预期保护行为），坏的是「如何把这个结果翻译成 CSS」这一步。而当时的三条测试都只断言**模板字符串本身**：

- `effective-layout.spec.ts`：`expect(g.gridTemplateAreas).toBe('"nav chat live"')`
- `layout.store.spec.ts`：`expect(...gridTemplateAreas).toBe('"nav chat"')`

它们把缺陷形态**当成正确期望钉住了**——实现与测试一致地错，所以全绿。**没有任何用例在真机里量过几何**。

---

## 3. 修复

### 3.1 网格模板：区域名永久保留，隐藏区宽度置 0

```ts
const conv = effective.conversationShown ? `${effective.conversationWidth}px` : '0px'
const live = effective.live2dShown ? `${effective.live2dWidth}px` : '0px'
const cols = [`${effective.navWidth}px`, conv, 'minmax(0, 1fr)', live]
return { gridTemplateColumns: cols.join(' '), gridTemplateAreas: '"nav conv chat live"' }
```

两种情形都正确，**不再依赖 `display:none` 的生效时机**：

- 元素被隐藏 → 0px 列不占视觉空间，与旧行为等价；
- 元素仍参与布局 → 落在自己的 `0px` 轨道内，不产生隐式列、不位移、不挤压。

原先「隐藏列占位把聊天排进错误列」的顾虑不成立：`chat` 是 `minmax(0, 1fr)`，`0px` 的 conv 轨道不影响它。

### 3.2 `App.vue` 补一层显式隐藏

`.cy-app` 绑定 `is-conv-hidden` / `is-live-hidden`，用 `:deep(> …)` 命中子组件根元素。
绑在 `.cy-app` 自己身上而非给子组件传 `:class`：子组件根带的是**自己的** scope id，父组件普通选择器命中不了它（实测传 `:class` 无效）。

### 3.3 语义澄清：`v-show` 并未失效

修复过程中一度据探针读数（`getComputedStyle(...).display === 'block'`）判断「`v-show` 没写下 `display`」。**该判断是错的**：

- 既有集成测试 `electron-live2d.spec.ts:327` 断言折叠后 `.cy-live` 不可见，且为绿；
- 同一探针换用事件驱动等待后，读到折叠后 `.cy-conversations` 计算 `display` **正是 `none`**。

即那些 `block` 读数是**静态等待取到的未稳定时机**，不是框架行为。文档与注释中因此**不**声称 `v-show` 失效——真正的教训是「网格模板的正确性不应押在隐藏时机上」。

## 6. 教训

1. **纯函数导数正确 ≠ 渲染正确。** `computeEffectiveLayout` 一直是对的，错在「推导结果 → CSS」的翻译层；这一类缺陷只有量真机几何才能发现。
2. **钉住字符串的测试会合法化缺陷。** 三条测试都断言模板字符串，于是「实现错 → 测试跟着错 → 全绿」。
3. **静态 `waitForTimeout` 取证不可靠。** 本次排查中它给出过与事实相反的读数（`display: block`），并把我引向「`v-show` 失效」的错误结论。**应以 `expect.poll` 或等待具体不变式成立来取证**。
4. 变异性验证（改回旧实现看用例是否变红）是区分「真回归网」与「自证式用例」的唯一手段。
