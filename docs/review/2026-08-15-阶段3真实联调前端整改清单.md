## 2. FE-S3-INT-P0-01：日期查询按后端自然日契约发送

### 2.1 当前问题

`RealBackend.fetchHistoryStream()` 当前把用户选择的 `localDate` 先转换为 UTC 半开区间，再发送：

```text
date_from=2026-08-13T16:00:00.000Z
date_to=2026-08-14T16:00:00.000Z
timezone=Asia/Shanghai
```

后端权威契约实际是：

```text
date_from=2026-08-14
date_to=2026-08-14
timezone=Asia/Shanghai
```

后端随后自行把自然日转换为 UTC 半开区间。当前前端值无法被后端 `date.fromisoformat()` 当作日期解析，最终会得到 200 空页，使用户误以为当天没有历史。

### 2.2 已拍板的修改

`apps/desktop/src/main/transport/real-backend.ts::fetchHistoryStream()` 应改为：

```ts
if (input.localDate) {
  params['date_from'] = input.localDate
  params['date_to'] = input.localDate
}
params['timezone'] = input.timeZone
```

约束：

1. 前端只传用户选择的 `YYYY-MM-DD` 自然日；
2. timezone 继续传 IANA 名称；
3. 不在 Adapter 内预转 UTC，不发送排他的 next-day 时间戳；
4. 无日期筛选时省略 `date_from/date_to`；
5. `localDateToHalfOpenRange()` 若仍被其他本地功能使用可保留，但不得用于该后端请求。

### 2.3 必须修改/新增的测试

- `real-backend-search.spec.ts` 改为断言 `date_from=2026-08-14`、`date_to=2026-08-14`；
- `Asia/Shanghai` 当天边界真实数据能被命中；
- UTC 与一个 DST 时区按自然日正确命中；
- 未选择日期时请求不含两个日期参数；
- 后端返回非法日期/时区错误时，历史查看器展示结构化错误，不显示伪空态。

## 4. FE-S3-INT-DEP-02：混合附件 `kind` 以前端逐文件语义为准

### 4.1 冻结的请求形态

当前前端对每个文件按顺序构造一组 multipart part：

```text
kind=image
files=<a.png>
kind=video
files=<b.mp4>
kind=file
files=<c.pdf>
```

该语义现正式冻结：

1. 每个 `kind` 只作用于紧随其后的一个文件；
2. 一个批次可包含不同 kind，仍保持一次上传与整批原子性；
3. 当前文件字段名为 `files`；后端负责同时兼容旧 `files[]`；
4. 前端不按 kind 拆成多个请求，避免破坏整批原子性；
5. kind 只是提示，上传响应中的 kind/mime 与服务端附件记录才是权威；
6. 上传成功后发送消息时继续把响应值映射为 `{attachmentId, kind, mime}`。

### 4.2 前端守护测试

- 直接检查 `FormData` part 顺序为 `kind, files, kind, files...`；
- PNG + MP4 + PDF 混合批次保持各自 kind；
- audio/webm + video/webm 的提示顺序不串位；
- 后端返回的权威 kind 与提示不同，以响应值构造消息引用；
- 任一文件失败时不发送聊天消息且队列保留可解释失败状态；
- 取消上传后无迟到发送。

后端的逐文件解析、旧单 kind 兼容、歧义拒绝与回滚要求见配套后端清单。
