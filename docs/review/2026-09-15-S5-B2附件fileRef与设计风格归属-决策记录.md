## 1. S5-B2 为什么要做（以及我先做的那次实测）

### 1.1 选题过程（先量后改）

原计划是「先跑 15 分钟实测探针，再定方案」。探针（`tests/integration/h01-fileref-probe.spec.ts`）
在真实 Electron（Mock 装配、`cyrene://` 生产产物）里量到：

| 观测 | 读数 |
|---|---|
| `getPathForFile(new File + 真 DataTransfer)` | `""`（空串） |
| `getPathForFile(new File(...))` | `""`（空串） |
| `getPathForFile(Object.create(File.prototype))` | `THREW: TypeError: getPathForFile expected to receive a File object but one was not provided` |
| 对端递伪造 `path`（`AttachmentInputFile` 无该字段） | `SCHEMA_VALIDATION_FAILED`（preload 字段白名单丢弃） |
| 合成 File（无 bytes） | `SCHEMA_VALIDATION_FAILED`（path 空 + 无 bytes ⇒ schema 拒） |
| 合成 File + bytes / 纯 bytes | `ok:true`，**进 bytes 分支，点名文件名被忽略** |

⇒ **对端无法让 `path` 承载任意主机路径**；它只能操作真实 OS 拖入/选中的文件。
据此我在探针出具后**建议不做结构性修法**（改为「探针升级为门禁 + 文档写清结论」）。

### 1.2 用户的裁决：仍然做全套

用户选择「还是做『Main 持表 + fileRef』全套」。**理由成立且已写进代码注释**：
即使今天攻击面已被 Chromium 行为压住，**「路径由对端命名」这一结构本身就是弱点**——
它把安全性寄托在 `getPathForFile` 的行为上（上游行为变化即静默失效），且 Main 侧无从区分
「用户真的选了这个文件」与「对端说它选了」。改为 token 后，**Main 自己的表**成为信任锚。

> **取证的诚实性说明**：探针结论**不因裁决而改写**。本记录如实保留「实测显示攻击面比 review 描述的小」
> 这一结论，同时记录「结构性收口仍然值得做」的理由。两者不矛盾：前者是**今天的可利用性**，
> 后者是**边界形态**。

## 2. S5-B2 落地形状

### 2.1 为什么不是 HMAC 签名（设计取舍，重要）

直觉方案是「Main 用只存在于主进程的密钥对路径签 HMAC」。**本仓的信任边界做不到**：
`main/ipc/registry.ts` 的 `isTrustedSenderFor` 只校验 webContents + mainFrame + URL
⇒ **Main 无法区分 preload 世界与页面主世界的 invoke**（同一帧）。
于是任何「由 preload 携带的秘密」都在对端可达面上，**签名方案的秘密本身不成立**。

可用的信任锚只有 **Main 自己的内存**：token 随机生成、路径只存在 Main 的表里。
效果等价且更简单——对端只能引用 **Main 登记过的**文件，且无法从 token 反推路径。

### 2.2 机制

| 环节 | 实现 |
|---|---|
| 表 | `main/attachments/file-ref.ts`：`Map<token, {path, issuedAt}>`，插入序即最旧序 |
| token | `fileref_` + 32 字节 CSPRNG hex（**不是**路径的哈希——无可计算关系） |
| TTL | `FILE_REF_TTL_MS = 10 * 60 * 1000`（与工具域 `SELECT_EXEMPT_TTL_MS` 同量级） |
| 容量 | `FILE_REF_MAX = 256`，超限逐**最旧**；`resolve` 时惰性清过期 |
| 铸造点 | **唯一**：preload 的 `toIpcDescriptor` → `webUtils.getPathForFile` → IPC `attachments:register-file-ref` |
| 铸造方 | preload 对同一个 `File` **复用** token（`WeakMap` 缓存），故 validate 与 upload 只登记一次 |
| 消费点 | `UploadService.resolveFileRef`（本文件内唯一的「token → 路径」入口） |
| 失败态 | 未装配表 / token 未知 / 已过期 ⇒ **fail-closed**，落 `forbidden_path`（**不是** `not_readable`——伪造引用与真实 IO 故障必须在日志里可区分） |
| 清空 | 断线重连即失效（会话内凭证，不跨连接复用） |

### 2.3 改动面

- `shared/contracts/attachments.ts`：`UploadFileDescriptor.path` → **`fileRef`**；新增 `FileRefRegisterResponse`。
- `shared/contracts/ipc.ts`：`IpcChannels` 新增 `fileRefsRegister`（**IPC 面 +1 通道**）。
- `main/ipc/channels.ts`：schema 换字段 + `fileRefsRegisterSchema`。
- `main/attachments/file-ref.ts`（新）、`upload-service.ts`、`attachments-handlers.ts`。
- `main/ipc/handlers.ts` / `channel-budgets.ts` / `main/index.ts`：装配与预算声明。
- `preload/desktop-api.ts`：`toIpcDescriptor` 改 async + `registerFileRef` + `WeakMap` 复用。
- 测试：`file-ref.spec.ts`（新 7 条）、`upload-service.spec.ts`（+2 fail-closed）、`attachment-validate.spec.ts`（改桩 + 1 条 token 无效）、
  `attachments-contracts.spec.ts`（类型级 + schema 级守护）、`attachments-handlers.spec.ts`、`desktop-api-attachments.spec.ts`（改分流 mock + 1 条复用）、
  `ipc-limit.spec.ts`（path 上界 → fileRef 上界）、`ipc-surface-alignment.spec.ts`（自动对齐）、`temp-dirs.ts`（探针前缀登记）。

**未变**：命中 token 之后的 realpath 规范化、userData 排除、`PATH_BLACKLIST_DEFAULTS` 黑名单、
大小与魔数复核**逐条照旧**。本表只回答「这个路径是谁登记过的」，**不**回答「这个路径是否安全」。

### 2.4 常驻回归门禁（本项最有价值的产出之一）

`h01-fileref-probe.spec.ts` 从「一次性取证」升级为**硬断言门禁**：

```text
expect(getPathForFile(合成 File), '...否则 preload 会把攻击者指定的路径登记进 fileRef 表').toBe('')
```

理由：fileRef 改造换掉了信任锚，但「对端只能引用 Main 登记过的文件」这条链条**仍然**依赖
`getPathForFile` 不解析合成 File——preload 会把它**任何**非空返回值登记进表。
若未来 Electron 改变该行为，防线会**静默失效**；故此处必须硬断言。

## 3. S5-B2 的边界与残余风险（如实声明，勿高估）

1. **`bytes` 分支仍可被直调**：对端能把任意字节 POST 到**当前已连接后端**并取得后端附件引用
   （`attachment.store.ts:74/103` 只是正常调用者，不是强制入口）。受每类型大小上限／聚合上限／文件数上限约束；
   对端本就能 fetch/WS 出网 ⇒ **单独看无额外权限提升**，唯一新增能力是「往会话里塞一个后端附件」。
   **本项不主张已消除该面。**
2. **真实文件路径在集成层无自动化覆盖**：集成夹具只能构造合成 File（`DataTransfer` + `new File`），
   而那恰好落进 `bytes` 分支。`fileRef` 分支由 **preload 单测**（mock `webUtils`）覆盖，
    **没有**「真 OS 拖入一个真文件 → 端到端上传成功」的自动化证据。
3. **未做变异验证**：新增断言未逐条验证「把实现改回坏形态会红」。
4. **`fileRef` 表是会话内内存态**：进程重启即失效，不做持久化（也不该做）。
5. **token 在 TTL 内可重复使用**：同一次拖入的 validate 与 upload 各用一次是正常路径；
   若要求「一次性消费」，属另一项取舍（当前未做）。
