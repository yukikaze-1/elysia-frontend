# 第三方资产授权与来源：立为显式阻塞项

**记录日期：** 2026-09-10

**文档状态：** 生效中

**决策类型：** 阻塞项登记（scope / 发布前置条件）

**影响范围：** 任何对外分发的产物（安装包、试用版、客户交付、公开仓库 Release）；doc 12 §4.7 G-01～G-03；doc 16 §4；doc 09 §10／§12／§17

**证据来源：** [前端门禁体系评估与整改记录](2026-09-10-前端门禁体系评估与整改记录.md) §5

---

## 1. 背景

Stage H 闭账后对仓库做了一次门禁与就绪度评估。评估在「第三方资产」这一面得到一个与既有文档口径不一致的结论：

- doc 16 §2 把**阶段 5（Live2D）记为「已真实联调」**；
- 但 doc 12 §4.7 的 **G-01（SDK 许可与发布分类）、G-02（合法可用模型）、G-03（表情/动作白名单与许可）至今仍是 `[ ]`**；
- 阶段 8 暂缓决策记录把 H-01／H-02／H-04／H-07 列为阻塞项，其「恢复后首批工作」第 5 条包含「资源授权和来源完整性检查」——即**资源授权被当成阶段 8 的一个 checkbox**。

评估发现的关键事实是：它**不是「还没做的 checkbox」，而是「今天连判定手段都不存在」**。这意味着若继续把它留在阶段 8 的清单里，它会以一个无法被评估的状态被继承下去。

## 2. 实测事实（本次评估，只读核对）

### 2.1 会随产物出货的部分

- `third_party/CubismSdkForWeb-5-r.5/`：**291 个跟踪文件、25.1 MB**（Core 0.51 MB / Framework 0.82 MB / Samples 23.76 MB）。
- 应用内 vendored 副本与 SDK 逐字节一致（实测 SHA256 全等）：`renderer/src/live2d/framework/` 59 个 `.ts`、13 个 shader、`live2dcubismcore.min.js`（228,050 B）。`THIRD_PARTY_NOTICES.md` 自述「未对源码本体做任何修改」**实测成立**（这对许可义务是有利事实）。
- 这些文件**确实进产物**：现有 `out/renderer/live2d/live2dcubismcore.min.js` + 13 shader 实测存在，`electron-builder.yml` 的 `files` 含 `out/**`。
- Cubism Core 是**专有软件**（非开源）。仓库内唯一的明确再分发授权是 `Core/RedistributableFiles.txt`，只覆盖 3 个文件（`live2dcubismcore.d.ts/.js/.min.js`）——**不覆盖 Framework 源码、不覆盖 shader、不覆盖 Samples 里的 8 个模型**。

### 2.2 不会随产物出货的部分（降低但不消除风险）

- **模型默认不出货**：`electron-builder.yml` 只打 `out/**` + `package.json`；模型由 `scripts/live2d-install.mjs` 装配进 **userData**（`%APPDATA%\Cyrene\models` 等）。
- 本机 userData 已装配 3 个模型（`haru` / `lil` / `wanko`）；其中 `lil` 的 `LICENSE.txt` 由装配工具按缺省模板生成，**来源写的是一个 gitignored 的本地临时目录**（`tmp/修女莉尔免费版/…`），仓库内零 provenance。
- `tmp/` 下另有 3 个第三方模型原档（约 265 MB），`git ls-files tmp` = 0。

### 2.3 许可正文与判定记录的缺失

- 仓库内 5 份许可/声明文件（SDK 根 `LICENSE.md`、`Core/LICENSE.md`、`Framework/LICENSE.md`、vendored 副本、`THIRD_PARTY_NOTICES.md`）**都不含许可条款正文**，只有指向 live2d.com 的 URL。
- `LICENSE.md` 里确实写明的两条可执行信息：
  1. **「All business users must obtain a Cubism SDK Release License」**，business = 最近会计年度营收 > 1000 万日元；
  2. Free Material License 覆盖的模型白名单恰为 8 个 `Samples/Resources/*`，且要求**逐个模型**同意其条款。
- **仓库内完全缺失**：四份 EULA 正文、Release License 适用性/签署结论、AI-Chatbot 与 Expandable Applications 分类的审批结论（doc 05 §15 与 doc 09 §17 都把它列为发布前必做）、8 个示例模型的逐模型承诺记录、3 个第三方模型的作者授权与来源。

### 2.4 构建/校验链上没有任何许可或来源检查

- `verify-sensitive-core.mjs` 的 `EXCLUDED_DIR_PREFIXES` **整树排除** `third_party/` 与 vendored live2d 两树，其注释自述「不留行级 allowlist 兜底——vendor 更新即静默放行」。这是**为机密扫描**做的合理取舍，但它同时意味着这三棵树不在任何扫描面内。
- `verify-artifact.cjs` 只做产物存在性、CSP、3 条**秘密**正则与 Fuse 读回；doc 09 §12 要求的「许可文件存在」「Live2D Manifest 资源完整」**均未实现**。
- 全仓无任何 license/provenance/SBOM 工具（`license-checker` / `oss-attribution` / `sbom` 等 grep 0 命中）。

## 3. 决策

1. **把「第三方资产授权与来源」立为显式阻塞项 `EXT-01`**，从 doc 12 §4.7 的 G-01/G-02/G-03 里提升出来，登记在 doc 16 §4。
2. **它的约束面是「任何对外分发的产物」，不局限于阶段 8。** 阶段 8 暂缓与否、是否开工，都不改变这条阻塞；反过来，阶段 8 的 H 组决策齐备也不解除它。
3. **不要求它成为阶段 5 的追溯性未完成项。** 阶段 5「已真实联调」记录的是运行时集成证据，这一点不变；本决策只声明：该证据**不构成**可对外分发的许可依据。doc 12 §4.7 的 G-01～G-03 行补一条指向本记录的注记，不再被读作「阶段 5 的遗留欠账」。
4. **当前可接受的用途**：内部/个人开发验证（doc 05 §15.1 已明确「开发验证可先行」）与本机 userData 装配。**不可接受**：把含 SDK 的产物交付给第三方，或在公开渠道分发。

## 4. 解除条件

`EXT-01` 的解除需要下列**全部**形成仓库内可查的记录（缺一不可，且必须是仓库内的产物而非口头结论）：

1. Cubism SDK Release License 的适用性判断与签署结论（谁判断、依据、日期）；
2. AI-Chatbot / Expandable Applications 分类的官方答复留档（doc 05 §15 / doc 09 §17 既有要求）；
3. 8 个示例模型的逐模型 Free Material License 承诺记录；
4. 3 个第三方模型的作者授权 + 来源 URL + 版本（当前 `lil` 只有本地临时路径）；
5. 四份 EULA 正文落入 `third_party/`（否则每次审查都依赖外网可达性）；
6. 一条**覆盖 vendor 的**许可/来源门禁接进构建或 CI（现在 vendor 三树被机密扫描整树排除，且无任何替代检查）。

第 6 条是本决策相对既有文档的新增要求：前 5 条是「补齐材料」，第 6 条是「防止材料再次腐烂」——没有它，本轮补齐的结论会在下一次 SDK/模型更新时静默失效，与 `verify:sensitive` 长期全红是同一类失效模式（见评估记录 §3）。

## 5. 本记录不做的事情

- **不主张侵权，也不做法律结论。** 本记录只陈述「仓库内无法证明合规」这一事实状态；条款原文不在仓库内，评估期对外网 EULA 的抓取亦被网络策略拒绝，因此本记录不解释条款含义。
- **不修改 doc 09 的发布设计**，只登记阻塞；doc 09 的发布矩阵更新归阶段 8 恢复后的工作。
- **不把 SDK 移出仓库**。vendoring 是阶段 5 的既定实现（CSP 不放宽、`cyrene://` 同源供给），本决策不改变它。
