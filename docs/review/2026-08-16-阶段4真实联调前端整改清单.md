## 3. FE-S4-RUN-P0-01：采集启动失败不能造成“前端 idle、后端 RECORDING”

### 3.1 真实复现

1. 前端已连接，语音开关开启；
2. 点击普通录音；
3. `voiceStore.startRecord()` 先调用 `api.voiceStartRecord({recordingId})`；
4. 后端接收 start 并进入 RECORDING；
5. 让 `PcmCapture.start()` 发生确定性失败（与真实权限拒绝、无设备、AudioContext 初始化失败同一 catch 路径）；
6. 前端设置 `micError`，清除 `activeRecordingId`，将 mode 改为 idle，再调用 `api.voiceDiscard()`；
7. Main 的 `RealBackend.discardVoice()` 只执行 `ws.send()`，随即清除本地 `activeVoice` 并 resolve；
8. 后端异步返回 `CONTRACT_VALIDATION: 录音中，先 stop 再 discard`；
9. 前端本地允许再次 start，后端却返回 `VOICE_SESSION_CONFLICT: 已有活动语音会话`。

本轮随后用原 recordingId 补 `voice.record.stop` 才恢复后端状态；再做 start/stop 探针无错误，证明冲突来自残留录音而不是 STT/连接故障。

### 3.2 代码位置与根因

文件：

- `apps/desktop/src/renderer/src/stores/voice.store.ts:256-289`
- `apps/desktop/src/main/transport/real-backend.ts:1001-1014,1052-1056`
- `apps/desktop/tests/unit/voice.store.spec.ts:327-336`
- `apps/desktop/tests/unit/real-backend-voice.spec.ts`

根因有三层：

1. Renderer catch 在清理协议完成前先清 `activeRecordingId` / mode；
2. `voiceDiscard()` 是 fire-and-forget，Promise 成功只代表 `ws.send()` 未同步抛错，不代表后端接受；
3. 单测 mock 的 `voiceDiscard.mockResolvedValue(undefined)` 把“已发送”和“服务端已取消”误当成同一件事。

另外，后端本轮的第一条错误码是 `CONTRACT_VALIDATION`，不属于 `VOICE_ERROR_CODES`，因此只走 `onChatError`；用户看到的是本地 micError，不会获知服务端仍处于 RECORDING。不能依赖错误展示提醒用户手动重连。

### 3.3 必须修改的行为

1. 将普通录音取消收敛成一个内部 helper，统一处理：采集启动失败、待发送删除、重录、设置页测试麦克风收尾及组件卸载；
2. helper 必须保留 recordingId 到取消帧成功发送后再清本地录音状态，不能提前丢失唯一关联 ID；
3. 配套后端修复后，采集启动失败继续使用 `voice.discard`，语义为“不 stop、不 STT、直接取消”；
4. 若 `ws.send()` 同步失败/已断线，不得静默吞掉后仍表现成一次成功清理；应进入断线清理或保留可诊断错误，由连接 reset 统一收口；
5. 不把 `voiceStopRecord` 作为最终契约：stop 表示请求转写，采集启动失败不应触发 STT；仅在兼容旧后端时可考虑有明确版本门控的临时 fallback，不得成为长期双发顺序；
6. 后端修复后的序列必须是 `start(A) -> discard(A) -> start(B)`，不需要断开重连；
7. realtime/dictation 的 capture failure 现有 `cancelRealtime` / `cancelDictation` 不得回归。

### 3.4 必须补充的测试

- voiceStore：`capture.start` reject 后保留同一 recordingId 完成 cancel helper，再回 idle；
- voiceStore：取消帧同步发送失败时不静默伪装成功；
- RealBackend + 有状态协议桩：start 后直接 discard，服务端接受后再次 start 成功；
- 真实错误序列回归：若后端返回 `CONTRACT_VALIDATION`，测试必须能发现本地 active registry 与服务端状态失配，不能只断言 `voiceDiscard` 被调用；
- Electron 集成：模拟 `NotAllowedError`/无设备/AudioContext 失败，随后普通录音、realtime、dictation 均能无需重连再次启动；
- 设置页“测试麦克风”启动失败后退出设置，聊天页仍可立即开始语音。

## 4. FE-S4-RUN-P1-01：空录音清理测试必须对齐真实异步协议

### 4.1 真实复验后的准确现象

使用确定性静音 MediaStream，经真实 UI 立即 stop：

1. 待发送条出现并显示“未识别，请重试”；
2. 确认发送禁用；
3. 点击删除后待发送条正常消失、普通录音按钮恢复，连接保持；
4. 后端随后异步返回 `VOICE_RECORDING_NOT_FOUND: 无活动录音`；
5. `onChatError` 收到 `backendCode=VOICE_RECORDING_NOT_FOUND`，real-backend 同时发出 `voice.error`；连接级横幅因现有语音码抑制没有出现。

因此此前“删除会卡死”的推断不成立，文档和测试不得这样描述。真实缺陷是：正常的用户清理动作被协议记为错误，Mock 又完全看不到这条异步错误。

### 4.2 直接原因

- 后端 `<640B` 或 STT 空结果会自动回 IDLE，不发 transcript；
- 前端为了保留本地 AudioBuffer 试听，仍维持 `record_pending`；
- `discardRecord()` 发送 discard 后立即清 UI；
- RealBackend 控制方法没有 discard ACK，后端错误稍后从公共错误通道返回；
- MockBackend `discardVoice()` 无条件清 active、不会模拟 `VOICE_RECORDING_NOT_FOUND`；
- 当前 Electron “未识别”用例只证明 UI 文案/按钮，不证明真实后端状态机与错误通道。

### 4.3 必须修改的行为和测试

1. 消费配套后端的幂等 discard 语义：空/过短/空转写后的删除、重录、测试麦克风收尾均不得收到错误；
2. 保留“未识别”本地待发送态和本地试听能力；不要求为了消除错误而立刻丢掉 AudioBuffer；
3. MockBackend 至少要建模 recording 的 RECORDING/TRANSCRIBING-or-terminal/PENDING 关键边界，不能所有 discard 都无条件成功且不产生任何后端语义；
4. 增加 real-backend/协议桩测试，覆盖 `<640B/empty -> stop -> discard` 与 `discard -> discard`；
5. 测试同时订阅 `onChatEvent` 和 `onChatError`，断言用户正常删除没有 `VOICE_RECORDING_NOT_FOUND`、`CONTRACT_VALIDATION` 或连接错误；
6. 重录必须在同一连接上成功，旧录音迟到错误不得污染新录音的字幕/按钮；
7. 设置页 3 秒测试录音的 `stop -> replay -> discard` 需覆盖 STT 非空、空结果和 discard 与 STT 完成竞态；
8. 不通过扩大 connectionStore 错误抑制列表来“修复”后端错误；错误帧本身应在配套后端修复后消失。

## 5. FE-S4-RUN-P1-02：字幕等待期必须与“未识别”终态分开

### 5.1 现状与根因

`voiceStore.stopRecord()` 在控制帧发出后立即把 mode 设为 `record_pending`，此时 `record.transcript` 仍为 `undefined`。`CyVoicePending` 只按“有没有 transcript/error”渲染，因此在 SenseVoice 仍正常转写的窗口内已经显示“未识别，请重试”。

当前所谓 45 秒兜底 timer 到期后只再次执行：

```text
caption = ''
record.transcript = undefined
```

这两个字段在 transcript 尚未到达时本来就是空值，所以 timer 到期前后没有任何可观察状态变化。代码注释、决策记录 D-P17 和真实 UI 行为不一致。

代码位置：

- `apps/desktop/src/renderer/src/stores/voice.store.ts:307-320`
- `apps/desktop/src/renderer/src/components/CyVoicePending.vue:10-17,40-43`
- `apps/desktop/tests/unit/voice.store.spec.ts:271-291`

### 5.2 必须修改的行为

1. 增加明确的字幕等待状态，例如 `record.awaitingTranscript` 或等价状态机字段；
2. stop 成功发送后进入“正在识别…”；
3. 收到匹配 recordingId 的 `voice.transcript`、`voice.error`，或 45 秒 timeout 时结束等待；
4. 仅 timeout 且无 transcript/error 后显示“未识别，请重试”；
5. 等待中仍允许试听已有本地 AudioBuffer、删除和重录，但确认发送禁用；
6. 删除/重录/reset/断线/会话切换必须清 timer 和等待状态，迟到 transcript 不得复活已删除录音；
7. 匹配 recordingId 的正常字幕到达后直接展示字幕并启用确认，不得短暂闪烁“未识别”；
8. 明确 STT error 与未识别的文案优先级，保持现有语音错误不进入连接级横幅。

### 5.3 必须补充的测试

- stop 后 0~44.999 秒显示“正在识别…”，不显示“未识别，请重试”；
- 45 秒无 transcript/error 才切到未识别；
- 慢字幕在第 30 秒到达：立即显示字幕、timer 清除，45 秒后不被清空；
- 等待中收到 STT error：展示明确错误并结束等待；
- 等待中删除/重录：timer 清理，迟到 transcript 被 recordingId/state gate 忽略；
- Electron 集成使用可控延迟的协议桩验证界面不闪烁错误终态。
