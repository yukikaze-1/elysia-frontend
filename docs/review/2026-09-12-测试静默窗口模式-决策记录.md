# 测试静默窗口模式（Silent Test Window Mode）决策记录

**日期：** 2026-09-12
**状态：** 已实施（本机 Windows 取证完成；CI 侧待下一轮 run 复核）
**范围：** `apps/desktop` 的窗口呈现路径、DevTools 窗口、原生对话框与测试入口脚本；**不改业务语义**
**触发：** 用户报告——运行测试（尤其集成 / verify 流程）时 Electron 窗口频繁弹出、抢走前台焦点、
置顶、进任务栏闪烁，正在进行的全屏/无边框游戏被反复切出

---

## 1. 根因

### 1.1 为什么跑测试一定会弹窗

全仓（`src/`、`scripts/`、`tests/`、根目录）逐文件审计后确认：**应用窗口只有一处创建点**——
`src/main/windows/main-window.ts` 的 `new BrowserWindow(...)`，但它连着三条"一定会把窗口显示出来"的路径：

| 路径 | 代码 | 后果 |
|---|---|---|
| 首帧就绪 | `win.on('ready-to-show', () => showOnce())` → `win.show()` | 显示 + **激活 + 抢前台焦点** + 进任务栏 |
| 5s 兜底定时器 | `setTimeout(showOnce, 5000)`（`ready-to-show` 到达才 clear） | 即使首帧事件不来也会显示 |
| 单实例/激活 | `focusOrDefer()` → `raiseWindow()`：`restore() → show() → focus()` | 直接抢前台（`app.on('second-instance')` / `activate`） |

`launchApp()`（`tests/integration/helpers/app.ts`）每次调用都会启动一个真实 Electron 进程；
集成套件 27 个 spec 共 **55 次 `launchApp`**，因此一次 `pnpm test:integration` 会把"弹窗 → 抢焦点 →
关窗"重复几十遍；`electron-live2d` 这类长文件（单文件上百秒）更是长时间占据前台。
`pnpm verify:artifact --smoke` 同样以 Playwright 启动打包产物，属于同一族。

### 1.2 次要来源（审计结果）

| 面 | 调用点 | 测试期风险 |
|---|---|---|
| 原生对话框 | `dialog.showOpenDialog`（目录授权 `index.ts`、文件选择 `tools/tool-executors.ts`）、`dialog.showSaveDialog`（诊断导出 `diagnostics/diagnostics-service.ts`）、`dialog.showErrorBox`（启动/运行期致命错误 `index.ts`） | 即使主窗口隐藏也照样出现在桌面并夺走焦点；模态框会阻塞到有人点击 |
| DevTools | `src/main/index.ts` `onDevModeChange` → `webContents.openDevTools({ mode: 'detach' })`（诊断设置页开关）、`main-window.ts` F12 → `toggleDevTools()` | detached 是**第二个受管窗口**，抢焦点且自动化里没有观察者 |
| 测试夹具窗口 | `tests/integration/ipc-security.spec.ts` 两处 `new BrowserWindow({ show: false })`（非主窗口 IPC 拒绝 / 未知通道） | 不打扰（恒 `show:false` 且用后即毁） |

**明确不存在**（全仓 0 命中，故本轮不引入任何空实现）：`BaseWindow`、`BrowserView` / `WebContentsView`、
`Notification`、`Tray`、`globalShortcut`、`autoUpdater` / `electron-updater`、`app.focus()`、
`moveTop()`、`setAlwaysOnTop()`、`setFocusable()`、`setSkipTaskbar()`、`setVisibleOnAllWorkspaces()`、
`setFullScreen()` / `setSimpleFullScreen()`、Splash、About 窗口、登录/OAuth 窗口、设置独立窗口、
悬浮窗 / Overlay / Toast / 预览窗口；系统托盘、协议 handler（`second-instance` / `open-url`）皆无。

## 2. 设计

### 2.1 单一判据：`src/main/config/runtime-environment.ts`

```text
CYRENE_TEST_HARNESS=1      本进程由自动化 harness 启动（既有标记：appData 隔离门与调试开关放行门已在用）
CYRENE_WINDOW_MODE=…       显式指定 silent | visible
```

| 情形 | 结果 | 来源标记 |
|---|---|---|
| 显式 `silent` + harness | `silent` | `env` |
| 显式 `visible`（任意环境） | `visible` | `env` |
| 未指定 + harness（**默认**） | `silent` | `harness-default` |
| 未指定 + dev/生产 | `visible` | `default` |
| 显式 `silent` 但**无** harness | `visible`（降级） | `rejected-not-harness` |

刻意不依赖 `NODE_ENV`（Electron/Vite/Playwright 三方语义不稳定）；单例缓存，进程内不会模式漂移。
最后一行是安全边界：dev / `pnpm start` / 打包产物 / 安装版**永远不会**因环境残留而静默启动。

### 2.2 边界一：`src/main/windows/window-presentation.ts`

Main 里唯一允许直接调用窗口呈现 API 的地方：

- `windowOptionsForPresentation()`：silent 下**创建前**改写 `show:false` / `alwaysOnTop:false` /
  `skipTaskbar:true`，其余配置（尺寸、最小尺寸、标题、背景色、`webPreferences`）逐字保留；
- `createAppWindow()`：唯一建窗入口（`new BrowserWindow` 只在这里出现），建完立即启动出帧保活；
- `showWindow()` / `focusWindow()`：silent 下 no-op —— `ready-to-show`、IPC、`second-instance`、
  托盘恢复、任何业务 `showWindow()` 都不会 raise；`focusWindow()` 覆盖 `restore → show → focus` 组合；
- `setWindowAlwaysOnTop()`：silent 下**恒 false**（即便调用方要求 true）；`setWindowSkipTaskbar()` 同理恒 true；
- `toggleWindowDevTools()` / `openWindowDevTools()`：silent 下不创建 detached 窗口；dev / 打包
  devToolsAllowed 行为逐字不变；
- `lastWindowPresentation()`：留痕实际生效的三项选项与保活形态（`skipTaskbar` 在 Electron 无 getter，
  集成断言只能靠它）。

**处理优先级**（按任务书 1→6）：不 show → 不 focus → 不 moveTop → 不置顶 → `skipTaskbar` →
**不设 `focusable:false`**。最后一条是刻意的：改 `focusable` 会动 renderer 的焦点/键盘语义
（`activeElement`、focus 事件、输入法），而 Playwright 的键盘断言正建立在其上。

### 2.3 出帧保活（本轮最关键的一处实测发现）

**隐藏窗口不等于冻结窗口，但也不等于正常窗口**：`show:false` 且从不 show 的窗口在
Electron 43 / Windows 上 `document.hidden === false`、`visibilityState === 'visible'`、
IPC/定位/键盘全部正常，**但 rAF 被压到约 1 帧/秒**：

| 观测（真实应用 `--mode test` 产物，Playwright 直读） | rAF 回调数 |
|---|---|
| 静默（隐藏）：600ms 窗口 / 1500ms 窗口 | **0 / 1~2** |
| 同一窗口 `show()` 之后（可见） | 121 / 500ms、360 / 1500ms、720 / 3000ms |
| 静默 + `webContents.beginFrameSubscription(false, …)`（在页面就绪后订阅） | **134 / 600ms、240 / 1000ms**（窗口仍 `isVisible:false`） |
| 静默 + **创建期**订阅（即 `new BrowserWindow()` 之后立刻订阅） | **0**（6s 预算内一帧都没有） |
| 静默 + `--disable-renderer-backgrounding` / `--disable-backgrounding-occluded-windows` / `--disable-features=CalculateNativeWinOcclusion` | 无改善（1~2） |
| 静默 + 主进程 60Hz `webContents.invalidate()` | 无改善（1） |

Live2D 渲染环、滚动跟随、`reduce-motion` 等页面行为全部建在 rAF 上，1 帧/秒会让这些集成用例
超时或断言失真——"静默"不允许以牺牲 renderer 语义为代价。因此统一建窗层在 silent 下
**订阅呈现帧**（回调里直接丢弃帧）：窗口保持**未映射**（不进桌面、不抢焦点、不进任务栏、
不把全屏游戏顶出去），合成器照常出帧。

**订阅时机是承重的**（实测，勿"优化"掉）：导航会重建 renderer 视图，**创建期建立的订阅收不到
任何帧**（上表第 4 行）。故首次订阅挂在 `dom-ready` 上——该事件在每次导航后都会到达，
renderer 崩溃自动 reload 后同样会重新订阅；单次订阅 700ms 内无帧则重试（最多 3 次），
重试耗尽才回退。修正订阅时机后，真实应用在启动后 200ms 即已落定为
`frameKeepAlive: 'unmapped'`，且 6s 观测窗口内 `isVisible` 恒为 false、rAF 稳在 ~220 帧/秒。

平台回退（如实记录，不是静默降级）：若 `beginFrameSubscription` 不可用或重试耗尽，
则回退为「映射但不可见」——先置不透明度 0、令鼠标穿透，再 `showInactive()`（映射但**不激活**）。
`setOpacity` 在 Linux 上是 no-op（Electron 文档明载），故 Linux 上该回退路径等于"窗口被映射且可见，
但不抢焦点、不进任务栏"——见 §6 残余风险。

### 2.4 边界二：`src/main/native-ui/dialog-service.ts`

| 运行形态 | 行为 |
|---|---|
| 生产 / dev | 逐字委派 Electron `dialog`（含"有父窗/无父窗"两种调用形态） |
| harness + visible | 真实弹窗 + 记录调用（人工观察时仍可点） |
| harness + silent | **不弹任何原生窗口**：记录调用 + 返回确定性「用户取消」（`canceled:true`）；`showErrorBox` 改为 stderr 留痕（原生模态框会阻塞到有人点击，测试看起来像卡死） |

测试仍可经 harness 探针 `__cyreneMainProbe.getDialogInvocations()` 断言"是否触发 / 参数是否正确 /
取消结果是否被正确处理"；需要"用户确实选了某路径"的分支继续用既有注入缝
（`pickFile` / `pickDirectory` / `openPath`），不让适配层猜测试意图。

### 2.5 可维护性：把审计结论变成门禁

`tests/unit/window-presentation-guard.spec.ts` 扫描 `src/main/**` 源码并要求：

1. `new BrowserWindow(` / `new BaseWindow(` 只允许出现在 `windows/window-presentation.ts`；
2. show/hide/focus/blur/restore/minimize/maximize/unmaximize/moveTop/setAlwaysOnTop/setSkipTaskbar/
   setFocusable/setVisibleOnAllWorkspaces/setFullScreen/setSimpleFullScreen/openDevTools/toggleDevTools/
   closeDevTools 只允许出现在该文件；
3. `dialog.show*` 只允许出现在 `native-ui/dialog-service.ts`；
4. Notification / Tray / globalShortcut / autoUpdater / `app.focus()` / `moveTop()` 在 Main 里必须为 0。

例外表硬编码且当前为空（漂移时必须有人显式改表）。判别力已做变异验证：临时加入一个含
`new BrowserWindow` / `win.show()` / `win.setAlwaysOnTop(true)` / `dialog.showMessageBox` /
`new Notification` 的文件后，四条规则相应变红，删除后复绿。

## 3. 测试入口

| 命令 | 模式 |
|---|---|
| `pnpm test`（单测） | 不启动 Electron，与窗口模式无关 |
| `pnpm test:integration` | 集成套件，**默认 Silent**（窗口不显示/不抢焦点/不置顶/不进任务栏/无原生对话框） |
| `pnpm test:integration:visible` | 同一个套件，**窗口真的显示**（人工观察窗口/焦点/任务栏/DevTools） |
| `pnpm verify`（新增） | `typecheck → lint → test → test:integration → build`，集成段同为静默 |
| `pnpm verify:artifact --smoke` | 打包产物冒烟，显式 `CYRENE_WINDOW_MODE=silent` |
| `pnpm test:e2e` | 仍是**未实现**的非零占位命令（阶段 8），提示已指向 `test:integration[:visible]` |
| Stage H runner | 沿用 harness 默认（silent）；需要肉眼观察时在 shell 里 `CYRENE_WINDOW_MODE=visible` |

可视化模式用独立 vitest 配置（`vitest.integration.config.visible.mts`）注入 `CYRENE_WINDOW_MODE=visible`，
而不是 shell 环境变量前缀——仓库跨 Windows/Linux，`FOO=1 cmd` 只在 bash 下成立，为一个变量引入
`cross-env` 依赖不划算（依赖清单本身受文档与门禁管辖）。测试侧仍有一层显式默认：
`helpers/app.ts` 的 `suiteWindowMode()` 缺省 `silent`，与 Main 的解析互为独立防线。

CI 未改动：Linux `xvfb-run` 与 Windows 运行时取证 job 都直接调 `test:integration`，
因此自动继承静默模式，不需要新增任何环境变量。

## 5. 残余风险（如实记录）

1. **Linux 回退形态**：`setOpacity` 在 Linux 是 no-op，若该平台也不提供 `beginFrameSubscription`，
   静默模式会退化为"窗口被映射、可见，但不抢焦点、不进任务栏"。CI（xvfb）无真实桌面，无实际影响；
   本地 Linux 桌面运行 `test:integration` 时仍会看到窗口——需要时用 `test:integration:visible` 显式确认，
   并把本项当作平台差异而非缺陷。
2. **出帧保活的成本**：静默模式以订阅帧换取渲染保真（测试期 CPU 用量上升），这是"不改 renderer 语义"
   的代价，只作用于测试进程，生产不订阅。
3. **打包产物冒烟不可目视**：`verify:artifact --smoke` 现在静默运行；要肉眼核对打包产物窗口行为，
   需临时以 `CYRENE_WINDOW_MODE=visible` 跑同一条命令。
4. **原生对话框的"成功路径"**：静默模式下对话框恒返回取消。需要验证"用户确实选择了路径"的用例必须走
   注入缝；若将来有人直接依赖真实选择器，会在静默运行下表现为"取消"，属预期行为而非 flake。
5. **本机取证范围**：rAF 数据来自 Windows / Electron 43.3.0 的实测；Linux/macOS 未在本机复核
   （CI 的 `linux-runtime` 与 `windows-runtime` 两层取证 workflow 会在下一轮 run 中覆盖）。
6. **全屏游戏**：首选形态下窗口从不映射，最不打扰；但 Electron 进程本身仍会创建顶层窗口对象，
   极端严格的全屏独占场景仍可能感知到进程存在——这属于 Electron 的固有限制，非本方案可消除。
