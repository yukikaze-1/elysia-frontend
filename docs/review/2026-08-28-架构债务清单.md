# 架构债务清单（独立盘点）

**日期：** 2026-08-28（Asia/Shanghai）
**性质：** 独立于《阶段 1-7 修缮候清单》（122 历史编号）的**架构层盘点**——评估当前代码的职责集中度、耦合、可测试性、边界清晰度。**只读盘点，未修改任何代码。**
**定位说明：** 用户明确「架构议题（RealBackend/MockBackend 体量、Preload/Main 装配集中度、Store 间依赖等）应另建架构清单，不能混入 122 个历史编号」。本清单即该独立架构清单。
**范围：** `apps/desktop/src` 全部非测试代码。

---

## 0. 总体结论

**上层重构是合理的**——`RealBackend`/`MockBackend` 各自 1292/1094 行实现同一 36 方法接口，且协议契约在 3 个 zod 层 + 跨仓 `frontend_contract` 手工镜像，是主要债务来源。

**但信任边界与解析层（protocol-v2）是健康的**——这是本仓库**最强的正面资产**（见 §3）。

**排序摘要：** 高 3 条（D1/D2/D3）+ 中 4 条（D4/D5/D6/D7）+ 低 3 条（D8/D9/D10）。**建议顺序：先 D2/D3（契约与双实现——已直接导致静默故障、维护成本最高），再 D1（RealBackend 拆类），然后 D4-D7。**

## 1. 高严重度

### D1. `RealBackend` 上帝类 —— 单类 10+ 职责
- **位置**：`main/transport/real-backend.ts`（1292 行，全仓最大文件）
- **债务**：一个 `class RealBackend implements BackendAdapter` 同时承担：WS 传输层（establishWs/onSocketClosed/scheduleReconnect/握手超时）、协议解析/分派（`handleFrame` 单函数 95 行 switch）、连接状态机、请求-响应关联（pendingAcks）、REST 会话方法、附件上传/签发、历史搜索 + image_video 双子流游标状态、模型/TTS 方法、语音控制帧（realtime/dictation/record）、工具提交 + 工具附件、TTS 音频缓冲、工具附件字节流 + PNG 魔数校验。
- **影响**：文件内以「// —— REST 会话方法 ——」等注释强行分段，但全在一个方法体边界内。改动任何一段（如音频缓冲）都要回归整个类。历史上多次 review 问题都集中于此。
- **严重度**：高
- **建议**：按职责拆为独立类——`RealWsTransport`（socket/状态机/重连）、`RealRestClient`（REST 会话/历史/模型）、`RealVoiceControl`（控制帧+音频缓冲）、`RealToolGateway`（工具提交+附件）。共享一个 `RealBackend` 门面。

### D2. 协议契约「三处镜像」无生成器 —— 漂移即整帧拒绝
- **位置**：wire 帧 `main/transport/protocol-v2/raw-schemas.ts`（543 行）+ 领域事件 zod `shared/schemas/events.ts`（267 行）+ 领域事件 TS 接口 `shared/contracts/events.ts`（209 行）；`DesktopCallStatus` 三处（`contracts/backend.ts:155` interface / `schemas/ipc-response.ts:398` schema / `rest-schemas.ts:196` 又一份 schema 副本，注释直言「两处修改需同步」）。
- **债务**：同一事件形状手工写 3 份（zod×2 + TS interface）。`Live2DDirective` 的 7 态枚举/priority 联合在 `raw-schemas.ts:324` 与 `schemas/events.ts:177` 各写一遍；providers/tts wire 又镜像跨仓 `frontend_contract/rest.py`。全程无代码生成，全靠纪律。
- **影响**：**已实际制造 bug 的向量**。代码注释多次记录「缺镜像 → preload `parseBackendEvent` 丢弃 → 语音功能静默失效」（P4-B 先例）、「缺镜像 → preload 丢弃」（C3）。三处不齐 = 合法帧被拒/功能静默断，而非显式报错。
- **严重度**：高
- **建议**：以单一源生成约束——用现有 `contracts/` 的 TS 类型推导 zod（现有 `ipc-response.ts` 已是 `z.ZodType<T>` 形态，可推广到 backend 事件），或引入 schema 生成器；至少消除「手写 zod 副本」，让 TS 类型成为 z.infer 的单一来源。

### D3. Mock / Real 两个独立 36 方法实现，仅靠接口约束行为
- **位置**：`main/transport/backend-adapter.ts`（接口 137 行，36 个方法）；`real-backend.ts` 与 `mock-backend.ts` 各自全量实现。
- **债务**：两者间的共享抽象只有 `BackendAdapter` 接口 + 少量工具函数（`redactToolArguments` 等）。RealBackend 有 connect 状态机/重连/REST/音频缓冲；MockBackend 从零重写全部 36 方法，自建 record/replay/emit/stamp 引擎。无共享基类，无行为契约。
- **影响**：任何行为改动须在两个文件重复落地，已产生 mock/real 漂移（如 `getToolCallStatus` mock「恒 null」、`queryStatus` mock「不注入 → 不查」、`sendAudioBytes` mock「无会话也计数」）。注释多处「与 real 语义对齐」正是靠人工对齐的佐证。
- **严重度**：高
- **建议**：抽出共享的领域行为片段（如 ack 关联/序列打戳/语音会话注册表），或让 mock 复用与 real 相同的「发送面」抽象（real 走 `ws.send`，mock 走记录器），把一个 36 方法面降到「一个接口 + 两个 3-5 方法差异类」。

## 2. 中严重度

### D4. `createToolService` 上帝闭包 —— 决策链/捕获子状态机/授权流/驱逐全在一个闭包
- **位置**：`main/tools/tool-service.ts`（513 行；一个函数闭包内 13+ 内部函数 + 8 个闭包容器）。
- **债务**：15 步决策链、4 执行器、capture 子状态机、目录授权流、per-path 写锁、TTL 驱逐、重连重发，全部耦合在一个闭包。与 `tool-executors.ts` **双向值导入循环**——`tool-executors.ts:9-10` 从 `tool-service` 导入常量/类型，`tool-service.ts:7` 导入 `createExecutors`。代码注释（「tool-service ↔ tool-executors 存在值导入互引……当前仅函数体内使用不触发 TDZ；若实现期遇循环 import 告警，把常量下沉到 limits.ts」）明确承认靠纪律规避。`grant-store.ts:11` 值导入 `ToolServiceError`。
- **影响**：逻辑无法脱离整套机器独立单测；决策链的优先级/幂等/授权命中判断内嵌在 513 行闭包；循环导入是 TDZ 隐患。
- **严重度**：中
- **建议**：按注释自荐方向，把 `FILE_READ_MAX_BYTES` 等常量下沉 `limits.ts` 切断 `tool-executors→tool-service` 值依赖；决策链抽成可注入的纯函数表。

### D5. Renderer Store 交叉耦合枢纽
- **位置**：`renderer/src/stores/`——`conversation.store.ts` 引 5 个外部 store（cache/connection/draft/message/voice）；`live2d.store.ts` 引 6 个（connection/layout/message/settings/tool/voice）；`voice.store.ts` 引 4 个（connection/conversation/message/settings）。
- **债务**：跨 store 通过 `useXxxStore()` 直接读对方内部状态，无事件总线/prop 边界。典型：**live2d 读 message.byId/order**（`live2d.store.ts:106-114` 遍历 `msg.order`/`msg.byId` 算 emotion 和正文明细）、**live2d 读 voice.tts.playing**（`setupMouthWatch` :163-184）。
- **影响**：live2d 对消息/语音内部结构形成隐性读依赖，任一 store 内部重排都会跨面破坏；难以替换/复用。
- **严重度**：中
- **建议**：至少把「live2d 读 message.byId」收成 message store 的显式 getter（如 `lastCompletedEmotion()`/`currentGenHasContent()` 已存在部分），减少对外暴露 byId/order。

### D6. `index.ts` 巨型组合根
- **位置**：`main/index.ts`（464 行）。
- **债务**：顶层解析 **18 个** `parseMock*Env` 桥（逐行 :178-215），装配 ~15 个服务（CredentialStore/SessionStore/SettingsService/ToolService/ChatService/UploadService/MediaService/Live2DRegistry/DiagnosticsService/GrantStore/ConnectionConfig/3 个 bridge 容器）。用 `mediaBridge`/`chatBridge`/`toolBridge` 三个容器打破 adapter→svc→media 环引用。装配顺序被大量注释约束（「SettingsService 上移——批次 C 需在 createToolService 之前装配」:295）。
- **影响**：组合根承载了过多装配决策 + 环境解析；顺序高度脆弱，任何服务构造顺序变化都可能触发注释里反复提到的「环引用」回归。
- **严重度**：中
- **建议**：把 18 个 env 桥解析函数抽到独立 `mock-env.ts` 模块统一导出，index.ts 只保留按序装配；服务构造改为显式依赖注入而非桥容器。

### D7. `voice.store` / `live2d.store` 单 store 约 10 职责
- **位置**：`voice.store.ts`（551）/ `live2d.store.ts`（492）。
- **债务**：voice 一个 store 管 三模式录制编排 + mic 采集 + 背压窗口 + ack-stall 定时器 + TTS 播放门 + 45s 转写兜底 + 10min 硬上限 + consent 门控 + 事件路由（`handleEvent` :127-216 单函数 15 case）；live2d 管 controller 生命周期 + GPU 重建 + 口部数据源 watch + 5 store 读值状态源 + 指令处理 + 可见性接线 + 切换持久化。
- **影响**：两者各有清晰分区（注释 D-P11/D-P16/D5B-04），但职责数超一个 store 合理上限；改动需跨多块回归。
- **严重度**：中
- **建议**：voice 的「采集/背压」「TTS 播放」「转写等待态」与 live2d 的「GPU 重建」「口部采样」各抽成可注入独立模块，store 保留编排。

## 3. 健康、无债务（正面资产）

**1. 信任边界方向干净（验证过）**
- `preload/` 不 import `renderer/`；`shared/` 不 import `main/` 或 `renderer/`；`renderer/` 不 import `main/`（三向 grep 均空）。`contextBridge` 暴露窄且 schema 校验（`desktop-api.ts` 每个方法经 `unwrap()`+zod）。工具的原始 arguments 永不进 Renderer（`tool.request` 领域事件契约不含 arguments）。这是本项目**最强的正面资产**。

**2. `shared/` 是真正的干净共享层（分层明确）**
- `contracts/` = 纯 TS 接口（类型），`schemas/` = zod 运行时，两者职责不混淆。Renderer/Main/Preload 共同消费而不产生反向依赖。

**3. protocol-v2 解析层与 transport 解耦、可独立测**
- `raw-schemas.ts`/`frame-mapper.ts`/`rest-mapper.ts`/`rest-schemas.ts` 只 import `@shared/contracts` + 少量 tools helper，不 import real-backend/mock-backend。帧解析、映射、REST 镜像可独立单测。`rawSchemasFingerprint()`（:528）提供契约门禁指纹，是设计上的一处亮点。
