## 2. 批次 ① H-01 结构性收窄（`dc8152e`）

### 2.1 评审说什么，实测是什么

全量评审 H-01 的标题是「`attachments:upload` 把 **Renderer 提供的字符串**变成任意本地文件读取，并上传出机」。

**实测：这条链不成立。** 关键在于 preload 的 `toIpcDescriptor`（`src/preload/desktop-api.ts`）**按字段逐个抄**，而不是 `{...f}` 展开：

```ts
const out: Record<string, unknown> = { localId: f.localId, name: f.name, size: f.size, mediaType: f.mediaType, source: f.source }
```

且面向 Renderer 的类型 `AttachmentInputFile` **没有 `path` 字段**；`path` 只能由 `webUtils.getPathForFile(f.file)` 铸造。我写了四组探针直接问"伪装的 path 能不能抵达 IPC 边界"：

| 攻击形态 | 入参实际收到的 |
|---|---|
| A 只给伪造 `path`（无 file/bytes） | `{localId,name,size,mediaType,source}`——**path 被完全丢弃** |
| B 伪造 `path` ＋ 真实 file | `path = /real/a.png`——**`getPathForFile` 赢** |
| C file 存在但 `getPathForFile` 返空串 ＋ 伪造 path | **path 被丢弃** |
| D `attachments:upload` 同样试 | **`getPathForFile` 赢** |

### 2.2 那真正该修的是什么

有一条**真的**：`UploadContent.path` 与 `real-backend.readUploadBytes` 里的 `fs.readFile(path)` 回退，是**全仓第二个「从 descriptor 取路径直接读盘」的解析点**，而那一层**没有** realpath、没有 userData 包含判定、没有敏感路径黑名单——四道守卫全在 `UploadService`。

实测该回退**从未执行**，依据三条：
- `UploadService` 是 `UploadContent` 的**唯一**构造点，且它两个分支（path 型／bytes 型）**都**填 `bytes`；
- `readUploadBytes` 优先返回 `bytes`；
- 工具附件走的是**另一个方法** `uploadToolAttachment(callId, bytes, mime, label)`，直接收 bytes，不经 `UploadContent`。

⇒ 删除它属"**删掉一段假能力**"，不是收紧策略。

### 2.3 改了什么

1. `UploadContent` 去掉 `path?`，`bytes` 改**必填** ⇒ 把"路径不再离开 `UploadService`"从**约定**升级为**类型级不变量**。
   佐证：改完 `pnpm typecheck` **0 错误**，即全仓无任何调用点依赖该字段——**这本身就是"它是死的"的证明**。
2. 删除 `readUploadBytes`（含 fs 回退），调用点直接用 `f.bytes`。
3. `upload-service.ts` 不再把 `path` 传给后端层。
   **保留不动**：`UploadFileDescriptor.path`（IPC 入参）——Main 仍需要它定位用户选的文件，四道守卫在那一层齐全。

### 2.4 新增守护（此前**两件事都没有门禁**）

缺口在于：IPC schema（`channels.ts`）**明确接受**自由 `path: z.string().max(1024)` 字符串，于是"安全"只体现为一行实现细节。
新增 4 条常驻用例（`tests/unit/desktop-api-attachments.spec.ts`）：
- **类型级**：`'path' extends keyof AttachmentInputFile ? false : true`——给 Renderer 面类型加 `path` 字段即**编译失败**；
- **行为级 3 条**：A/C（伪造 path 不抵达 invoke，validate 与 upload 各一条）＋ B（伪造+真 file 时 `getPathForFile` 赢）。

### 2.5 变异验证

把 `toIpcDescriptor` 的首行改成 `const out: Record<string, unknown> = { ...f }`：

```
× 行为级 A：只给伪造 path（无 file/bytes）⇒ 不抵达 invoke
   AssertionError: 伪造 path 竟然抵达了 IPC —— preload 的字段白名单被改坏了: expected true to be false
× 行为级 C：upload 通道同样吃不到伪造 path
× 另两条既有用例（webUtils 注入、P2-7 优先 path）
→ 4 failed / 10
```

已还原并复跑 10/10 绿。

## 5. 顺带查实的**门禁盲区**（本批意外收获）

那 4 条条目的 `reason` 原文写着「命中本文件 **11 行**／**22 行**」，而实测**各 1 行**。

原因是：这两个数字是 **2026-09-10 规则收窄为「像秘密」（`isSecretLikeBase64`）之前**的读数，规则收窄后没人回头改 reason。

**为什么长期无人发现**——测试里那条"reason 记的行数须与实测一致"的校验，**只对 `hitsForEntry(e).length > 1` 的条目生效**：

```ts
for (const e of GENERIC_ANCHORS.filter((x) => hitsForEntry(x).length > 1)) {
  expect(e.reason, ...).toContain(`命中本文件 ${hitsForEntry(e).length} 行`)
}
```

4 条**全部**是 1 行 ⇒ **整个循环体一次都不执行** ⇒ 过期读数永远不会被抓到。这是一个**结构性盲区**（不是"忘了改一个数字"），已在批次 ③ 连同 reason 一起更正，并把盲区本身写进测试注释。

## 7. 一次真实的流程事故（不淡化）

### 7.1 发生了什么

批 ④ 由 subagent 并行执行。它把该批的**暂存删除**（`git rm apps/desktop/tests/integration/electron-live2d.spec.ts`）放进了 **index**，但那 3 个替换文件**还没 `git add`**（仍是未跟踪）。

我在同一工作区提交批次 ② 时，用的是 `git add -- <我的两个文件>` 然后 `git commit -F <msg>`。**`git commit` 提交的是整个 index**，于是把 subagent 那个暂存删除一并带走：

```
[b2f5edb] 3 files changed, 79 insertions(+), 1035 deletions(-)
 delete mode 100644 apps/desktop/tests/integration/electron-live2d.spec.ts
```

**后果**：`b2f5edb` 删掉了原文件，却**没有带上**三个替换文件 ⇒ **HEAD 短暂丢失整个 Live2D 集成覆盖**（28 个用例）。这是一次**静默丢覆盖**，如果没被发现，CI 上会表现为"Live2D job 找不到测试文件"。

### 7.2 处置

1. `git checkout HEAD~1 -- apps/desktop/tests/integration/electron-live2d.spec.ts` 恢复原文件（**62900 B**，与原来一致），提交 `fc607db`。
   **取舍**：宁可让工作区**短暂重复覆盖**（原文件 + 三个新文件并存），也不让 HEAD 出现**缺覆盖**——缺覆盖是静默的，重复覆盖是显式的、且会在 subagent 提交时立刻暴露。
2. 立刻用 `send_message` 告知该 subagent：它的暂存删除已被我的提交消费掉、原文件已恢复，请**显式 `git rm`** 并在提交前 `git status` 确认范围（只见它自己的 5 个路径）。
3. 批次 ③ 起改用 **only 模式**：

```
git commit -F <msg> -- apps/desktop/scripts/verify-sensitive.mjs apps/desktop/tests/unit/verify-sensitive-e2e.spec.ts
```

`git commit -- <paths>` **绕过 index**，只提交指定路径的工作区内容——实测批次 ③ 的提交为 `2 files changed`，subagent 的暂存项**原封不动**留在 index 里。

### 7.3 教训

**只用 `git add -- <paths>` 不足以保证提交范围**——它只保证"我加了什么"，不保证"index 里没有别人的东西"。多 agent 共用一个工作区时，必须用 `git commit -- <paths>`（only 模式），或先 `git status` 确认 index 内容。

## 8. 我自己犯的两次同类错误：误删行尾换行

这两次都发生在**编辑文档时**，而且**两次都是同类**：

| 次序 | 文件 | 我做了什么 | 怎么发现的 |
|---|---|---|---|
| 第 1 次 | `docs/17-…环境与依赖安装记录.md` | 本意是"不做改动"，却误删了 `### 自动化工具不可用` 之后的一个空行（把标题与正文并成一行） | `git diff --numstat` 复核时发现"11 新增 / **0 删除**"的预期不成立，改为逐行看 diff 后还原 |
| 第 2 次 | `docs/08-…测试与Demo验收方案.md` | 修 doc 08 时第一次编辑**又**误删行尾换行，把 436／437 两行表格并成一行 | 复核 diff 时发现，已修复并以 `docs:check` + 逐行检查确认表格完好 |

**为什么容易犯**：我用编辑工具做"插入一段"时，若 `old_string` 里带了行尾、而 `new_string` 用"原文 + 新段"拼接却漏掉末尾换行，就会把**下一行**吸上来。这两次的共同点是**我以为那次编辑是无害的**。

**教训（已写进 doc 16 §3.1 与 `6b08b09`）**：**用编辑工具做"无操作"或"纯插入"时也要复核 diff**，不能假定无害。可操作的判据是——改文档后看 `git diff --numstat` 的**删除列是否为 0**（纯插入应为 0）；若非 0 且你并未打算删除，就是误删。

⇒ 这两条 `?.warn` 在生产**恒为 no-op**：代码**看起来**在告警，实际谁也看不到。这与我前几轮修的 `restFailure` 诊断面同族（"有留痕代码、无留痕效果"），但那处修的是"成因被吞"，这里是"**接线断着**"。

**代价**：往仓库里放后端生成物属**架构性决定**，且要定"何时刷新"的纪律 ⇒ 必须用户同意，故未做。

## 11. 批次 ④ 的关键事实（`72b9117`，由 subagent 执行）

**拆分依据**（本机 Windows i5 逐用例实测，**按耗时均衡切、不是按行数或 describe 均分**）：
原文件 28 例、`Duration 128.58s`／墙钟 `129.4s`。最重的单例是 C1 11.9s，其次 F-1 9.3s、B3 8.5s。

**结果**：`core` 12 例 / `motion` 7 例 / `settings` 9 例＝ **28 例，无删除、无新增、无改名、无 `--retry`、无超时放宽**。
用例体经脚本逐字节比对一致；仅"装配块 + 会话/设置操作原语"抽到**唯一一份**共享 helper `tests/integration/helpers/live2d-fixture.ts`

**耗时**：

```
拆分前：1 文件 / 28 例 / Duration 128.58s / 墙钟 129.4s  ← 单 job 关键路径
拆分后（每文件独立跑 = CI matrix 形态）：

合并跑（单进程串行三文件）：28/28 passed，Duration 125.12s / wall 125.9s
```

**CI 侧（`ci.yml`）**：
- `integration-live2d` 改 **matrix（3 文件 = 3 job，`fail-fast: false`）**。因 `pnpm <script> -- <args>` **不转发参数**（分片 job 出过"三片各跑全量"的假绿事故），故改为显式 `ensure:electron` + build 后**直连 vitest** 把 `${{ matrix.file }}` 当位置过滤器；判据写进注释：每个 job 的日志必须是 `Test Files 1 passed (1)`，过滤器没到位时 vitest 以 "No test files found" 非零退出，**不会静默变绿**。

## 12. 不确定 / 没写进去的地方

1. **批 ④ 对 CI 总墙钟的净收益尚未在 CI 上实测。** 单 job 关键路径降 60% 是本机实测；但 matrix 让 **3 个 job 各付一次 install + build 固定开销**。本机"三文件墙钟合计 126.3s vs 拆分前 129.4s"说明**总测试量几乎不变**，CI 上是否真的省了墙钟取决于 job 并行度与固定开销的相对大小。**按设计应省**（3 job 可并行、关键路径取最慢的 51.8s），但**我没有任何 CI 实测数据**，不作断言。
2. **H-01 的结构性修法只做到"删掉无守卫解析点 + 立守护"，没有做到"边界自我强制"。** 原因是我实测发现一个硬约束：`isTrustedSenderFor` 只校验到 `webContents` + `mainFrame` + frame URL，而 **preload 与页面主世界共享同一 frame** ⇒ **Main 在原理上无法区分"preload 发的 invoke"与"渲染进程发的 invoke"**。因此文档里"Main 签发不可猜 `fileRef`"这个说法**本身不完整**——若 `fileRef` 由一个"register 这个 path 换 ref"的通道签发，那个通道同样收 path、同样对渲染进程可达，`fileRef` **只是把字符串挪了一跳**。要让它真正成立，需要"preload 独有凭据（会话密钥签名）"或"只传 bytes"（后者会撞上已被声明为全局不变量的 4 MiB 单条 IPC 预算，而 video 上限 50 MB）。**这两条路我都没有实施**，属需用户裁决的方向选择。
3. **§5 的门禁盲区我只"更正了数据并写进注释"，没有把它变成一条会红的门禁。** 即：将来若再出现"reason 行数与实测不符且该条目只有 1 行"，仍然不会有人被提醒。
4. **批 ④ 的 28 例一致性是"脚本逐字节比对用例体"的结论**，我没有逐个人工阅读那 28 个用例的语义是否仍与拆分前等价（只验证了文本一致 + 28/28 通过）。
5. **本汇总里所有"实测"读数都来自本机 Windows 环境**（i5、静默窗口、`out/` 由 `electron-vite build --mode test` 重建）。CI（Linux 自建机）上的对应读数**我没有取**。
