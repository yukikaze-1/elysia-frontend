## 2. 落地内容与修法取舍

### P1-1 退出前 flush 在真实退出路径上恒空转

- **机制**（逐处读码复核，与报告一致）：`deliver()` 读 `getMainWindow()`；Windows/Linux 关最后一个窗口的顺序是 `close → closed`（此处 `setMainWindow(null)`）`→ window-all-closed → app.quit() → before-quit` ⇒ `before-quit` 时窗口已销毁，`deliver()` 恒 `false`，requester 立即 resolve（fail-open）。renderer 侧**无** `beforeunload`/`pagehide`/`unload` 补偿通道（本批复核：`src/renderer/**` + `src/preload/*` **0 命中**）。
- **修法**：`main-window.ts` 的 `win.on('close')` 一次性 `preventDefault()` → `await` flush requester（自带 700ms 预算）→ `win.destroy()`；钩子经模块级 `setBeforeCloseFlush` 注册（`focusOrDefer` 在 `second-instance`/`activate` 上重建窗口不带 opts，per-opts 会丢——沿用文件内 `crashSink` 已记录的同一理由）。`before-quit` 那条通道**原样保留**（`app.quit()` 路径上它仍先跑；requester 对在途请求幂等）。
- **为什么 `destroy()` 而不是再 `close()`**：flush 已完成，destroy 直接进 `closed`，避免二次 `close` 递归；renderer 无 `beforeunload` 处理器，跳过它不丢行为。
- **未采纳报告备选②**（renderer 侧 `beforeunload` + 同步 IPC）：会引入同步 IPC，而报告自己也把它列为次选。

### P1-2 看门狗对工具事件失明

- **机制**：`bootstrap` 在 `applyEvent` 之前 `return` 掉三族工具事件，而 `message.store` 的 `watchdog.touch` 只在 `applyEvent` 内、且只认带 `generationId` 的事件 ⇒ 工具等待期间窗口不被续命。
- **新增的生产证据（报告未给）**：后端等人工审批的上界是 **60.0s**（X99 `elysia-agent` HEAD `10acc315`：`Module/tool/safety.py:399` 的 `_hitl_timeout = 60.0`，等待点 `:790`），而 `generation.completed` 只在回合末发出且 `finish_reason` **硬编码 `"stop"`**（`core/cognitive/finalize.py`）⇒ 等待期间那一代**始终开着**。**60 > 50 是常量倒挂**，不是偶发竞态。已写入 doc 02 §10 的 ⚠️ 注记。
- **修法**：`tool.store` 增派生量 `toolWorkActive`（`visibleLiveOrder` 中非终态记录；**必须含 `running`**——`waitingForApproval` 只认 `awaiting_permission`，而后端等工具结果时同样静默）；bootstrap 用 **sync watch** 镜像进 `messageStore.setToolWorkActive`（不能在工具事件旁路里补一次调用：桌面工具的 `awaiting_permission` 走 `tool:event → upsertLocal`，**不经过**该旁路）；看门狗增 `setHold`，工具活动期间窗口放宽到 **180s**。
- **有意偏离报告建议的「暂停计时」**：`tool.store` 的记录**没有客户端过期**（状态只随事件推进），一条丢失的终态事件会让「工具有活动」永久为真 ⇒ 纯暂停**等于把 H-10 这张网永久关掉**，而 H-10 存在的理由恰恰是「后端丢终态」。故取「放宽到有限上界」：既不误杀，又保证后端真死时 3 分钟内仍收敛。
- **`hold` 有意跨 `disarm`/`arm` 存活**：`clearForGeneration` 让 `awaiting_permission` 跨代保留，若在 disarm 时清掉 hold，下一代就会退回 50s 再被同样的误杀命中。

### P1-5 向导取消后续体仍写共享 store

- **修法**：`submitGeneration` 世代号 + `onUnmounted`/`closeWizard` 双失效点；`activate`（切全局激活模型服务，后果更重的一半）与后续落库因此停止。
- **有意不采纳「提交中禁用取消」**：禁用会把用户锁在一个可能永不返回的请求里；栅栏让取消真正生效且随时可退出。用例显式断言「取消按钮保持可用」以钉住这个取舍。
- **附带修掉**：`cancelEdit` 不清 `testResult` ⇒ 重开向导显示上一次的「测试通过」（**过期绿灯**，与本仓反复出现的「绿灯含义被高估」同型）。
- **诚实边界**：取消发生在 `saveProfile` **已发出之后**时，那次远端写入无法收回（无补偿删除接口）；能保证的是**不再切换全局激活模型服务**、不再有后续写入。

### P1-6 dictation 会话标识竞态

- **机制**：第二次 start 的失败分支按「我这次失败」清理**共享**态（`dictationClientRequestId` / `capture` / `captureReady`）⇒ 第一次随后成功建立采集并置 `dictating`，但停止入口已没了 ⇒ **麦克风持续采集且无停止入口**；该标识全仓无任何事件回写，**不可自愈**。
- **可达路径**：「按住 → 松开 → 立刻再按」。UI 的 `dictationHold` 标记在松开时已清（其自身注释亦记录「单靠 store 门挡不住第二次 start」），故 store 层必须自己有门。
- **修法两层**：① `dictationStartInFlight` —— 整个 start 序列（控制帧 + 采集）的 in-flight 门，第二次 start 直接拒绝且**不碰任何共享态**（从源头消除）；② `dictationOwner` 世代判据 —— await 之后所有共享态写入须仍持有本世代，被接管者走 `abandonDictationStart` 收尾（停采集 + 清只属于本世代的标识 + 取消后端会话）；`stopDictation`/`cancelDictation` 递增世代以接管。
- **`guardStart` 未改动**：它被录音/realtime 两个入口共用，为 dictation 改它的语义会波及其它两条链路，故单列一道门。

### P2 `clientMessageId` 被 IPC schema 剥掉

- 链路三缺一：renderer 填、preload 原样透传（对**请求**不做校验）、adapter 一直在读 `input.clientMessageId`，唯独 Main 的 `chatSendSchema` 没声明 ⇒ zod 默认 strip。
- 修法：`chatSendSchema` 补 `clientMessageId: z.string().min(1).optional()`。**取可选而非必填**：schema 的职责是「不吞掉调用方发来的字段」，不是新增一道必填门（renderer 两条发送路径都恒填）。补**经 IPC 跳**的断言（既有 `real-backend.spec.ts` 直调 adapter，故对这条缺陷零判别力）。

**唯一 GREEN（据实记录，不删也不假装被覆盖）**：P1-6 的「放弃时不停采集」（`abandonDictationStart` 里的 `ownedCapture?.stop()`）。它在本修法下**不可达**——唯一的接管来源 `stopDictation`/`cancelDictation` 自身已经停了采集。保留它是**纵深防御**（未来若出现第三种接管路径），因此没有会红的用例；在此明确标注为「无判别性覆盖」，以免下轮误以为它被守住了。

**自审中改掉的一处自身缺陷（如实记录）**：`abandonDictationStart` 初版在 `await capture?.stop()` 之后**无条件**写 `capture = null`。而调用方的 `finally` 会立刻复位 `dictationStartInFlight`，于是这次 await 期间完全可能已有新 start 接管 `capture`/`dictationClientRequestId`——无条件写就会把接管者刚建立的句柄清掉，**正是本缺陷的同型后果**。已改为「同步取句柄 + 每处写入按写入时刻的值再判定一次」（`if (capture === ownedCapture)` / `if (dictationClientRequestId === requestId)`）。教训：**owner 判据必须覆盖收尾函数自己**，不能只在被调用处加栅栏。

**P1-1 的判别力对照（本批最有价值的一次变异）**：移除 `setBeforeCloseFlush` 接线后，**新用例（真实 `BrowserWindow.close()` 路径）红，而既有用例（`app.quit()` 路径）仍绿**——这就地证明了报告「该用例对缺陷零判别力」的判断。新用例同时断言 `page.isClosed()`，确保「在 close 上 `preventDefault` 一次」不会把退出卡住。
