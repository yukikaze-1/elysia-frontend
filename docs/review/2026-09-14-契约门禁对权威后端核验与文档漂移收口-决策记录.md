# 契约门禁对权威后端核验与文档漂移收口 · 决策记录

**日期：** 2026-09-14
**范围：** `check:contract` 的核验口径与一次实测取证；doc 02 §19 帧型覆盖清单；`check-backend-contract.mjs` 注释更正。**本批不含产品代码改动。**
**证据：** 权威后端 X99 `fc57b16d`（提交标题 `docs(gates): 「第三种假绿」写进约定 + .PHONY 补 secret 门禁 + 旧用例改名指针`）；实测命令与读数见 §2。

## 1. 背景：一条"长期未核实"与一处"没有门禁守着的缝"

doc 16 §3.1 的 `check:contract` 行长期写作"**未重跑／NOT VERIFIED**"（本机无后端仓库挂载），并注明"该状态不得读作通过"。这条本身是诚实的，但它意味着：**跨仓契约这条门禁的真实判别力，在本机侧一直没有被当场验证过**。

与之相邻还有一处结构性缺口：`check:contract` 比的是**代码 ↔ 后端**。而 CLAUDE.md 把 doc 02 定为"后端协议与前端领域契约"的维护文档——**"文档 ↔ 代码/后端"这一段没有任何门禁**。两者叠加的后果在本次核验里立刻显形（§3）。

## 2. 实测：对权威后端已 PASS

**口径：** 后端权威副本在 X99（本机不是权威，见 §3）。按既有取证先例，把契约文件取回到**临时目录**后本地核验，仓库零改动、跑完清理。

```bash
# 1) 取回权威契约与真实轨迹（临时目录，不入库）
scp -q yomu@192.168.1.18:/home/yomu/elysia-agent/frontend_contract/*            "$TMP/"
scp -q yomu@192.168.1.18:/home/yomu/elysia-agent/docs/archive/frontend-handoff-v2/traces/ws-v2-*.jsonl "$TMP/"

# 2) 指定来源后核验
CYRENE_FRONTEND_CONTRACT_DIR="$TMP" CYRENE_FRONTEND_CONTRACT_TRACES="$TMP" pnpm -F @cyrene/desktop check:contract
```

**读数（exit 0）：**

| 段 | 结果 |
|---|---|
| WS v2 帧 type 覆盖 | **36/36 型**；后端多出 6 型有意滞后（warn） |
| 字段级帧深度比对 | 12 个契约文件 / **88 条帧**解析后与输入逐字段相等（另 2 条来自合成探针，合计 90） |
| REST 段 | **16/16 模型**（字段名/必填性 + role 枚举子集） |

⇒ **`check:contract` 对权威后端不是"未核实"，而是可复现的 PASS**。doc 16 §3.1 该行据此更新。

**一处必须同时说明的边界（读数可信的前提）：** 上面那三个漂亮数字（`36/36`、`88 条`、`16/16`）**只在 `traces/` 齐备时才成立**。缺 `ws-v2-*.jsonl` 时脚本会自行降级为"仅合成探针"，**但汇总行的前两个数字形态几乎不变**（见 §3），只有 exit code 与最后一行能区分。

## 3. 本批最重要的产出：一次"假绿"被自己的纪律拦下

核验前我先图省事，把 `CYRENE_FRONTEND_CONTRACT_DIR` 指向了**本机** `~/Desktop/elysia-agent/frontend_contract`，得到：

```
[check-contract] WS v2 type 覆盖: 36/36 通过;字段级帧 2 条完整保留(0 条来自后端契约文件);未纳帧 6 个有意滞后(warn)
[check-contract] REST 段 16/16 模型通过
→ exit 2
```

**三处事实让这个读数不可用：**

1. **本机克隆是过时的**：`5669ed32`（2026-09-11），而权威副本是 `fc57b16d`（2026-09-14）。
2. **本机那份不完整**：根本没有 `contract.schema.json`，也没有 `traces/ws-v2-*.jsonl` ⇒ 字段级深比对**降级成合成探针**（`2 条完整保留（0 条来自后端契约文件）`）。
3. **它长得像通过**：`36/36` 与 `16/16` 两行与真通过时**逐字相同**，只有藏在中间的那句"(0 条来自后端契约文件)"和 exit 2 能揭示真相。

**这是本仓库"第三种假绿"的一个新实例**——不是"没跑就报绿"，也不是"门禁被绕过"，而是**跑了一个来源不对的输入、拿到一个形态正确的结果**。它比 `NOT VERIFIED` 危险：后者不会骗人。

**已采纳的纪律（用户 2026-09-14 明确要求）：**

- **本机后端克隆一律不得作为契约核验的权威来源。** 它没有自动保鲜机制，且可能只是部分副本；`CYRENE_FRONTEND_CONTRACT_DIR` 这个"看起来很自然"的赋值路径，就是下一个拿到假绿的入口。
- 权威来源只有：X99 上的 `~/elysia-agent`（经 SSH），或后端交接包。
- **读数必须连同 exit code 与最后一行一起看**，不能只看汇总的数字行。

**未做（属环境决定，不在本批范围）：** 没有给该脚本加"来源可疑即拒"的守卫（例如要求 `contract.schema.json` 与 `traces/` 同时在场，否则直接 `NOT VERIFIED`）。那会改变门禁语义与 CI 行为，应单独决策。

**未做（本机环境）：** 没有同步或修复本机那份后端克隆。它不在本仓库内，且"本机是否需要一份后端仓库"是使用者的选择；本批只确立"**它不是权威**"这条口径。

### 4.2 测出来的名单（此前只有数量、没有名字）

后端 `ServerMessage` 判别联合实测 **42 型**：

- **36 型**在前端白名单内 ⇒ 门禁核对面（`36/36`）；
- **6 型后端有、前端有意滞后**（只 warn）：`capabilities`、`command`、**`live2d.directive`**、`service_mode_result`、`transcription`、`wake`；
- 前端白名单 **37 条**里有 **1 条**（`character.catalog.changed`）**不在** `ServerMessage` 里 ⇒ 前端预埋。门禁只做子集判定，故**不会**因"前端多认"报错；
- 另有三型不在 `ServerMessage` 联合内但**被前端接纳**，因而先前完全没被记录：`typing`（兼容帧）、`character.state.changed`、`character.catalog.changed`。

**这三型正是"文档 ↔ 代码"这段缝里长出来的漂移**：`git show HEAD:docs/02-*.md` 全文检索，`typing` / `character.state.changed` / `character.catalog.changed` **各 0 命中**，而代码早已接纳它们（前两型在 `WS_V2_FRAME_TYPES` 白名单与 `raw-schemas.ts` 内）。doc 16 §3.1 也记过：多角色 FE-A 引入 `character.*` 帧时，**"后端尚未实现，入白名单后两侧任一就绪即可对拍"**——即这是有意的预埋，但**从未回写到 doc 02**。

### 4.3 被更正的过期主张（"前端超集帧"）

doc 02 §19.1 的「数据来源与记录」注记原写：

> `live2d.directive` 为**前端超集帧**（后端 `frontend_contract` 当前未含该帧类型，`check:contract` WS 28/28 通过不触发报错）

**两句都已被实测推翻，且错在两个不同层面：**

1. **事实层错**：该帧**已在后端 `ServerMessage` 内**（属那 6 型之一，2026-09-14 实测）。原句依据的是过期读数。
2. **论证层错（更重要）**：它拿"`check:contract` 通过"去论证"后端未含某帧"。**该门禁是子集判定，结构上不可能发现"后端新增、前端未认"的帧** ⇒ 这类"通过"对该命题**零信息量**。即便事实层没变，这个论证也是无效的。

⇒ 已在 doc 02 就地更正，并写明"所引 28/28 是批次 7 时点的数字"。
