## 1. 起因

用户要一份能「读一遍就了解这个项目架构」的文档。核查后发现三种近似物**都不能直接当它用**：

| 近似物 | 实际性质 | 为什么不能直接当「总架构」 |
|---|---|---|
| `docs/01-…总体架构设计-v0.2.md` | **设计口径**。元数据自陈「文档状态：参考（阶段 1～7 架构设计基线）」「现行行为以代码为准」 | 是设计基线而非现状：§6.2 的 `DesktopApi` 上有就地更正，原文即「**照它实现会走错**」（11 个方法在 `src` 0 命中）；§10 的 markdown 缓存挂接点已被取代（F-8）；§5 的推荐目录与现状不符（无 `renderer/features/`、无 `tests/e2e/`、`main/permissions/` 只剩占位 README） |
| `docs/review/2026-09-15-项目架构与进度总览.md` | **一次性快照**，首行即「不是状态源」，锚在 `037cc18`，且按仓规不可就地改数 | 体例最接近，但数字已漂（快照 108/188/255+39 vs 实测 112/190/266+45），且它是「快照」性质，下次还得再出一份 |
| `docs/review/2026-09-16-全仓工程级代码与架构审计报告.md` | **问题目录 + 分级裁决**（P0 0 / P1 6 / P2 ~60 / P3 ~70），含 `Architecture Assessment` 模块评级表 | 评级表有价值，但主体是待处置清单，不是结构说明；且其结论句会被后续批次修掉（见 §6） |

同时确认「权威分散」在本仓是**刻意设计**而非疏漏：CLAUDE.md 明写「There is no single global priority for every kind of question」，doc 00 §7 给的是冲突处理表（状态→doc 16、契约→doc 02、门槛→doc 12、运行行为→代码）。

## 2. 决策

**新增 [doc 20 前端架构现状总览](../20-Cyrene-前端架构现状总览.md)**，元数据为**维护中**，权威范围限定为：

分工（两份互不替代，冲突时以代码为准）：

| 维度 | doc 01 | doc 20（本文档） |
|---|---|---|
| 口径 | 设计（应当是什么样） | 现状（代码现在是什么样） |
| 状态 | 参考 | 维护中 |
| 是否随行为更新 | 只在设计变更时更新，历史主张不追改 | 结构变化时必须同步 |

## 4. doc 20 的写法纪律（针对本仓已发生过的事故类型）

1. **只写结构，不写状态**：任何阶段、阻塞项、读数、下一步都指向 doc 16。
2. **每条结论给落点文件**：便于读者自行复核；本仓出现过「文档声称某行为存在、代码里是死代码」（`fileRef` 的「重连即清空」）的事故。
3. **不转述 review／审计记录的结论句**：只认代码（理由与实例见 §6）。
4. **计数附复核命令，并声明不逐次追平**：数字只随结构性变化更新；`IpcChannels` 的数字**不被门禁钉住**（门禁保证的是三面集合相等），这一点在文档里明写了。
5. **不复制反面的「未修项」清单**：那是 doc 16 §5 与 review 记录的职责。

## 7. 代价与残余风险

1. **多了一份要维护的文档**——这是本仓最容易被诟病的失败模式（「写下了意图，但没变成代码或测试」）。缓解：只写结构不写状态（结构变化频率远低于状态）、结论附落点、计数不追平。
2. **数字漂移没有门禁**：文件计数与通道数不会被任何 spec 拦住，只能靠维护规则与复核命令。**已知边界，未做自动化。**
3. **两份文档（01／20）并存可能被误引**：已在两份文档的顶部互相说明分工；doc 01 未改动，故其历史更正仍按原样可读。
