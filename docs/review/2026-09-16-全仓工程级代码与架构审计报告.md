# Executive Summary

## 项目总体健康度

**骨架健康、局部有真实缺陷、门禁判别力弱于其宣称。**

这是一个明显高于同阶段平均水准的 Electron 代码库：进程边界、IPC 契约、路径 containment、凭据处理、工具权限链、Live2D 降级、诊断脱敏等**安全与结构性基线扎实**（见 §Security Assessment 的正面清单，多数条目经两轮独立复核）。first-party 代码 605 文件中 `any`/`@ts-ignore`/`@ts-expect-error`/`eslint-disable`/空 `catch`/裸 `JSON.parse` **全部为 0**；22 个 Pinia store 无环、无 `store → 组件` 反向依赖、无跨 store 直写；`shared/` 零 Electron/Vue/Node 依赖；vendored Live2D framework 与上游 SDK **59/59 文件逐字节相同**。

问题集中在三类：

1. **文档与台账断言了不存在的行为**（`clientMessageId` 上行、沙盒目录层、强制确认、退出前 flush、"集成套件覆盖主路径"）。这类问题在本仓历史上已反复造成"以为已修"的误判，本报告把它们与代码缺陷**同等对待**。
2. **生命周期出口缺失**：真实退出路径上的 flush 恒为空转、崩溃 reload 无风暴抑制、`did-fail-load`/`unresponsive` 无处理点、工具执行超时不取消 `await`。
3. **"绿灯的含义"被高估**：42 个 Electron 集成用例全部观测 mock 装配，而打包产物恒为 real 且 `CYRENE_BACKEND` 在测试 harness 中不可覆盖；`expect.assertions()` 全仓 0 命中（存在"零断言也通过"的实例）；若干关键判断（mock/real 等价、契约镜像、通道预算执行点）由"名单核对"承担。

## 是否发现 P0

**没有 P0。** 15 路审计 + 6 路对抗复核后，没有任何**当前可达**的 RCE、凭据泄漏、权限绕过或不可恢复数据损坏路径。特别地，G 路穷举了所有可到达 `executor.execute` 的调用点，结论是**不存在绕过 Permission 层执行 Desktop Runtime 能力的路径**（唯一执行点在 `tool-service.ts:435`，`run()` 的三个调用点全部有同步前置状态校验且中间无 await 间隙；Renderer 可达的工具通道只有 5 个非执行操作，schema 为 `.strict()` 且仅收 `{callId, decision}`）。

## 最值得优先处理的 5 个问题

1. **`[P1]` 退出前持久化 flush 在真实退出路径上恒为空转**（`main/index.ts:552-560` + `main/windows/main-window.ts:121`）。Windows/Linux 关闭最后一个窗口时 `closed → mainWindow=null` 严格早于 `before-quit`，`deliver()` 立即返回 `false`，草稿（800ms）/设置（500ms）/布局（200ms）/角色草稿（800ms）防抖写全部静默丢失；而集成用例走的是 `app.quit()` 的反时序，**对缺陷零判别力**。这是"用户输入丢失 + 门禁假绿 + 文档双重宣称已修"的三合一。**已用同版本 Electron 43.3.0 最小实验证实事件顺序**（见 Finding 1）。
2. **`[P1]` 看门狗对工具事件完全失明 ⇒ 等待人工授权或长时工具会误杀正常生成**（`renderer/src/bootstrap.ts:264-274` + `stores/message.store.ts:686-687`）。50s 静默窗口内若只有工具/授权事件，`GENERATION_STALLED` 会把正在进行的回复置为 `interrupted` 并清空本地 accumulator，**其后到达的正文与终态帧被永久丢弃**。修正：该路径的 wire `tool.request` **不带 `generationId`**，"转发 touch" 的直觉修法是无效的，正解是权限窗存续期暂停/延长窗口（`waitingForApproval` 信号已存在但未接线）。
3. **`[P1]` 无客户端 WS 存活检测（零心跳）**：half-open 连接不可发现，界面长期停在 `connected` 假态，发送被静默吞掉后报成 `TIMEOUT`，且无自动恢复路径（`real-backend.ts` 全文件无 ping/keepalive，仅有被动的 autoPong）。违反 `docs/07:155` 的明文要求，且零测试覆盖。
4. **`[P1]` 集成套件 100% 观测 mock 装配，且注入不可覆盖**（`tests/integration/helpers/app.ts:143-154` 把 `CYRENE_BACKEND: 'mock'` 写在 `opts.env` 之后）。打包产物恒为 real（`config/backend-mode.ts:8`）⇒ **主目标平台（Windows）的 real 装配在 Electron 层零端到端覆盖**。"集成全绿"这一信号的含义被系统性高估。
5. **`[P1]` 设置向导卸载后异步续体仍写共享 store**（`components/CyProfileWizard.vue:104-132`；提交中的"取消"按钮 `:215` 未禁用）。用户明示取消后仍会远端落库并**切换全局激活模型服务**，且 `cancelEdit` 不清 `testResult`、pane 重挂载的 `load()` 还会把错误横幅抹掉——属"取消按钮不取消"。

（第 6 条 P1：语音 dictation 的 `stopDictation` 因竞态被污染会话标识后可致**麦克风持续采集且无停止入口**；触发窗口 ms～百 ms，但后果不可自愈，见 Finding 6。另有 `clientMessageId` 上行被 IPC schema 静默剥掉一条——严重度 P2，但修复成本 1 行且直接推翻两份维护文档的"已做"记载，建议与上述 5 条同批处理。）

## 当前架构最强的地方

- **进程边界与 IPC 收口**：89 个 channel 三面对齐 89/89/89、零重复、零孤儿；88/89 走 `createIpcHandler` 双向 zod；统一 sender 校验（`webContents` + `mainFrame` + 受信 URL 三重）；arity 强制；generated 通道名常量零散落。
- **安全基线**：四项 webPreferences 齐全（`sandbox/contextIsolation/nodeIntegration:false/webSecurity`）、生产 CSP 无 `unsafe-*`、`cyrene://` 为 `standard+secure+supportFetchAPI` 且 `bypassCSP=false/corsEnabled=false`、路径 containment 对编码/反斜杠/UNC/ADS/symlink 逐条 fail-closed、凭据 `safeStorage` + origin 双绑且不可读回、生产代码零 `child_process`/`eval`、Fuses 三项关闭。
- **工具权限链**：单一执行闸口、黑名单压过 grant 与豁免、风险单调不降、`callId` 幂等、终态单向、原始参数不进 Renderer、审计与脱敏齐备。
- **流式领域模型**：一次生成 = 一条 assistant 消息 + 有序 `assistantSegments`（唯一创建点 `message.store.ts:739`），`generation.completed` 才是父终态，segment 完成不产生新父消息；inner voice / public reply 归属正确；`StreamAccumulator` 的序号连续性、权威 content 覆盖、缺口 `completing` 语义清晰且有单测。
- **工程纪律**：类型检查严格、零 `any` 家族、注释记录**为什么**而非**是什么**（代价见 P2"注释即历史"一条）、变更普遍带变异验证记录。

## 当前架构最大的技术风险

**"已修"的可信度来自文档而不是会红的断言。** 本仓历史上已两次记录同型事故（2026-09-10 门禁整改、2026-09-15 §2.1"我写下了意图，但没有把它变成代码"），本次审计再次命中同型 4 例：`clientMessageId`（doc 16/doc 18 记已做，实际被 IPC schema 剥掉）、沙盒目录层（doc 04 记唯一入口，实际零调用点）、退出 flush（doc 16 记 H-04 已修，实际生产路径恒不生效）、Linux GPU 回退（doc 16 把测试侧修复记成"已修复"）。**这四项都不是"写错代码"，而是"能力没有断言兜住"**——它同时污染技术判断与排期决策，因此本报告把它们列为与功能缺陷同级的处置对象。

## P1 — High

### [P1] 退出前持久化 flush 在真实退出路径上恒为空转（H-04 在生产从未生效）

#### Location
- file: `apps/desktop/src/main/index.ts`
- lines/function: `:552-560`（`createPersistFlushRequester` 装配）、`:562-576`（`before-quit` shutdown 步骤，第一步即 `renderer-persist`）、`:606-608`（`window-all-closed → app.quit()`）
- related files: `apps/desktop/src/main/windows/main-window.ts:121`（`win.on('closed', … setMainWindow(null))`）、`apps/desktop/src/main/persistence/persist-flush.ts`、`apps/desktop/src/renderer/src/bootstrap.ts:280-285`（ack 回执）、`apps/desktop/tests/integration/persist-flush.spec.ts:67,89`

#### Evidence
Windows/Linux 上用户退出应用的**唯一**路径是关闭最后一个窗口。该路径的事件顺序经**同版本 Electron 43.3.0 最小实验**实测为：

```
win:close → win:closed（此时 windows=0、isDestroyed=true）
          → window-all-closed        （index.ts:606 → app.quit()）
          → before-quit              （此时 windows=0）
```

即 `main-window.ts:121` 的 `setMainWindow(null)` 严格早于 `before-quit`；而 flush 的唯一投递点是：

```ts
// index.ts:552-560
deliver: () => {
  const win = getMainWindow()
  if (!win || win.isDestroyed()) return false   // ← 该路径恒真
  win.webContents.send(PushChannels.persistFlushRequest); return true
}
```

`deliver()` 返回 `false` 时 requester 立即 resolve（fail-open），shutdown 流程继续。**关键补充证据**：renderer 侧全仓**没有** `beforeunload`/`pagehide`/`unload` 落盘路径（直接 grep 0 命中），因此窗口销毁时不存在任何补偿通道。

对照实验（同一最小工程）：`app.quit()` 路径下 `before-quit` 时 `windows=1` 且 `webContents` 存活 —— 这正是集成用例走的那条路：`tests/integration/helpers/app.ts:207` 的 `launched.app.close()` → Playwright `ElectronApplication.close()` → `coreBundle.js:43906-43912` 的 `app.quit()`。**故该用例对缺陷零判别力。**

#### Problem
H-04（"退出前请求 Renderer flush 防抖持久化"）在文档与台账中被记为已修复，实际在 Windows/Linux 生产路径上从未生效一次。这不是"偶发失败"，而是**判据与触发点被放在同一条事件链的错误两端**：flush 必须在 renderer 还活着时请求，而它被挂在窗口已销毁之后。

#### Trigger
用户在任何一次防抖窗口内输入后关闭窗口。丢失上界：草稿 800ms、设置 500ms、布局 200ms、角色草稿 800ms；四个防抖均为**尾沿且无 maxWait**，连续输入时无上界（理论上可丢整段未落盘的编辑）。

#### Impact
用户可见的输入/设置静默丢失；且因文档与 CI 同时背书，问题不会被发现（本仓真实数据丢失类的最高优先级项）。

#### Root Cause
判据放在 `before-quit`（应用级、晚）而状态在 renderer（窗口级、早）；缺少"窗口 close 前拦一次"的机制（`win.on('close')` + `preventDefault` + flush 完成后再 destroy，或 renderer 侧 `beforeunload` 同步落盘）。

#### Recommended Fix
二选一（推荐 ①）：
① 在 `main-window.ts` 的 `win.on('close')` 上做一次性拦截：首次触发时 `event.preventDefault()`，请求 flush 并 await ack（带 ~1s 预算），完成后置位"已 flush"标记再 `win.destroy()`；`before-quit` 路径保留现状作为第二条通道（幂等）。
② 在 renderer 注册 `beforeunload`，用 `ipcRenderer.sendSync`（或 preload 提供的同步落盘原语）把防抖 state 直接交给 Main；代价是引入同步 IPC。

#### Verification
- integration（**判别性关键**）：现有 `persist-flush.spec.ts` 改用真实关窗路径（`app.evaluate(({ BrowserWindow }) => BrowserWindow.getAllWindows()[0].close())`），断言关窗后 `settings.json` / `drafts-v1.json` 已含改动。**当前该用例会红**——这就是它的价值。
- unit：`createPersistFlushRequester` 增加"`deliver()` 返回 false 时不得静默 resolve"的语义断言（或显式记录 `persist-flush:no-window` 诊断）。
- manual：`pnpm dev` 中输入文字后立刻点窗口 ✕，重启验证草稿是否恢复。

#### Confidence
**High**（事件顺序已用同版本 Electron 实验证实；Playwright 调用链已在 `node_modules` 内定位）。

需要 ms～百 ms 的竞态窗口（用户/自动化在 pending 置位前重复触发 start-dictation）。概率不高，但后果不可自愈，且修复面很小。

#### Impact
隐私相关的持续采集（用户以为已停止）+ 后端资源泄漏；符合 P1"严重 race"定义。

#### Root Cause
失败分支缺少 owner 判据（与 `R24` 同族：语音三入口无 in-flight 门）。本仓已有正确范式（`voice.reset()` 幂等收敛、`upsertRecord` 的终态单向守卫）。

#### Recommended Fix
给 dictation 的 start/stop 加 owner（每次 start 生成 `requestId`，成功写入的标识只能由**持有该 requestId** 的路径清理）；或按 `R24` 的建议为三个入口补 in-flight 门（第二次 start 在 pending 期间直接拒绝且**不做任何清理**）。

#### Verification
- unit（确定性，无需真实计时）：注入"延迟 resolve 的 fake capture + 第二次 `voiceStartDictation` 被 reject"，断言 `stopDictation()` 后 `fake.stopped === true` 且停帧已发出。
- integration：`electron-voice.spec.ts` 增加"连点两次开始听写 → 停止 → 断言麦克风轨已停止"。

#### Confidence
**Medium-High**（机制由对抗复核重建并给出确定性单测方案；原始行号引用有误，已在报告中更正）。

# Systemic Issues（跨模块根因）

跨 15 路审计与 6 路复核，反复出现的**根因**（而非单点 bug）如下，按影响排序：

### S-1「能力没有断言兜住」——文档/台账描述的行为从未变成代码或测试
本仓历史上已两次记录同型事故（2026-09-10 门禁整改；2026-09-15 §2.1"我写下了意图，但没有把它变成代码"），本次审计再次命中 **4 例**：

| 能力 | 声称处 | 代码现实 | 本条对应 Finding |
|---|---|---|---|
| `clientMessageId` 上行 | `docs/16:863`、`docs/18:782`「已做/已上行」 | IPC schema 无该字段，被 zod 静默剥掉 | P2 |
| 沙盒目录层是"唯一入口" | `docs/04:332-335`、`src/main/permissions/README.md:3` | `isPathWithinSandbox` 生产零调用、形参是死参数 | P2 |
| 退出前 flush Renderer 防抖态（H-04） | `docs/16`、`docs/review/2026-09-11-…` | 真实退出路径恒 `deliver()=false` | **P1** |
| Linux GPU 回退 | `docs/16:55-58`"已修复" | 修复只在测试脚手架与 `verify-artifact` | P2 |

**根因**：本仓的"修复"常常落在**位置**上（测试、同层、文档）而非**缺陷位置**（生产路径、跨层、代码），且缺少"这条断言在实现坏掉时会红吗"的评审项。
**建议**：把"新增/修改的能力必须有一条会红的断言"写成门禁清单项；对无法自动化的能力（如真实后端交互）显式登记为"未取证"而不是"已修"。

### S-2 失败分支按"我这次失败"清理**共享单例态**，缺 owner/世代判据
实例：dictation 会话标识竞态（P1）、realtime 变体（P3）、`R24`（语音三入口无 in-flight 门）、`R25`/`stopRecord`（P3）、附件贴图队列失败后无条件清空（P2）。正确范式在本仓**已存在**（`voice.reset()` 的幂等收敛、`upsertRecord` 的终态单向守卫、`message.store` 的 `contextOwner`），属**范式未扩散**。

### S-3 收敛/订阅/落盘点建在错误的"主体"上
- 订阅建在 **await 之后**（`CyDiagnosticsPane.vue:59`、`tool.store.init()`）⇒ 在途卸载即永久驻留；
- 收敛点绑在**组件存活性**（语音采集绑 `CyChatInput`）⇒ 视图切换不收敛；
- 落盘点绑在**应用级事件**（flush 绑 `before-quit`）⇒ 窗口级状态早已消失（P1）；
- 校验点绑在**上下文而非事实**（取消/超时只改状态不中止副作用；`chat:cancel` 丢弃 `generationId`）。

### S-4「绿灯含义被高估」——门禁的判别力集中在最容易的那一层
- Electron 集成 100% mock 装配且注入不可覆盖（P1）；real 装配在 Electron 层零 E2E；
- `expect.assertions()`/`hasAssertions()` 全仓 **0/302**，存在"零断言也通过"的实例（`ipc-security.spec.ts:155-171` 在 Linux CI 恒跳过；该属性另有单测覆盖，故严重度 P3，但**机制**普遍存在）；
- 契约镜像、通道预算、store 图、窗口边界四类门禁均以"名单相等"而非"行为等价"为判据；
- `check:contract` 在 CI 恒 exit 2（warning，不变红）⇒ 跨仓契约核对事实上不阻断。

### S-5 Mock 与 production 分叉，且无等价性测试
`mock-backend` / `mock-character-backend` 与 real 在**装配路径**（工具请求交付）、**行为语义**（取消终态）、**默认值**（`responseId`、`mouthLevel`）上不同；302 个 spec 中"同文件同时出现两实现"命中 0。这条与 S-4 互为因果。

### S-6 同一事实多个承载，且**无单一写入点**
- 待发送队列：附件在 store（按会话分桶）、贴图在组件本地 ref（无会话维度）⇒ 同族契约只覆盖了一半；
- 连接身份判据两套独立实现（`message.store.ts:61-73` 与 `conversation.store.ts:79-86`）；
- 持久化故障两份（`draft.store` 与 `cache.store` 各持一份，属有意设计但 UI 需读两处）；
- Live2D"启用/可见"分散在 4 处（总开关/布局折叠/窗口可见/controller 上报）。

### S-7 注释承载历史而非不变量
本仓注释质量整体很高（解释了"为什么"），但其中夹带大量**过程叙事**（"此前…现已…"）。当代码再次变更时这些句子会变成错误信息，并已在本次审计中多次误导（沙盒分支、退出 flush、`fileRef.clear()`）。建议：不变量保留、过程叙事移入 `docs/review/` 决策记录。

2. **`ipc-security.spec.ts:155-171`**：`return { skipped: true }` + `console.log` 后 vitest 记 passed（Linux CI 恒走该支）⇒ "通过"与"未执行"在报告上不可区分。该安全属性另有单测覆盖，故降为 P3，但**模式**危险。
3. **`contract-mirror` 运行时用例**：6 个 `toBeDefined()`（实测 6 passed / 7ms），真正判别力在编译期类型断言；而 `pnpm test` 不含类型检查（CI 的 `check` job 才有）。
4. **mock 自身输出当 golden**：多处断言以 mock 的产出为期望值，生产漂移时断言方向相反。
5. **Live2D 损坏注入用例**：夹具在 `tmp/`（不入 git）⇒ CI 上恒不注入却记 passed。
6. **IPC 预算门禁**：只验证"声明存在 + 有说明文字"，不验证执行点存在（S4 实例即由此漏过）。

## 哪些场景最值得增加测试（按收益排序）

1. **判别性关窗 flush 用例**（把 `persist-flush` 改成真实 `BrowserWindow.close()`；**当前必红**）。
2. **工具/授权等待 > 静默窗口**的生成存活用例（须先做 P1 的修法）。
3. **half-open 连接**用例（真实 `WebSocketServer` 静默挂起 ⇒ 断言进入重连）。
4. **real 装配的 Electron 冒烟 2–3 条** + 让 `CYRENE_BACKEND` 可被调用方覆盖。
5. **mock/real 共享契约测试**（同一事件序列 ⇒ 同构领域事件）。
6. **arity-0 通道的返回值语义**（`{ok:true, data:undefined}` 跨 contextBridge；同时回答 NV-1）。
7. **`expect.assertions(n)` 清扫**：至少给"有条件跳过"的用例加断言计数，避免静默通过。
8. **时序敏感用例的稳定性**：`electron-live2d-settings` B6 在本机负载下会红（本次审计实测），建议要么提高采样预算、要么把像素判据改成"结构性 + 一次重试"，并记录 flake 率。

# Recommended Fix Order

按依赖关系排序。**每批都给出"为什么先做 / 涉及 Finding / 是否需 migration / 风险 / 验证方式"。**

### Batch 1 — 用户可见的丢失与误杀（先做，因为它们每天都在发生）

- **migration**：无。
- **风险**：flush 修法涉及窗口关闭流程，需保证"不阻塞退出"（预算 + 超时放行）。
- **验证**：Batch 4 的判别性用例；每条都要求一条**修复后必红、修复前必绿**的变异验证。

### Batch 2 — 终止"文档撒谎"（与 Batch 1 并行，成本极低）
- **范围**：`clientMessageId`（1 行 schema + 2 用例 + 2 处文档）、沙盒层死码（接线或改文档）、doc 16 的 H-04/Linux GPU 措辞、`permissions/README`、doc 02/03/06 的 Token 旧读数、doc 16 行号漂移。

- **migration**：无。

- **验证**：`pnpm docs:check`；对可断言的项（`clientMessageId`）加集成断言。
