## 1. ① `CharacterDraftStore`：H-11b 同族第三处（本轮先复核实测）

修前 `load()` 的 catch 里是 `await this.isolation.isolate(...).catch(() => {})` —— 正是 H-11b 明确否掉的「改名失败被吞」，而本 store 的写入路径**没有任何守卫**。于是这条静默销毁路径成立：

> 隔离失败（文件被 AV/备份代理锁住、只读目录、符号链接越根…）⇒ 原文件仍在磁盘上、内存被换成空仓库 ⇒ **下一次 `save`/`delete`/`deleteByCharacterId`/`retryPendingWrite` 把未能隔离的原文件覆写** ⇒ 用户自建角色的恢复草稿整份消失。

修法（与 `SessionStore`／`SettingsService` 同纪律）：置降级位 → **读写全拒** → 留痕计数（`character-drafts:degraded`）。**读也拒绝**是有意的：降级时 `list()` 返回空仓库是**谎报**——磁盘上明明有东西、只是读不出来；返回空会让 UI 显示"没有草稿"，用户以为丢了，或者更糟：以为可以继续编辑并保存。

- 日志纪律照旧：只含固定 code/文件名，**不含正文、绝对路径、底层 message**；完整 fs 原文只进本进程的 `getDegradedReason()`（不跨 IPC）。集成/单测都断言了这一点。
- `clear()` 也拒绝（unlink 会毁现场）。
- Renderer：目录页那条恢复失败横幅原本是**写死**的一句「本地草稿列表暂时不可用。可以继续浏览角色，稍后重试恢复。」——降级**不会自愈**，按它说的"稍后重试"只会一次次撞墙。现走 `errorMessage()` 单一来源（有码走映射表 →「本地保存已停用…」），"角色目录仍可继续浏览"的安抚语义改由横幅内固定补充行承担（对两类码都成立）。

**变异 2 次**：① 摘掉写守卫 → 降级用例红，且 `save()` 由 reject 变 **resolve**（说明"覆写"真的发生了；这也是我改掉第一版夹具的原因——见 §1.1）；② 隔离失败改回吞掉 → 降级用例红（`getDegradedReason()` 为 undefined）。

### 1.1 一处夹具自纠（值得记）

我第一版的"判别用例"是用 **safeRoot 不匹配**造降级的。变异验证时发现它是**假判别**：那种夹具下 `assertStorageRoot` 本来就会拦住写，"覆写"根本发生不了，红的只是错误码不同。改成**真实形态**——保留正确的 safeRoot、只注入 `isolate` 失败（文件被锁住/rename 失败），此时写入路径本身健康，判别力才成立（与 `session-store.spec.ts` 同款手法）。

## 2. ⑤ B3-a：`cache.store` 快照推送失败不再无声

`pushMessages` 的 `catch { /* 缓存缺落由后端调和兜底 */ }` 是**有意**的 best-effort（失败不影响发送/加载），但它让"消息快照没存住"对用户完全不可见——与草稿域不对称。现：**best-effort 语义不变**，失败记进本 store 的故障态，由**同一条全局横幅**聚合显示（`draft.store` 优先，它带 file/reason 投影；store 之间**没有**新增依赖边）。

转移规则抽到 `utils/persistence-failure.ts`（失败置位、成功只清"单次失败"、**不清不可自愈的降级**），两个 store 共用一份——此前只写在 `draft.store` 里。变异：catch 改回静默 → 3 条用例红。

## 3. ⑤ B3-b：设置域降级**启动即可见**

`settings:load` 在降级态改为**拒绝读取**（`loadSettingsForRenderer`，具名导出以便直测）。理由同 §1：返回默认值等于谎报——用户会以为设置被重置了，接着改一改、写一写，把未能隔离的原文件覆掉。Renderer 的 `settings.hydrate` 把失败记进 `saveError`，由设置页那条三态横幅显示（M-19 那批建的）。

**启动期不受影响**：`main/index.ts` 直接调 `settings.load()`，不经这条 handler，boot 仍 fail-open。
**测量口径的诚实说明**：这消除的是"要等到一次保存失败才可见"，不是"在聊天页就能看到"——设置失败只在设置中心可见。草稿域有全局横幅、设置域没有，这个不对称是**有意的**（设置的影响面限于设置页），已记入残余。

变异：读改回返回默认值 → 该用例红（`promise resolved … instead of rejecting`）。

**被既有用例抓到的契约变化**：`voice-handlers.spec` 的 settings 替身是手搓的 `{ load, save }`；handler 新增 `getLastError()` 依赖后该用例当场红（`settings:load` 变成 `UNKNOWN/内部错误`）。已按其真实契约补齐替身，并在该文件写明原因。

## 4. ② ④ `message-list-follow-bottom`：**在 CI 机器上复现，判定为"停住且不恢复"**

### 4.1 复现配方（本轮的最大产出，成本从"推一次 CI 等 6 分钟"降到"20 秒一轮"）

1. 本机 `ssh 192.168.1.18`（`yomu-X99`，24 核，runner 所在机；**免密可用**）；
2. 该机 `~/elysia-frontend` 是开发克隆（https remote 无凭据、不能 fetch）⇒ 从本机 `git push x99 <sha>:refs/heads/<tmp>` 推一个分支过去，再 `git worktree add`（共享对象库、不碰原工作树）；
3. 工具链用 runner 自带的：`PATH=<runner>/_work/_tool/node/22.23.0/x64/bin:<~/setup-pnpm/node_modules/.bin>:/usr/local/bin:/usr/bin:/bin`（**必须保留系统路径**，否则 pnpm 的 shim 会因为找不到 `sed`/`dirname`/`uname` 而失败）；
4. `pnpm install --frozen-lockfile`（store 已暖，2 秒）→ `ensure:electron` → `electron-vite build --mode test`；
5. `taskset -c 14-23 xvfb-run -a pnpm --filter @cyrene/desktop exec vitest run --config vitest.integration.config.mts message-list-follow-bottom`，跑 8 轮。

**结果：8 轮中 1 轮冻结**（`run4 exit=1 median=78px settledGap=3856px frozen=1`）。另两次"整分片"运行（单独跑、以及与 live2d job 并发跑）都是绿的——**"机器忙"不是充分条件**，触发点更随机。

### 4.2 冻结曲线（自诊断第一次真的用上）

```
top=    …,7706,7768,7860,7953,8139,8139,8139,8139,8139,8139,8139,8139
height= …,8294,8465,8526,8619,8712,8882,8975,9068,9161,11635,11867,12053
frozenAt=#18 top=8139 height=8882→12053（top 不再变化而内容继续增长）
settledGap=3856px
resample(+5000ms)=3856px top=8139 height=12568   ×3（三次都一样）
```

三个结论，逐条对应此前的开放疑问：

1. **`top` 完全冻结而 `height` 持续增长** ⇒ 命中的是组件里已记录的那条"**再无恢复路径**"分支（`CyMessageList.vue:112-125`：一旦早退，缺口更大、atBottom 更不可能为真 → 此后不再产生 scroll 事件 → 没有 settle → 没有重锚）；
2. **三次 5s 重采样都是 3856px 且 `top`/`height` 不再变化** ⇒ 流式结束后**它没有自愈**。这把"15s 观测窗内不收敛"推进为"**明确不收敛**"（仍受 15s 重采样窗口限制，但不再是"可能只是慢"）；
3. **数值与 CI `34740144774` 逐像素相同**（`median=78px max=3341px within=19/25 settledGap=3856px`）⇒ 那是同一个冻结，不是另一类现象。

### 4.3 下一步（已定位到分支，未定位到触发点）

冻结起点在流式开始后约 3.6s（第 18 个采样）。按代码，清掉"跟随意图"的唯一入口是 `onScroll` 里的 `scrollTop < prevTop`（用户上翻）分支——**而虚拟列表重锚自身就会写小 `el.scrollTop`**（`restoreScrollTop` 用的是估算高度）。故最可疑的是「重锚把 scrollTop 写小 → 触发 scroll 事件 → 被当成用户上翻 → 意图被清 → 再无恢复路径」。

**下一轮要做的**（本轮未做，属独立批次）：在渲染层加一个**只读探针**（`.cy-messages` 的 `data-follow-intent` / `data-at-bottom`，或测试模式下挂 `window.__cyFollowProbe`），用同一配方跑 8 轮直到复现，读出"意图被清的那一刻 `prevTop`/`scrollTop`/`scrollHeight` 各是多少"，据此判定是重锚写小还是别的路径。**判据一字不改**：修复必须让 ④ 在复现配方下稳定转绿，而不是调阈值。

## 4bis. ④ 第二轮：探针到位，**根因分支已确认**（2026-09-13 同日追加）

上一节把"是什么形态"钉住了（`top` 冻结、`height` 继续涨、15s 不恢复）；这一轮把"**是谁清的**"钉住了。

### 4bis.1 做法：只读探针 + 修正假阳性

- `CyMessageList.vue` 把两个内部布尔量反射到 DOM：`.cy-messages[data-follow-intent]`（`stickToBottom` 跟随意图）、
  `[data-at-bottom]`（瞬时贴底）。**只读**：不参与任何渲染决策、两个字符串属性、零行为改动。
  存在的理由正是这一节：这两个量此前只活在组件作用域里，测试只能看到几何量，判不出分支。
- 第一版冻结判定（"任意相邻两点 top 相同且 height 增长"）**当场被证伪**：X99 run2 命中了它，但那一轮
  `intent` 全程为 1、`atb` 只是正常闪动、用例**通过**——单点重复只是跟随恰好落回同一个取整值。
  现判据为"**末尾连续 ≥3 个采样 top 不变且 height 仍增长**"，并把两个布尔量一起打出来。

### 4bis.2 复现与读数（X99，`taskset -c 14-23`，第 5 轮命中）

```
median=2506px max=5104px within=2/25        settledGap=5526px
top=   5593,6469,6469,6469,6469,…（连续 23 个采样不变）
height=6729,7042,7212,7305,…→12146（持续增长）
intent=1100000000000000000000000            ← 第 3 个采样起变 0
atb=   1100000000000000000000000            ← 同步变 0
冻结时 intent=0 atb=0（前一点 intent=1 atb=1）
resample(+5s)×3 = 5526px，top/height/intent 全不变 ⇒ 永不恢复
```

**结论（分支确定）**：清掉意图的正是 `onScroll` 里那条 `else if (el.scrollTop < prevTop) stickToBottom = false`。
而按几何量反推，那一刻**距底只比 `BOTTOM_EPS=40` 大几像素**（`height=7212`、`top=6469`、视口约 700）——
即**一次约 40–50px 的瞬时下移**（布局修正把 scrollTop 夹小/锚点重算写小）就足以把"跟随"判成"用户上翻"，
并且此后**永不恢复**（意图没了 ⇒ 不再贴底 ⇒ 缺口单调增到 5526px）。

### 4bis.3 为什么**没有**当场改（以及下一轮该怎么做）

代码本身记着这条张力：注释写"我曾加过一条『且最大可滚动量未增长才算用户上翻』的判别……**被既有测试反驳**"。
也就是说"防误清"这件事**试过一次并失败**，而流式期间 maxScroll **一直在增长**，那条判据等于永远不生效——
它防不住误清，却会让真正的用户上翻被忽略（列表把用户拽回底部）。

下一轮应走的判别方向（按可行性排序，**都需先在 X99 配方上验证，判据不许动**）：
- **按幅度而非按"是否增长"**：只有下移量**显著**（如 ≥ 一屏的一部分）才算用户上翻；几十像素的抖动不足以放弃跟随。
  需先跑既有 H-02 用例确认不回归（它们里有"上翻后必须停止跟随"的场景，属**有意**的非贴底定位）。
- **区分"我们写的"与"用户滚的"**：所有程序性 `el.scrollTop = X` 处做标记（`restoreScrollTop`／`commitScrollHeights`／`goBottom`），
  下一次 scroll 事件若落在该写入的夹小结果上则不改意图。风险是滚动条拖拽不产生输入事件，需与上一条合用。
- **兜一条恢复路径**（与上面正交，且可能才是用户真正感知的那一半）：即便意图被清，也应有个"回到底部"的入口或
  自动恢复条件——当前形态是**意图一旦丢失就再无任何路径回来**（组件注释里那句"再无恢复路径"）。

**本轮不改的理由**：这是一处**试过一次、失败过一次**的滚动语义，改动面涉及流式/虚拟列表重锚/用户上翻三方博弈；
在只剩一轮预算的情况下仓促改它，风险高于收益。**证据（复现配方 + 探针 + 读数）已经足够让下一轮直接动手。**

## 4ter. ④ 第三轮：**修好了**（同日追加）

### 4ter.1 定数的读数（第二轮探针跑 16 轮，命中 2 次，两次读数**逐字节相同**）

```
d=31 acc=31 t=8139 max=8185 h=8758 c=573 w=own/+32ms
```

三个事实，每一个都改变了做法：

1. **下移量是 31px，不是上一轮反推的"40–50px"**。上一轮只拿到上界（"清掉之后 gap 刚越过
   `BOTTOM_EPS=40`"），下移量本身可以是 3px 也可以是 43px。**没有这个数就定不出任何阈值**——
   这正是第二轮加探针的理由，也是它唯一的产出。
2. **`w=own/+32ms`：这次下移紧跟在我们自己 32ms 前的一次程序性写入之后**，而且下移**前**的位置
   正是我们写入的那个值。即：**浏览器在我们贴底写入之后自己把位置回退了 31px**，
   `onScroll` 把它读成"用户上翻"。这不是用户行为，也不该由几何量去猜用户意图。
3. 两次命中读数**完全相同**（同一段内容、同一套几何）⇒ 这是**确定性**伪影，不是随机抖动，
   所以"多跑几轮看运气"永远只能看到它的一部分。

### 4ter.2 修法：清意图的判据从「任何下移」改成「**累计**下移 ≥ 64px」

`USER_SCROLL_MIN_PX = 64` **不是拍的，是上面那 31px 定的**：

- 实测误清 31px 被挡住；且**累计量每次贴底都清零**（内容一增长就重新贴底），连两次误清也凑不够；
- **必须配累计**：只按单次幅度判别的话，触控板的小步上滑（每次几像素到几十像素）永远清不掉意图，
  于是每次内容增长都会把正在阅读的用户拽回底部——那是比原缺陷更烦人的回归；
- 上界由既有 `perf-gate` ②b 的刺激性写入给出：`Math.max(0, scrollTop - (clientHeight - top + 120))`
  ⇒ 实测 ≥120px，该用例要求"上翻后必须停止跟随"，仍稳稳越过 64px。

**与那条"试过并被否掉"的加固的区别**：那条用几何条件（"最大可滚动量未增长才算用户上翻"），而流式期间
maxScroll 一直在增长 ⇒ 恒不生效、却会忽略真正的上翻（②b 红于 245 < 534）。本条只看**位移本身**，
不依赖任何"内容是否在增长"的假设。

**"回到底部"按钮确实存在**（`v-if="!atBottom"`）：冻结时 `atBottom=0`，故按钮可见、点击可重新表达跟随意图。
即缺陷形态是"**自动跟随静默失效、需用户自己发现并手点一下**"，不是"完全无路可走"——
这与 doc 16 §1 记的 H-02 场景（`atBottom` 仍为 true ⇒ 按钮根本不出现）是两回事，不要混。

### 4ter.3 确定性回归用例（不靠集成碰运气）

新增 `tests/unit/cy-message-list-follow-intent.spec.ts`（5 条）。happy-dom 不做布局，故三个几何量由用例
**直接给定**（`Object.defineProperty` 桩 `scrollTop`/`scrollHeight`/`clientHeight`），把"贴底写入后
浏览器回退 31px"变成可重复的输入；断言读的是组件反射到 DOM 的 `data-follow-intent`（与集成用例同一观测面）。
覆盖：31px 误清必须**不**清意图、≥64px 必须清、小步**累计**过门限必须清、回到底部清空累计、探针可用。

**变异验证**：把门限改成 1（等价于修复前的"任何下移即清"）⇒ 5 条里 **3 条红**（含那条 31px 判别用例），
另 2 条（≥64px 上翻、探针可用性）不依赖门限、保持绿——判别力落在该落的地方。

## 4quater. 顺带查实的一条**既有**缺陷：右键消息时菜单会被列表自身的滚动关掉（不属于本轮修复，也未修）

排查 ④ 的回归时在本机 Windows 全量集成里发现 `tests/integration/context-menu.spec.ts` 的 ④b 步骤稳定红，
逐项取证后确认**与本轮修复无关、且修复前就存在**：

- **取证**：把 `USER_SCROLL_MIN_PX` 临时改成 `0`（**等价于修复前的"任何下移即清意图"**）重建后，该用例
  **同样红**（连跑 2 次）⇒ 不是本轮引入的回归。
- **机制（探针读数，非推断）**：给组件临时加两个只读属性（`data-menu-opens` / `data-menu-open`）后复现：
  右键那一刻 `menuOpen=1`、`menu-opens` 计数 +1（**菜单确实开了**），400ms 后 `menuOpen=0`、菜单元素消失，
  同一窗口内 `.cy-messages` 的 `scrollHeight` 从 710 变 742，并捕获到**恰好一次 scroll 事件**。
  即：右键后列表发生一次布局/重锚调整并产生 scroll 事件，而 `CyContextMenu` 的
  `window.addEventListener('scroll', onViewportChange, true)`（**capture 相位、任何元素的滚动都算**）
  把这个刚打开的菜单立刻关掉了。
- **性质**：这是**产品行为层面**的既有交互缺陷（"右键时列表若正在自行调整滚动，菜单会一闪即没"），
  也是**本机 Windows 特有**的稳定失败——CI（Linux/X99）上同一提交是绿的。
- **本轮处置：只记录，不修**。理由：修法要在"滚动就关菜单"（防 fixed 菜单指向错对象）与"流式期间列表
  一直在动"之间重新定规则，属独立一批；本轮把它写进 doc 16 §5，避免它被当成"偶发 flake"重跑掉。
