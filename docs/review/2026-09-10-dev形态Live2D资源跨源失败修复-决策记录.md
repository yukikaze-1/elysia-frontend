# dev 形态 Live2D 模型加载失败（跨源供给）根因定位与修复（2026-09-10）

**记录日期：** 2026-09-10

**文档状态：** 生效中

**触发：** 用户重启前端后仍报「模型加载失败」。上一批交付的诊断态（`2026-09-10-Live2D失败态可诊断化-决策记录.md`）首次把真实原因显示出来，截图为：

```
模型加载失败
原因：Failed to fetch
已发现 3 个模型，其中可用 3 个
```

这三行**互相矛盾**（模型明明 3/3 可用，为何加载失败），正是本轮的入口。

**结论：** 不是模型问题、不是后端问题、不是 GPU 问题。是 **dev 形态下模型文件的供给通道跨源被 Chromium 拒绝**——一个自阶段 5 起就记录在案（F-后续-2）、但**从未修复**的已知限制。上一批交付的「失败态可诊断化」是本轮能定位它的直接原因。

---

## 1. 根因

`cyrene` scheme 在 `src/main/protocol/scheme.ts` 恒注册为 `corsEnabled: false`（阶段 5 D-4 安全结论：放开后非受信 origin 也能读 `cyrene://` 资源）。

而 Live2D 模型文件只在 `cyrene://renderer/__cyrene-live2d/{modelId}/{relPath}` 上供给（`adapter.ts` 的 `LIVE2D_BASE`）。`pnpm dev` 下页面由 Vite dev server 供给，origin 是 `http://localhost:<port>`——**与 `cyrene://` 跨源**。跨源 `fetch` 一个未注册为 CORS-enabled 的 scheme，Chromium 在 CORS 层直接拒绝，JS 侧只拿到原生 `TypeError: Failed to fetch`。

`handler.ts` 里那段 `withCors`（受信 origin 回补 `Access-Control-Allow-Origin` + `Vary`）**根本没机会生效**——CORS 层不看响应头，方案本身就没被启用。

**为什么清单显示 3/3 可用**：`live2d:list-models` 是 `ipcRenderer.invoke` 通道，不受同源策略约束；它纯本地读目录并校验完整性。所以「清单正常 + 文件取不到」是同一原因的两面，不是矛盾。

### 1.1 实测取证（真实 Electron + 真实 Vite dev server）

| 断言 | 实测 |
|---|---|
| 页面确为 dev 形态 | `href = http://127.0.0.1:4678/` |
| dev 页面跨源 fetch `cyrene://` | **`TypeError: Failed to fetch`** |
| 模型清单 IPC | `[{ id: 'wanko', available: true }]` |
| 带 dev 修复后端到端 | **`Live2D 就绪 · Wanko`** |

**变异验证**：把 `needsIpcResourceSupply()` 临时改为 `return false` 后重跑，探针复现用户现象——

```
statusText:  "Failed to fetch"
overlayText: "模型加载失败 原因：Failed to fetch 已发现 1 个模型，其中可用 1 个"
```

与用户截图逐字一致（用户为 3 个模型，探针 appData 只装了 wanko）。证明探针**能失败**，不是恒绿。

## 2. 为什么此前长期未被发现

四个因素叠加，缺一不可：

| # | 因素 | 说明 |
|---|---|---|
| 1 | **错误注释掩盖** | `dev-csp.ts` 的 `connect-src cyrene:` 注释写「Framework 经 `fetch(cyrene://…)` 取 shader 文本」。**与实现不符**：`SHADER_PATH = '/live2d/shaders/'` 是根相对路径，由 `src/renderer/public/` 同源供给。该注释让人以为「dev 下的 `cyrene://` fetch 是被设计支持的」 |
| 2 | **集成测试全是 prod 形态** | `tests/integration/helpers/app.ts:76` 无条件 `delete env['ELECTRON_RENDERER_URL']`——页面恒为 `cyrene://renderer`（同源），**dev 形态没有任何测试覆盖** |
| 3 | **已知限制被记录但未排期** | `2026-08-19-阶段5-Live2D真实联调验收.md` §F-后续-2：「dev 模式 Live2D 不可用……需专门设计（例如 dev 下改用同源代理或安全 CORS 方案）后修复」；`2026-08-27-阶段7批次C-真实联调验收.md` 环境注记亦记为「该安全决策的预期运行形态，不是回归」 |
| 4 | **失败信息此前被丢弃** | 修复前界面只有「模型加载失败」四个字，看不到 `Failed to fetch`，也看不到「3 个模型可用」（见上一批决策记录） |

### 2.1 我上一轮引入的文档回归（须记录）

修复前 doc 17 §4.1 原本**正确写着**这条 `corsEnabled:false` 限制。在 `2026-09-10-新用户上手路径审查与整改-决策记录.md` 中，我判它「是未经实测的强断言，且与 dev CSP 的显式放行相矛盾」而**删除**，改为一句「待实测确认」。

**判断是错的**：那条断言有 2026-08-19 / 2026-08-27 两次真机记录支撑；「与 dev CSP 矛盾」的表象恰恰源自因素 1 的错误注释——我用一个错误注释去否定了一条正确结论。

本轮已把 doc 17 §4.1 改写为实测结论，并在 README 同步。

## 3. 修法选择

| 方案 | 取舍 |
|---|---|
| A. dev 下放开 `corsEnabled: true` | **否决**。scheme 级全局开关，与阶段 5 D-4 安全结论直接冲突，且 2026-08-21 已回退过一次并补回断言（`tests/unit/protocol-scheme.spec.ts`） |
| B. dev 下起本地 HTTP 代理供给模型文件 | **否决**。在 Electron 进程边界之外新开一条读模型文件的路径，且需要复制路径解析（安全逻辑不可复制） |
| C. **dev 下经 IPC 供给字节**（采用） | 走既有 preload 信任边界（具名窄接口 + 双向 schema 校验）；门禁与协议通道**共用同一实现**；能力上不新增——打包形态下 Renderer 本就能同源 fetch 同一批字节 |

### 3.1 C 的关键约束：闸门只能有一份

两条供给通道若各写一遍「verifyIntegrity → registered/available → containment 白名单」，二者迟早分叉，**分叉的那一侧就是绕过入口**。故抽出 `src/main/live2d/serve-gate.ts`（electron-free），`protocol/handler.ts` 与 `ipc/live2d-handlers.ts` 共同调用。

顺带补上一个**此前完全没有覆盖**的断言：变经验证，把闸门里的 `verifyIntegrity` 与 `listInstalledModels` 顺序对调后，既有 `protocol-live2d.spec.ts` **19/19 仍全绿**——即 fail-closed 时序此前未被任何测试钉住。新增 `live2d-serve-gate.spec.ts` 补上。

## 4. 实现

| 文件 | 变更 |
|---|---|
| `src/main/live2d/serve-gate.ts` | **新增**。`gateLive2dFile`（判定）+ `gateHttpFailure`（状态码/文本映射），electron-free |
| `src/main/protocol/handler.ts` | 门禁判定改为调用 `gateLive2dFile`；闭包只剩 CORS 补头 + 读文件 + 状态码映射 |
| `src/main/ipc/live2d-handlers.ts` | 新增通道 `live2d:read-model-file`（arity 1）：闸门 → `readFile` → 字节 + mime |
| `src/shared/contracts/live2d.ts` | 新增 `Live2dModelFileResult`；**`LIVE2D_PATH_PREFIX` 上移为共享常量** |
| `src/main/protocol/live2d-path.ts` | 前缀改为从 shared 再导出（不再两处各写字面量靠注释对齐） |
| `src/renderer/src/live2d/dev-resource-fetch.ts` | **新增**。`needsIpcResourceSupply()` + `createDevLive2dFetch(reader)`：URL 形态不变，字节读取改走 IPC |
| `src/renderer/src/stores/live2d.store.ts` | `buildController()` 仅在需 IPC 供给时注入 `fetchImpl` |

**打包/preview 形态行为逐字节不变**：`needsIpcResourceSupply()` 要求 `MODE === 'development'` **且** 页面 origin 非 `cyrene:`，两者同时成立才走 IPC。判据取「是否与 `cyrene://` 同源」而非「是否 dev」——因为跨源才是真正的原因。

### 4.1 连带收紧：dev CSP 去掉 `connect-src cyrene:`

静态可证已无用途：渲染层全部 `fetch` 调用点只有三处——适配器（dev 已走 IPC）、`cubismshader_webgl.ts`（根相对路径，同源）、`media-url.ts`（构造 `<img>`/`<audio>` 的 `src`，走 `img-src`/`media-src` 的元素加载，不经 `connect-src`）。

dev 探针在收紧后仍 8/8 通过，其中「Live2D 就绪」本身就证明着色器同源加载正常（着色器若被 CSP 拦，模型不可能就绪）。

- **`CyLive2DPanel.vue:71` 的 `statusText` 仍直接渲染 `store.error`**（原生 `Failed to fetch` 会出现在面板底部状态行）。本轮未改：根因已修，且改动属展示层措辞收敛，与 `CyCharacterPublicState` 的去技术细节口径统一应单独处理。
