## 3. FE-S3-RUN-P0-01：相对签名 URL 必须基于 backend origin 解析

### 3.1 真实现象

使用已归档 WAV 附件 `att_a84070305526490c9d48510fb9` 复验：

1. 后端 `GET /api/attachments/{id}/sign` 返回 200；
2. 返回的 `url` 为契约规定的相对路径 `/api/attachments/{id}?sig=...&exp=...`；
3. Ubuntu 端直接将该路径拼到后端 origin 后，完整下载、过期重签和 Range/206 全部通过；
4. 真实 Electron 点击音频卡后 UI 变为“加载失败 / 重试”；
5. `window.desktopApi.attachmentsCheck(id)` 返回 `{ status: "error", reason: "probe_failed" }`。

完整签名和密钥未写入本文。

### 3.2 根因

`apps/desktop/src/main/attachments/media-service.ts` 已注入 `baseUrl()`，但附件分支没有使用它：

- `resolveSignedUrl()` 在 `:51-59` 直接缓存 `sign.url`；
- `proxyFetch()` 在 `:68-82` 直接 `fetchImpl(signedUrl)`；
- `checkStatus()` 在 `:145-161` 同样直接 `fetchImpl(signed.url)`；
- Node/Electron Main 的 `fetch` 不能解析没有 base 的相对 URL，因此抛异常并被映射为 502/`probe_failed`；
- sticker 分支 `:125-141` 已正确使用 `baseUrl()`，只有 attachment 分支漏接。

现有 `apps/desktop/tests/unit/media-service.spec.ts:9-18` 默认签名 fixture 始终返回 `https://cdn.x/...` 绝对地址，因而掩盖了真实契约。

### 3.3 必须修改的行为

1. 在 Main 受信边界内集中解析签名地址：相对 `sign.url` 使用当前配置的 backend base URL 转成绝对 URL；
2. `streamAttachment()` 与 `checkStatus()` 必须复用同一解析结果，不能一个修好、另一个继续 probe 失败；
3. backend base URL 缺失或签名 URL 非法时返回可诊断状态，不把语法错误伪装成附件不存在；
4. 只允许受支持的 HTTP(S) 后端 URL，并保持现有签名不进入 Renderer、日志脱敏和 `Sec-Fetch-Dest` 防护；
5. endpoint 切换/断开时清理旧 origin 下的签名缓存，避免把旧签名请求到新后端；
6. 不要求后端把相对 URL 改成写死 origin 的绝对 URL。SSH 转发、反代和远程部署都应由前端当前 endpoint 决定 origin。

### 3.4 必须补充的测试

- 签名返回 `/api/attachments/att_1?...`，base URL 为 `http://127.0.0.1:18765`：实际 fetch URL 正确拼接；
- 相对 URL 的普通流、Range/206、401/403 强制重签和 `checkStatus` 均通过；
- base URL 尾斜杠、有 path/无 path 的规范拼接不产生双斜杠或吞路径；
- endpoint 变化后不复用旧绝对地址缓存；
- 非 HTTP(S)、畸形 URL、base URL 缺失按安全策略拒绝；
- 保留绝对 URL 场景的明确兼容/拒绝策略测试，不能只测试绝对 CDN fixture。

### 3.5 完成验收

真实 Electron 点击 WAV、WebM audio、MP4 和 PNG 卡片，代理请求能抵达当前 SSH 转发 endpoint；Range 媒体可播放，重载后仍可重新签名并恢复。

## 4. FE-S3-RUN-P0-02：ContentPart 的 `null` 必须归一化为字段缺省

### 4.1 真实现象

有效 PNG 已成功上传、关联并持久化。后端 REST 消息 ContentPart 合法返回：

```json
{
  "type": "image",
  "width": null,
  "height": null
}
```

Main Mapper 生成的 `MessageAttachment` 仍带 `width: null`、`height: null`，随后 IPC 成功响应 Schema 拒绝整个消息页，实际错误包括：

```text
attachments.0.width expected number, received null
attachments.0.height expected number, received null
```

结果不是“该图片缺少尺寸”，而是包含它的整页 `getMessages` 失败，其他正常消息也无法恢复。

### 4.2 根因

- `apps/desktop/src/main/transport/protocol-v2/content-part.ts:20-29` 的 TS shape 只声明 `number | undefined`，没有反映 REST JSON 的 `null`；
- `toMedia()` 在 `:42-53` 用 `!== undefined` 判断，因此 `null` 被当作存在；
- `mapContentMedia()` 在 `:75-91` 再次用相同判断把 `null` 写入领域对象；
- `apps/desktop/src/shared/schemas/ipc-response.ts:49-52` 正确要求 optional number，于是在 IPC 边界拒绝整页。

### 4.3 必须修改的行为

1. REST/replay 边界把 `null` 视为“未知/缺省”，不要进入领域 `MessageAttachment` 或 `AssistantSegment`；
2. 至少统一处理 `width`、`height`；同时审计 `size_bytes`、`duration_ms` 等全部可空数字，使用 `typeof value === "number"`、有限值和必要的非负约束；
3. 保持 IPC Schema 严格，不能用 `z.number().nullable()` 把 wire 的可空性扩散到 Renderer 领域模型；
4. 单个可选元数据缺失不能丢弃媒体，更不能丢弃整个消息页；必填 `attachmentId/kind/mediaType` 的错误仍应 fail-closed。

### 4.4 必须补充的测试

- image `width:null,height:null` 映射成功且领域对象不含这两个字段；
- `undefined`、合法数字、0、负数、NaN/Infinity（单元注入）分别按约束处理；
- video/audio 的可空 `duration_ms` 和 file 的可空 size 不会污染 IPC；
- 一页同时包含普通文本、该 PNG 和其他附件时，IPC 整页返回成功；
- REST 首屏、`getMessageContext`、WS replay 三条恢复路径使用相同归一化语义。

### 4.5 完成验收

真实 Electron 切走再切回、来源跳转、Renderer reload 和后端重启恢复后，该 PNG 仍显示媒体卡；同页其他消息不丢失。

## 5. FE-S3-RUN-P0-03：持久化 StickerPart 必须恢复为 `Message.stickerId`

### 5.1 真实现象

- 真实发送贴图成功，乐观消息中的贴图立即可见；
- 后端原始归档内容正确，消息 `msg_8a159f39d0144dba927358712a` 含 `type=sticker`、稳定 `sticker_id/src`；
- 历史查看器 `category=sticker` 能搜到该消息，来源跳转也能定位；
- 一旦来源跳转重新加载上下文，或切会话/Renderer reload，贴图从消息气泡中消失。

### 5.2 根因

- 乐观发送在 `apps/desktop/src/renderer/src/stores/message.store.ts:210-246` 正确写入 `Message.stickerId`；
- `RestMapper.assemble()` 在 `apps/desktop/src/main/transport/protocol-v2/rest-mapper.ts:80-123` 只恢复文字和普通附件；
- `mapContentToEntries()` 在 `apps/desktop/src/main/transport/protocol-v2/content-part.ts:57-71` 明确忽略 `sticker`；
- 因此持久化消息经 REST 首屏、context 或 WS replay 进入 Store 时不再含 `stickerId`。

### 5.3 必须修改的行为

1. 贴图 wire/显示语义以前端已冻结的 `Message.stickerId` 为准；
2. 从 `StickerPart{type:"sticker", sticker_id, src}` 恢复稳定 `stickerId`，REST 与 WS replay 共用同一映射逻辑；
3. 校验 `st_` ID，Renderer 继续只使用受控 `cyrene://renderer/__cyrene-media/sticker/{id}` 代理，不直接信任任意 `src`；
4. “文字 + 贴图”和纯贴图都必须保留；贴图不能被错误塞入普通上传附件数组；
5. 同一消息的乐观对象迁移到服务端 ID 后，与 REST/replay 恢复对象字段一致，不能闪一下后消失。

### 5.4 必须补充的测试

- `RestMapper.toDomainMessage()` 映射纯贴图、文字 + 贴图；
- `toDomainMessageFromReplay()` 对同一 StickerPart 得到相同 `stickerId`；
- 来源 context 加载、会话首次历史、Renderer bootstrap replay 均恢复贴图；
- 非法 sticker ID/任意外部 src 不进入贴图代理；
- 乐观消息 ACK ID 迁移后再收到 REST/replay，不重复、不丢贴图；
- `category=sticker` 搜索命中后跳转，目标消息实际显示对应贴图。

### 5.5 完成验收

真实发送贴图后依次执行来源跳转、切换会话、Renderer reload、后端重启；同一消息始终显示同一贴图且没有重复。

## 6. FE-S3-RUN-P1-01：历史搜索分页必须从第一页起使用一致排序

### 6.1 真实现象

真实 IPC 分页结果：

- 第一页 50 条，第二页 50 条；
- 合计 100 个 `hitId` 全部唯一，页间 0 重叠；
- 说明后端 keyset cursor 和数据续接正确；
- 但首次查询和点击“加载更多”后的界面时间顺序相反，结果列表整体翻转。

### 6.2 根因

- 后端搜索契约按 `timestamp DESC, _id DESC` 返回每一页；
- `RealBackend.queryChatHistory()` 单流分支在 `apps/desktop/src/main/transport/real-backend.ts:665-672` 直接透传后端顺序；
- `historyViewerStore.submitQuery()` 在 `apps/desktop/src/renderer/src/stores/historyViewer.store.ts:75-90` 直接赋值，因此第一页为倒序；
- `loadMore()` 在 `:99-115` 合并后却按 `sortKey` 升序排序；
- `image_video` 双流分支与 `RestMapper.toChatHistoryPage()` 又使用升序，导致不同分类也不一致。

### 6.3 已冻结的目标行为

前端历史查看器领域层统一按 `sortKey` 升序展示；后端仍保持 DESC keyset 分页，不修改 cursor 语义：

1. 单流第一页进入领域前就升序归一化，与 `image_video`、Mapper 和 `loadMore` 一致；
2. 加载更早一页后，全局仍稳定升序，旧项插到合适位置，不能整表翻转；
3. 同时间戳用 `messageId/hitId` 作稳定次键；
4. cursor 必须继续原样使用后端返回值，排序只能作用于展示副本；
5. 合并继续按 `hitId` 去重，并保持滚动锚点，避免插入旧项后用户视口跳走。

### 6.4 必须补充的测试

- 单流后端返回 `[new, old]`，第一页领域结果为 `[old, new]`；
- 第二页是更旧数据，合并后全局升序、无重复、cursor 原样续接；
- 同时间戳稳定次排序；
- `all/sticker/file/audio/link/image_video` 分类排序一致；
- 500 条多页加载无重复、无遗漏、无整体翻转，加载前后的可见锚点保持。

### 6.5 完成验收

真实 Electron 连续加载至少两页 50 + 50 条结果，顺序始终一致，页间无重复/遗漏，来源跳转仍定位正确。

## 7. 后端配套依赖：不要在前端掩盖 MIME 真值问题

当前后端对 WebM audio 返回 `kind=audio,mime=video/webm`，对 WAV 返回 `audio/x-wav`；重载时又可能回退为 `audio/wav`。主修归后端 BE-S3-RUN-P0-02：规范为 `audio/webm`、`audio/wav` 并保证上传、记录、下载、replay 一致。

前端在后端修复后应补真实契约测试，并继续以服务端最终 `kind/mime` 构造消息。不要把 audio 静默降级成 file、也不要仅扩大白名单来掩盖重载前后 MIME 不一致。若决定额外兼容历史别名，应作为显式兼容层并有测试，不能改变规范输出口径。
