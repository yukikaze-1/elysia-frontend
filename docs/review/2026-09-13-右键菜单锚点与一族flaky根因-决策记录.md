## 1. 右键菜单被列表滚动关掉（`CyContextMenu`）

### 1.1 现象与取证

集成用例 `context-menu.spec.ts` 的 ④b 步骤（右键用户消息 → 菜单应出现）在本机 Windows **稳定红**、CI Linux 绿，
而**同一次全量本机集成**里其余 36 个文件全过。取证过程（每一步都留了读数）：

1. 先排除"是不是我上一批改坏的"：把 ④ 的判据临时改回修复前的行为（`USER_SCROLL_MIN_PX = 0`）重建后**同样红**（连跑 2 次）⇒ 与本批无关。
2. 加只读探针（`data-menu-opens` / `data-menu-open`）后复现：右键那一刻 `menuOpen=1`、计数 +1
   ⇒ **菜单确实开了**；400ms 后 `menuOpen=0`、DOM 里没有菜单了。
3. 同时段窗口监听：**恰好一次 scroll 事件**，且 `.cy-messages` 的 `scrollHeight` 从 710 变成 742（列表自己在做布局/重锚调整）。

⇒ 结论：`CyContextMenu` 原先"**任何滚动即关闭**"（`window.addEventListener('scroll', …, true)`，capture 相位、
任何元素的滚动都算）**分不清"用户滚的"与"应用自己滚的"**——流式回复期间消息列表会自行跟随底部/重锚，
于是用户刚打开的菜单被列表自己的滚动关掉。

### 1.2 修法：把"关闭"换成"跟随"，并给出真正的关闭条件

`CyContextMenu` 新增**可选** `anchor?: () => HTMLElement | null`：

- **给了锚点**（消息列表、会话列表都给了）：
  - 打开时记录"指针相对锚点"的偏移；
  - 滚动/缩放时**重新贴回锚点**（保持该偏移），菜单不再与它所指的对象脱钩；
  - 只有锚点**从 DOM 消失**或**整体移出视口**才关闭——那才是"菜单会指向错误对象"的真条件。
- **不给锚点**：保持既有语义（任何滚动即关）。

消息侧的锚点是"渲染窗口里那一行"（`[data-message-id=…]`）：虚拟列表把行卸载掉（滚出窗口）时
`querySelector` 返回 null ⇒ 菜单关闭，正是想要的语义。

### 1.3 验证（判据都做过变异）

| 层 | 用例 | 变异：把"跟随"改回"任何滚动即关" |
|---|---|---|
| 单测 `cy-context-menu.spec.ts` | 新增 4 条：跟随（相对偏移保持）、锚点消失→关、锚点出视口→关、无锚点→滚动即关 | **跟随那条变红**，另 3 条仍绿（判别力落在该落的地方） |
| 集成 `context-menu.spec.ts` | 新增 ④c：滚动列表后菜单**仍在**，且与行**同幅**移动 | 摘掉 `CyMessageList` 的 `:anchor` 绑定 ⇒ **④c 红**（`滚动不得关掉菜单`），其余断言不受影响 |

集成侧那条断言写成了"行与菜单**同幅**移动"，因此对"列表随后又被跟随逻辑拉回底部"也成立（那一瞬两者一起动）。

## 2. real-backend-search 一族"偶发"：**三条各自独立的根因**（都不是被测产品逻辑）

用户报的那次是 `real-backend-search.spec.ts` 的 `RealBackend.restFailure`。用"全量单测连跑 15 次"复现
（`FAIL` 行逐次记录），拿到的是**多处不同文件、多种不同机制**——即"偶发"其实是几件事叠在一起。

### 2.1 根因一：happy-dom 默认 URL 会让每个 happy-dom 文件**真的去 fetch `http://localhost:3000`**

- 证据链：stderr 里 `AsyncTaskManager … browser frame is closed` 的栈是
  `BrowserFrameNavigator.navigate → Fetch.send → AsyncTaskManager.startTask`；同一条错误里还有
  `ECONNREFUSED ::1:3000 / 127.0.0.1:3000`。而**没有任何** spec 会去连 3000 端口（全仓只有两处把
  `http://localhost:3000` 当**数据**用）。
- 源头：vitest 的 happy-dom 环境把窗口 URL 默认设成 `http://localhost:3000`
  （`url: happyDOM.url || "http://localhost:3000"`），happy-dom 据此**发起一次真实页面请求**；
  这次请求经常在环境拆卸**之后**才落定，于是抛出**未处理错误**——vitest 把它记到**当时正在跑的那个文件**头上。
  这也解释了为什么"每次红的文件都不同"（real-backend-search／diagnostics-handlers／session-store 各一次）。
- 修法：`vitest.config.mts` 加 `environmentOptions: { happyDOM: { url: 'about:blank' } }`（不发起网络请求）。
- 验证：连跑 13 次，`AsyncTaskManager` 与 `ECONNREFUSED` 的出现次数从**每次 3/5 条**降到 **0**。

### 2.2 根因二：默认 5s 单测预算在机器被压满时不够（I/O 重的用例）

- 证据：复现轮里另有两次红是 `session-store.spec.ts`（连写 52 条会话）与 `diagnostics-handlers.spec.ts`，
  报的是 `Test timed out in 5000ms`，紧随其后还有 `ENOTEMPTY: directory not empty, rmdir …cyrene-session-…`
  （超时后 `afterEach` 清理与仍在跑的异步写撞上）。
- 判定：这是**预算不够**，不是产品坏了——断言本身与 happy-dom 无关，且与根因一同时被记到不同文件上。
- 修法：`testTimeout` / `hookTimeout` 提到 **15s**（真卡死仍会被抓住，只是晚 10 秒）；
  与集成套件对 flake 的处置口径一致（**提预算，而不是加 retry 掩盖**）。

### 2.3 根因三（**未定论，但有实测边界**）：本机夹具 HTTP 请求偶发失败

修掉前两条之后，`real-backend-search.spec.ts` 在**重负载连跑**下仍有约 **1/5–1/10** 的失败，形态与
happy-dom 无关：`CyreneError: 无法连接后端：网络请求失败`（`restFetch` 的兜底），栈指向该用例自己的
本机夹具 server。逐条排除与处置：

- **不是超时**：把该用例的 `restTimeoutMs` 从产品默认 10s 显式提到 **30s** 后失败照旧
  （该显式值仍保留：夹具是本机的，且本文件没有用例在测"默认 10s 生效"）。
- **不是 happy-dom 泄漏**：探针实测该 node 环境里的 `globalThis.fetch` **就是 Node 自己的实现**
  （`internal/deps/undici/undici` 懒加载那份），`document` 也不存在 ⇒ 我原先怀疑的"happy-dom 的 fetch
  泄漏到 node 环境"这条**被证伪**。
- **处置（修法，不宣称已定论）**：夹具响应改成 `Connection: close`。理由：Node 的 fetch（undici）
  **连接池是进程级全局的**，而本文件每个用例都起一台夹具 server 再关掉——池里可能留着上一台（已关闭）
  的 keep-alive 连接，重负载下 OS 复用同一临时端口时新请求就可能落在死连接上。
  **实测**：改前同一命令连跑 10 次 1 红、另 5 次 1 红；改后**连跑 20 次 0 红**（若真实失败率 15%，
  20 连绿的概率约 4%）。这是**夹具层面的稳健性修法**，未改任何断言与夹具语义。

**仍然成立的两条残余**：

1. **这条偶发在 CI 上也真的出现过一次**（`34774946206` 的 `windows build-level` job，同一个 spec、同一句话，
   栈指向 `queryChatHistory`）——即它不是"只在本机人为负载下才有"。故本轮**同时把诊断面补上**（见下）。
2. 20 连绿是在**本机、按 10 连跑的方式**取得的；CI 分片负载不同，**不构成"CI 上也不会红"的证明**。

**诊断面补上（`d492f31`）**：`restFailure` 原先把 `ECONNREFUSED`／`ECONNRESET`／abort／DNS 等完全不同的成因
压成同一句话**且不留任何痕迹**——本轮为定位它花了三轮，主因就在这里。现在：

- 原始错误挂到**非枚举的 `cause`**（ES2022 语义）：诊断代码拿得到、序列化输出里不出现；
- `details` 里只放**成因的码/名**（`error.code` 是字符串就用它，否则用 `error.name`／`typeof`），
  **不带消息、不带路径**——vitest 会把 `details` 序列化进失败输出，于是**下一次偶发在 CI 日志里就能读出成因**；
- 用户可见文案、错误码、IPC 投影均未变（已核实 IPC 执行器只从 `details` 取特定字段，不整体转发）。

**因此这一条的定性是**：机制**未完全定论**（已排除超时与 happy-dom 泄漏；第三个候选——连接池复用死连接——
有 20 连绿的支持性证据但不足以定论），**但下一次出现时成因会被自动记录**；处置与读数边界都在本记录里，
不需要再"花三轮"。


### 2.4 边界（如实记录）

- 三条根因都是在**人为制造的负载**（连跑全量套件 + 并行跑集成套件 + 并行 agent）下复现的；正常单跑从未见过。
- 根因一/三**修的是测试夹具与环境**（不改被测代码）；根因二**修的是测试预算**。
- 本轮**没有**给任何用例加重试、没有放宽任何断言、没有改产品的超时默认值。

## 3. 测试侧 type-aware lint 全集（口径 A）

### 3.1 测量与口径

- 测试目录在全集下实测 **455 条 / 74 文件**；其中 `no-unnecessary-type-assertion` **208 条全部可自动修**，
  自动修后剩 **259 条 / 48 文件**。
- 两条豁免（**有计数、有理由**）：`require-await`（474 条，`async` 测试替身）与
  `unbound-method`（73 条，vitest 的 `expect(obj.method)` 惯例）——理由与生产侧同款，见
  [type-aware lint 全集接入生产代码](2026-09-13-type-aware-lint全集接入生产代码-决策记录.md) §3。
- 其余规则分布：`no-unsafe-assignment` 108、`no-unsafe-member-access` 57、`no-unsafe-argument` 54、
  `no-base-to-string` 18、`no-unused-vars` 8（自动修的连带）、`no-unsafe-return` 8、`only-throw-error` 1、
  `no-unsafe-call` 1。

### 3.2 修法口径（**写给复核的人**）

优先**给值本身标注真实类型**（例如把 `vi.fn((input) => …)` 改成 `vi.fn((input: CharacterListQuery) => …)`，
类型从 `@shared/contracts` import）——这类修法的价值不只是消警：**契约漂移时测试会编译失败**。
其次才是 `unknown` + 判型；禁止 `any` / `as any` / `@ts-ignore` / `eslint-disable`（复核时按这三个模式扫过 diff）。

### 3.3 过程中的两次"自动修复必须复核"（同族，第二次了）

`eslint --fix` 在测试侧也删错过断言：`tests/integration/electron-live2d.spec.ts` 的
`document.querySelector('select[aria-label=…]') as HTMLSelectElement` 被判为多余，删掉后 `.value` 编译不过
（属性选择器不触发 TS 的标签名映射）——改为 `querySelector<HTMLSelectElement>(…)` 泛型形式。
**这与生产侧 `as 'error' | 'warning'` 被删错是同一类**：`--fix` 的结论必须过一遍 typecheck。
