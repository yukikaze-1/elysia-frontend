# M-26 录音 PCM 缓冲收口 · 决策记录

**日期：** 2026-09-14
**范围：** `apps/desktop/src/renderer/src/voice/voice-capture.ts`（录音段内存模型）与其单测。**`onStop(AudioBuffer)` 契约未变，store／组件／IPC 零改动。**
**来源：** 全量评审 M-26（[2026-09-11-full-frontend-review.md](2026-09-11-full-frontend-review.md) §M-26，P2-9 子项），此前多轮被列为"独立批次、触及音频热路径"而未做。

## 1. 问题是什么（评审原文已由代码逐处坐实）

`PcmCapture` 每个 20ms 帧做三件事（改造前）：

1. 把 Int16 解码成 `Float32Array`（320 样本）——**只为算 RMS 做静音判定**；
2. 把这个 float 数组推进 `floatChunks` **留下来**；
3. 原样把 bytes 交给 `onChunk` 发后端。

`stop()` 在关闭 `AudioContext` 之前（closed 上下文 `createBuffer` 抛 `InvalidStateError`，故顺序不能改）再建 `AudioBuffer`：先 `new Float32Array(totalSamples)` 把 30000 个碎片拼平，再 `copyToChannel` 拷进去。

唯一约束是 `voice.store.ts` 的 `RECORD_HARD_CAP_MS = 600000`（10 分钟）。

**范围比评审描述的更窄**（逐链路核对 `onStop` 接线）：

| 链路 | 是否累积整段音频 | 证据 |
|---|---|---|
| record（普通录音） | **是** | `voice.store.ts` `onStop: (ab) => { record.value.audioBuffer = ab }` |
| realtime（实时语音） | 否 | 只传 `onChunk`，无 `onStop` |
| dictation（输入法转写） | 否 | 只传 `onChunk` |

且 `audioBuffer` 的**唯一消费者**是 `replayRecord()`（试听）；`CyVoicePending` 只读它判断"试听是否可用"。真实使用里语音消息是 10–30 秒 ⇒ 原实现的代价（1.8MB 常驻 / 峰值几 MB）**完全无感**。**M-26 只在"有人真按住录数分钟"时咬人。**

## 2. 实测（这是本批全部结论的依据）

**度量口径先行**：必须用 `process.memoryUsage().arrayBuffers`，**不能用 `heapUsed`**。V8 把大 typed array 放在堆外，`heapUsed` 对它们几乎不计数——本批我先用了 `heapUsed`，读到"扁平数组只占 0.7MB"，据此差点得出"问题不大"的错误结论。改口径后数字才对上（≈36.6MB）。

**10 分钟 = 30000 帧：**

| 量 | 改造前 | 改造后 |
|---|---|---|
| 常驻 | **36.6MB**（30000 个 `Float32Array`） | **约 20MB**（1 个 `Int16Array`；9,600,000 样本 = 18.3MB，2 倍增长浪费 9%） |
| `stop()` 瞬间**同步存活** | **73.2MB**（碎片 36.6 + 扁平数组 36.6） | **约 20MB**（不再产生中间扁平数组） |
| 逐帧对象数 | 30000 | 1 |
| `stop()` 内同步耗时 | 18ms | 约 19ms |

**一处必须纠正评审措辞的地方**：评审写"停止瞬间再加两份完整拷贝 ≈ 115MB"——那是**总分配量**，不是峰值存活量。实测 `stop()` 内同时存活的 JS 侧是 **73.2MB**（拼接完 flat 后 `floatChunks` 仍在，这份 36.6MB 要到 `clearState()` 才释放，而它在 `onStop` **之后**）；第三份是浏览器侧的 AudioBuffer，JS 侧探针看不全。**结论方向不变（确实是三份），但写进代码注释的必须是实测的 73.2MB。**

**另一处纠正评审措辞**："约 30000 个独立 `Float32Array` 对象头"被列为代价之一，但 `perf_hooks` 的 GC observer 实测两者**GC 停顿都是 0.0ms、总耗时 20ms vs 18ms** ⇒ **这不是延迟问题，纯粹是内存峰值问题**。

## 3. 修法（三件，全部落地）

### ① 累积原始 Int16（`PcmAccumulator`）
单个可增长 `Int16Array` 取代碎片数组。初始容量 320KB（≈10 秒）⇒ 典型 10–30 秒语音消息**全程不扩容**；2 倍增长（实测 10 分钟浪费 9%）。
**曾考虑 1.3 倍增长**：只多省约 1.1MB，却要多约 3 倍次数的拷贝——不值得，已记录在类注释里。

### ② 静音判定改读 Int16（`computePcmRms`）
**这是让改造成立的关键发现**：RMS 可以从 Int16 直接算，且与 `computeRms(floatToPcm16(x)/32767)` **数值等价**——因为 `floatToPcm16` 就是 `round(clamp(v)*32767)`，除以 32767 精确还原同一套代数，唯一差别是量化误差（约 3.05e-5），相对 `SILENCE_RMS_THRESHOLD = 1e-2` 小三个数量级。
⇒ **那个每帧的 `Float32Array` 可以完全不产生**，`floatChunks` 随之整个消失。
`computeRms` **保留**为 Float32 侧的规范实现（判据用例一字未动），并被新增的等价性用例消费。

### ③ `stop()` 直接解码进通道存储
`buffer.getChannelData(0)` 写一次，取代"拼 flat → `copyToChannel`"两次大分配。

**顺带修掉一个存量隐患**：原实现的缓冲构建在 try/catch 之外——`createBuffer`/`copyToChannel` 一旦抛错，后面的**轨道停止与 context 关闭全被跳过**（麦克风白占、`AudioContext` 泄漏）。现改为 `finally` 兜底。且 `onStop` 仍在 `finally` **之前**调用，故"无捕获样本不回调"的语义未变。

## 4. 验证

**新增 3 条用例**（`tests/unit/voice-capture.spec.ts`，该文件 13 → 16 条）：

1. **等价性特征化**：`computePcmRms` vs `computeRms(floatToPcm16(x)/32767)`。**用波形而非 ±1 这类定点值**——那些值两条路径都恰好精确，测试会平凡通过、证明不了量化误差。同时断言量到的是正确幅值（`0.3/√2`），否则"两边同为错误值"也能算"等价"。
2. `PcmAccumulator` 基本语义：跨块按序、`extract` 切出恰好尺寸、取出后归零、空时返回 `null`。
3. 扩容路径：推 2000 帧（超过初始 327,680 样本容量）后按序不丢不漏，并**校验扩容衔接处**（第 2 帧首 = 2）。

**变异验证 4 次**（每次确认真的改了代码路径、且红在预期断言上）：

| 变异 | 结果 |
|---|---|
| A `if (need > this.buf.length)` → `if (false)`（越界写） | 红 —— **且只有"扩容路径"那条红**（说明它是扩容检查的唯一守护者） |
| B `extract` 的 `slice(0, this.length)` → `slice(0, length-1)` | 红 **4 条**（两条 Accumulator + 两条 PcmCapture） |
| C 写入循环 `pcm.length` → `pcm.length - 1`（漏写最后一格） | 红 —— 恰在尾部哨兵断言 |
| D `computePcmRms` 的 `/32767` → `/32768` | 红 —— 恰在等价性用例 |

**一次我自己造的弱断言被变异抓出**：尾部边界我最初写成 `copied[959]` 对 `makeChunk(0)` 的值断言，而 `0` 正是 `Float32Array` 的初值 ⇒ **"漏写一格"与"写了 0"无法区分，变异 C 会假绿**。改为让末块填非零哨兵（8192）后才真正有判别力。

**集成回归**：`electron-voice` **16/16**（含用例 1「录音闭环」——它断言"录音后有音频缓冲 ⇒ 试听可用"，正好覆盖 `copyToChannel` → `getChannelData` 这条改动路径，且用的是真实 AudioWorklet + Chromium fake capture device，走过的字节是真的）、`voice-silence-autostop` **1/1**（静音自动结束在真实链路上仍成立 ⇒ Int16 版 RMS 与 float 版行为一致）。**`onStop(AudioBuffer)` 契约未变**，store/组件零改动。

**门禁**：`pnpm test` **253 文件 / 3110 通过**（+6 expected-fail +22 skipped）、`pnpm typecheck` 双端 exit 0、`pnpm lint` exit 0（`--max-warnings=0`）。

## 5. 刻意没做的事

1. **没有动 `onStop(AudioBuffer)` 契约**：曾考虑改成 `onStop(pcm: Int16Array)` 让渲染层自己解码，但那会把"试听"的音频上下文交给 store、并改动 store/组件/4 个测试文件——**收益仅是省掉一份临时 Float32Array，成本是整个契约面**，不做。
2. **没有改 `RECORD_HARD_CAP_MS`（10 分钟）**：上限本身是产品决定，与内存模型无关。
3. **没有为 realtime／dictation 加任何东西**：它们本就不累积，加了反而是新增记忆面。
4. **没有给 `PcmAccumulator` 加上限**：上限已由 `RECORD_HARD_CAP_MS` 在 store 层强制（到点自动 `stopRecord`）。在累积器里再设一个上限会变成第二处需要同步的常量。
5. **没有把 `computeRms` 删掉或改签名**：它是既有判据用例的被测对象（4 条断言），改它会为了"整洁"而削弱既有覆盖。

## 6. 残余

1. **浏览器侧那个 `AudioBuffer`（10 分钟 ≈ 36.6MB 样本数据）无法用 JS 探针度量，也仍是必要成本**——试听需要它，且它是 `onStop` 契约的载体。故改造后仍有"停止瞬间约 20MB(Int16) + 36.6MB(AudioBuffer)"的量级；本批只保证**不再有第三份**。
2. **探针是临时文件、跑完即删**，未入库（本批的量化数据因此不可由 CI 复现，属一次性取证）。
3. **`PcmAccumulator` 的"2 倍增长浪费 9%"是实测值而非证明**：它取决于录音长度与 2 的幂的关系，最长录音（恰好 9,600,000 样本）时容量为 10,485,760。
4. **本批只改内存模型，不改任何用户可见行为**——故 doc 11 §3.3 的产品口径无需变更；仅在 doc 16 §3.1 记门禁与验证。
