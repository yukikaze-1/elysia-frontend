## 3. 逐项依据与验证

### 3.1 主动间隔清空导致保存静默失效（产品缺陷，已修复）

**缺陷链**：`Number('') === 0` 是有限数 → `updateInterval` emit `intervalSeconds: 0`（而非代码注释意图的回退 3600）→ 输入框自身 `min="60"` 判 `rangeUnderflow` → 该字段位于折叠的「高级：主动对话」内，Chrome **既不展开该区域也不移动焦点**，原生气泡在 `display:none` 子树中无处渲染，`submit` 事件一次都不派发 → **用户点「保存角色」没有任何反应，且零提示，编辑内容根本没保存**。

**真机复核**（`tmp/probe-form-fix.mjs`，Playwright 真实 Chromium 复刻修复后结构）：

| 场景 | 结果 |
|---|---|
| 清空输入框后点保存 | 输入框值回填 `3600`；`formValid: true`；`submits: 1`（提交真正放行） |
| 值为 `0`（模拟旧草稿）后点保存 | `submits` 不增；`invalid` 事件 `target` = 该输入框；提示文本 = 「主动间隔（秒）（/runtimeDefaults/proactive/intervalSeconds） 不符合输入要求，已阻止保存：请修正后重试。」；`detailsOpen: true`（折叠区被展开） |
| 值改回 `1800` | `formValid: true`；`submits: 2` |

同时确认一个关键机制事实：**`novalidate` 抑制的是「提交时自动校验并弹气泡」，`checkValidity()` 触发的 `invalid` 事件仍会派发**（HTML 规范的 interactivity 分支），因此「先关掉原生气泡、再自己查并自己解释」是可行的，且能拿到精确的失败字段。

**语义选择**：清空即「未填写」→ 回退默认值 3600，而非「保持原值不动」。理由是代码注释原本就写明回退 3600（意图明确）、且与后端契约默认值一致；超界值同样回退而不是夹取到边界，避免静默改写用户输入。

### 3.2 附件渲染失败被误报为附件正常（产品缺陷，已修复）

**缺陷**：元素已损坏却把 `mediaStatus` 置成 `attachmentsCheck` 返回的 `ok` → 占位永不出现 → 用户面对一个静默损坏的媒体元素，既无解释也无重试入口；而其他所有失败路径（expired/not_found/revoked/error）都会给出带文案的占位。触发场景现实存在：字节完好但浏览器解不开（截断图片、容器/编解码不受支持）。

**语义拆分的理由**：`ok` 是「附件在服务端可用」的事实，不该被本机解码结果覆盖；反过来，本机解码失败也不该谎报成「附件不存在/已过期」——那会把用户引向错误的处置动作（重新上传）。因此新增独立信号，文案用「无法显示该附件」（表达本机渲染结果），重试按钮保留（重查仍 `ok` 时换 nonce 真正重新请求）。

**测试更正**：评估记录 §8.1 第 2 条初版曾记为「error→check→ok→重挂载的无退避循环」，经探针实测证伪（前后 DOM 节点同一、`src` 不变、`attachmentsCheck` 调用次数恰等于手动触发次数）。原「锁定现状」用例已改为锁定修复后语义，并在注释中保留更正说明。

### 3.3 集成套件遗留测试应用（测试基建，已修复）

**根因**：套件被中断时 `launchApp` 拉起的测试应用不会退出，带着 `--user-data-dir=<tmp>/cy-int-ud-XXXX` 长期驻留（一个实例 main + gpu + utility + renderer，实测约 375 MB）。孤儿跨运行累积，与后续运行争抢 CPU/GPU，使 `electron-live2d` 这类「启动后连接后首次交互」的重型 spec 在每个 8s 等待预算上偶发超时——单文件跑必绿，全量跑随机红。CI 用一次性 runner，不存在该机制。

**判据的关键事实**（决定了实现形状）：签名**分处两个进程**，实测采样：

```
main    : "<exe>" "--inspect=0" "--remote-debugging-port=0" "<repo>/apps/desktop"
renderer: "<exe>" --type=renderer --user-data-dir="<tmp>/cy-int-ud-HmxGhg/Cyrene" ...
```

即 Playwright 调试开关只在 **main** 上，`cy-int-ud-` 临时 userData 只在**子进程**上，且**子进程命令行里完全没有仓库路径**。因此：

- 两个信号各自成判据（不能要求同时成立）：信号一 = 仓库 app 目录 + Playwright 调试开关；信号二 = `cy-int-ud-` 临时 userData 目录段（该前缀只有 `launchApp` 的 `mkdtemp` 会产生）。
- **按「应用实例」聚合回收**：沿 `ppid` 回到 main 进程整体回收。直接杀子进程会触发 Chromium 崩溃恢复重建，反而留下更多进程（这正是只看单进程判据时的错误行为）。
- `pnpm dev`（真实 userData + 无 Playwright 调试开关）与用户真实应用都不匹配；进程表不可读或平台不支持时**什么都不做**并报告，绝不猜测。

**真机端到端验证**：真实拉起一个测试应用后执行回收——识别出 6 个遗留实例、`killed` 24 个进程、`failed` 0，`electron` 进程数 **20 → 0**；随后完整集成套件 **22 files / 136 passed / 2 skipped 全绿**。

**同时落地**：`app.ts` 注册进程退出兜底（用例忘记 `closeApp` 时应用不活过测试进程）。`globalSetup` 位置的选择理由：孤儿回收只需在套件启动时做一次，per-file `setupFiles` 会让每个测试文件各查一次进程表（实测 22 个文件累计约 15s），收益为零。

## 4. 本轮不做的事情

- **不改安全策略**。§8.1 之外的既有残余项（`openSafeFile` 非 0600 的静默丢弃、`allowRoots` 注入面、`check:contract` 本地 `NOT VERIFIED`、`EXT-01` 第三方资产授权）全部维持原状，处置见评估记录 §8.2 与 [EXT-01 决策记录](2026-09-10-第三方资产授权与来源立为阻塞项-决策记录.md)。
- **不改集成 suite 的等待预算与 POLL 常量**。孤儿是已证实的根因，扩容等待只会掩盖同类宿主负载问题；现在孤儿在套件启动时即被清理，并有明确输出。
- **不为 §8.1 第 3 条（死代码/守卫不一致）做无收益改动**，理由见 §2 表格第 4 行。

## 5. 防复发

| 失效模式 | 防护 |
|---|---|
| 未来任何字段再走「原生约束静默拦截整个表单」 | 表单 `novalidate` + 提交前自查；失败时必然渲染原因（含「无 `data-field-path` 控件」的兜底文案），不可能回到静默返回 |
| 同一失效模式扩散到其他表单 | **全仓 6 个 `<form>` 已逐个核对**：只有 `CyCharacterEditor` 同时具备「原生约束字段 + 折叠容器」两个前提。其余为搜索表单（无约束字段）或字段可见且自带内联错误与 `aria-invalid`（`CyIdentityPane` 的 `displayName`/`locale`/`timezone`），最坏情况是浏览器气泡可见地拦截，不构成静默失效 |
| 回退边界与输入框 `min/max` 漂移 | 同一组常量同时驱动脚本回退与模板绑定，单测断言两者一致 |
| 附件渲染失败再次静默 | 单测钉住「分类 ok + 元素损坏 → 必须出现可重试占位」，并覆盖重试后仍失败仍回到占位 |
| 孤儿进程再次跨运行累积 | 套件启动即回收并打印结果；进程表不可读时打印「未执行」而非静默通过；`Get-Process electron` 仍是诊断第一步 |
