# M-19 设置保存失败可见性 —— 决策记录

**日期：** 2026-09-13
**范围：** 评审 [2026-09-11 全量评审](2026-09-11-full-frontend-review.md) 的 **M-19**（设置保存失败对用户不可见且被丢弃）；连带处置 doc 16 规格漂移台账里 doc 11 §9「未同步／同步中／已同步／错误 四态」那一行（原建议"砍或改写规格"）
**触发：** 用户在 H-11b renderer 半边落地后直接指定「M-19 继续排查和修复」
**结论：** **已落地**。(a) 保存失败不再丢弃改动；(b) 失败对用户可见且说明"改动没丢"；(c) 原「跨端同步四态」按**本地保存**语义改写为三态并实现；(d) **顺带发现并修掉一处启动路径缺陷**——设置文件隔离失败会让整个应用起不来。

## 1. 先复核，再动手（评审是 2026-09-11 写的，两处都要实测确认）

| 评审原文 | 本轮实测（2026-09-13） | 结论 |
|---|---|---|
| `pending = {}` 在 `await` 之前执行，catch 只写 `saveError` | `settings.store.ts:88-89`（修前）确为 `const patch = pending; pending = {}` 再 `await api.settingsSave(patch)` | **成立**：写盘失败即丢弃该 patch |

**排查中额外发现的第四条（不在评审里）**：

`SettingsService.load()` 的 catch 里 `await this.isolation.isolate(...)` **没有自己的 try/catch** —— 隔离本身失败时异常继续上抛，而 `main/index.ts:374` 是 **eager `await settingsSvc.load()`**，注释写着"fail-open：损坏/版本不匹配隔离备份 + 回默认，**不阻塞启动**"。即：**注释与实现相反**——"配置文件是符号链接 / 被 AV 或备份代理锁住导致改名失败"这条链（与 H-11b 给 `SessionStore` 修的是同一族条件）会让**整条启动装配被打断**。

证据（变异 M3，把隔离失败的 catch 改回上抛）：
- 单测：`await svc.load()` 由 resolve 变 reject（`isolate 目标逃逸安全根: C:\Users\…`）；
- **端到端**：`settings-save-failure.spec.ts` 红在 `electronApplication.firstWindow: Target page, context or browser has been closed` —— **应用根本没起来**。这是修前真实存在的启动崩溃，不是理论风险。

## 2. 修法与取舍

### 2.1 失败不丢改动（M-19 的核心）

```ts
// 修前：pending = {} 在 await 之前 → 失败即丢
// 修后：
} catch (e) {
  pending = mergeSettingsPatch(patch, pending)   // 放回队列；**等待期间的新改动优先**
  unsaved.value = true
  saveError.value = parsePublicError(...)
  if (!retryScheduled) { retryScheduled = true; /* 3s 后重试一次 */ }
}
```

取舍：**不做无限自动重试**。磁盘满/权限不足是**持续**失败，按 500ms 防抖节奏重试等于热循环打盘；故只安排**一次**、间隔 3000ms（`SETTINGS_SAVE_RETRY_MS`），再失败就把 patch 留在队列里，交由下一次修改或退出 flush。测试把"恰好重试一次"钉成了断言（`toHaveBeenCalledTimes(2)` 并跨 10 个重试周期复验）。

`mergeSettingsPatch(older, newer)` 与 `hasPendingPatch(patch)` 抽成导出的纯函数：前者供"失败回滚"和"防抖累积"共用（否则两份合并语义必然漂移），后者收口早退判据（新增子树时只改一处——live2d／appearance 两批都曾因漏改早退条件而出现"只改该子树时 persist 早退"的隐患）。

### 2.2 失败可见：三态常驻 + 文案单一来源

- 位置：设置中心**头部下方**，不随子页切换消失（用户在任何子页拨动开关都能看到结果）；
- 三态**优先级**：保存失败（`role="alert"`）> 正在保存 > 已保存（三条同时为真时只显示失败，不允许被"已保存"盖住）；
- 失败文案必须包含**动作**（检查磁盘空间/目录权限）与**"改动仍保留在待写队列"**——后者是本轮修复的事实，不说就等于让用户以为白改了；
- store 只产出 **code**（`PublicError`，`parsePublicError` 解析），措辞归 `utils/error-message.ts`——与 2026-09-10「多套 UI 基础」定下的分工一致。**形状从原始 message 改成 code 是破坏性的**，但该状态此前无任何消费者，故无迁移负担；单测里那条断言同步改写，并注明 `parsePublicError` 取**第一个**方括号段为 code（`[IPC_ERROR] [UNKNOWN] x` → `IPC_ERROR`，既有语义）。

### 2.3 跨 IPC 的码：新立 `SETTINGS_SAVE_FAILED`，降级复用 `PERSISTENCE_DEGRADED`

- 单次写失败用**设置专用码**，这样 UI 说的是"设置没写进磁盘"而不是"草稿/缓存没写进磁盘"——两类改动在用户眼里是不同的事；
- **隔离失败（不可自愈）复用 `PERSISTENCE_DEGRADED`**：那句话（"本地保存已停用…为避免覆盖现场已停止一切写入"）对两个域同样成立，不另立码；
- Main 侧把 `atomicWriteFile` 的裸 fs 错误包成 `toWriteFailure(e, SETTINGS_SAVE_FAILED)`：**只带 errno、绝不带路径**。该函数从 `session-store.ts` 提取到 `main/persistence/write-failure.ts`（H-11b 那批写的），因为"只取 errno 形状的码 + 不带原文"是**同一条判据**，两处复制必然漂移；`session-store` 与 `settings-service` 现在共用同一份实现。

### 2.4 启动路径：隔离失败转降级，不再打断装配

`SettingsService` 现在与 `SessionStore` 同纪律：`degraded` 置位 → `getLastError()` 可诊断 → `assertWritable()` **拒绝一切写入**（保现场，绝不覆写未能隔离的原文件）→ 启动照常。降级只在**下一次保存被拒**时才对用户可见（见 §4 残余）。

### 2.5 文案：把"500ms 自动保存"改成真实陈述

`CyLive2DPane` 的落款改为「修改即时预览，约 0.5 秒后自动保存（保存结果见页面顶部状态）」——现在这句话有对应的可见状态，不再是单向承诺。

## 3. 刻意没做

| 未做项 | 理由 |
|---|---|
| 无限/指数退避自动重试 | 见 §2.1；持续失败下把"重试"变成打盘热循环是负收益，且退出 flush 与下一次修改已覆盖恢复路径 |
| 给 `settings:load` 也带一个降级标记 | `SettingsStateSchema` 就是 **settings.json 的文件格式**（同一份 schema 既校验文件又校验 IPC 响应），往里加运行态字段会污染文件格式。降级因此在"下一次保存被拒"时才可见——记为残余 |
| 设置中心的「重试」按钮 | 自动重试一次 + 下一次修改/退出 flush 已覆盖；加按钮是把自动恢复变成用户负担（与 H-11b 同一取舍） |
| 把 `AppearanceSettings`/`voice` 等子树的保存失败分开显示 | 三态是**整份设置**的保存状态（Main 一次 patch 写一个文件），按子树拆分会假装有四份独立状态 |
| `CharacterDraftStore` 同款的 `isolate().catch(() => {})` | 那是 H-11b 明确否掉的形态（"改名失败被吞"）——本批没有顺手改成降级态，因为它不在 M-19 范围内，且其 `lastError` 已被角色编辑器渲染；**记为独立未做项** |

## 5. 残余（如实记录）

1. **降级态只在"下一次保存被拒"时可见**：`settings:load` 不带运行态标记（理由见 §3）。若启动即降级且用户从不改设置，UI 不会主动提示——与草稿域（H-11b 随水合告知）**不对称**，因为设置域的响应 schema 就是文件格式。要做需新增一条只读通道。
2. **`CharacterDraftStore` 的 `isolate().catch(() => {})` 未改**：同族形态仍在（见 §3），其失败经由 `lastError` 在角色编辑器显示。
3. **退出 flush 失败仍无法告知**：窗口正在关闭，无处显示（H-04 与 M-19 的固有交界）；错误状态至少已在关闭前显示过。
4. **`SETTINGS_SAVE_FAILED` 的 errno 细分未做**：UI 文案只说"检查磁盘空间或目录权限"，不区分 `ENOSPC`/`EACCES`/`EROFS`（errno 已在 message 里，需要时可再细分）。
