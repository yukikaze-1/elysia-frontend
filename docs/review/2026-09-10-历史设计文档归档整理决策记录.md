# 历史设计文档归档整理决策记录

**决策日期：** 2026-09-10

**文档状态：** 已定案；整理已执行并收口（归档判据仍作为后续维护规则生效）

**适用范围：** `docs/superpowers/` 与新增 `docs/archive/`

**影响文件：** 42 份历史文档移动（`git mv`，历史保留为 R100 重命名）；`scripts/docs-check.mjs` 索引生成扩展；`docs/archive/README.md` 新增

## 1. 背景

`docs/superpowers/` 累积了 82 份历史文档（10 final report + 36 spec + 36 plan），全部平铺在三个目录里。其中阶段 0～2 的批次已完全闭账、结论由 final report 接管，设计内容也已被后续阶段与现行代码吸收，但它们在索引中与阶段 7 等仍然生效的技术记录混排，读者无法从目录结构判断哪些是「当前实现的依据」、哪些只是「历史证据」。

## 2. 决策

按 **「该批次是否已有 final report 接管结论」** 作为唯一归档判据，将符合条件的批次移入 `docs/archive/`：

```text
docs/archive/
├── README.md     生成索引（含归属分布表）
├── reports/      10 份 final report
├── specs/        16 份 spec
└── plans/        16 份 plan
```

保留在 `docs/superpowers/` 的 40 份为阶段 3～7 的 spec/plan。

**为什么以 final report 为判据：** final report 的存在意味着该批次的「交付物、决策、门禁数字、已知限制、执行偏离」已经有独立结论文档接管；spec/plan 从此只承担追溯职责。阶段 3～7 **没有 final report**，其结论散落在 spec §0 决策表与 `docs/review/*决策记录.md` 两处，spec/plan 本身就是主要技术记录，因此**不归档**。

### 归属分布（按标题核对，非按文件名猜测）

| 归属 | 文档数 | 文件名前缀 |
|---|---:|---|
| 阶段 1 安全骨架（地基 + 块 A/B/C） | 8 | `2026-08-08-phase1-foundation`、`2026-08-09-phase1-*` |
| 阶段 2 核心聊天闭环（块 A/B/C + realconn A/B/C） | 16 | `2026-08-1{0,1,2}-phase2-*` |
| 阶段 0/1 整改（复核批次 A～D） | 12 | `2026-08-12-phase01-recheck-*` |
| 首次/二次真实联调整改 | 6 | `2026-08-13-realint*-fix` |

阶段 0 没有独立 spec/plan：协议与工程基线由 `phase1-foundation` 一并建立，实质性阶段 0 整改见 `phase01-recheck-batchD`。

**易错点（已核对，勿凭文件名归类）：** `2026-08-12-phase01-recheck-batchA~D` 的标题是「**阶段 0/1 整改**」，不是阶段 2；只是日期与阶段 2 的 realconn 批次相近。同理 `2026-08-14-phase3-*` 是阶段 3 的复核批次，**不在本次归档范围**（阶段 3 无 final report）。

## 3. 归档不等于失效

这是本次整理最需要留档的口径，避免后人把归档读成「已废弃」：

1. 归档文件仍是**契约与决策的唯一原始记录**，可以且应当被引用；
2. 归档只表示它们「不再作为当前实现的必读入口」；
3. 尚未闭账的批次（阶段 3～7）继续留在 `docs/superpowers/`，其文件**不是**候选归档对象；
4. 引用归档文件时必须写明所属阶段，因为它们不在按阶段推进的主索引里。

移动前后用脚本对 `docs/` 全量 markdown 链接做了逐条解析，结果：

**`pnpm docs:check` 通过不等于没有断链**：它的链接检查只覆盖 README、CLAUDE.md、「维护中」核心文档与生成的索引；`docs/review/*`、`docs/superpowers/*` 与「参考/已归档」核心文档都不在检查面内。本次的核查用独立脚本完成。

## 5. 机制变更

`scripts/docs-check.mjs`：

1. 新增 `ARCHIVE` 常量与 `archiveIndexContent()`，生成 `docs/archive/README.md`（含归属分布表）；
2. `docs:index` 现在同时写三份索引（review / superpowers / archive）；
3. 陈旧索引断言覆盖 `docs/archive/README.md` —— 手工改动该文件会让 `docs:check` 以非零退出（已验证）；
4. `docs:check` 汇总行增加归档计数：`... 40 superpowers records, 42 archived records`。

## 6. 后续维护规则

- **新增批次不自动归档。** 仍按「先归档：该批次是否已有 final report」逐批判定；阶段 3～7 在补齐结论记录前不进入归档目录。
- **不手工维护 `docs/archive/README.md` 条目**，改由 `pnpm docs:index` 生成；归属分布表也由脚本产出。
- **分批执行。** 后续若归档阶段 3～7，必须单独成为一个批次并重跑链接核查，不与内容修订混在一起（`doc 00 §9` 文件名约定同款纪律）。
- 归档上限以「不破坏可追溯性」为准；如需撤销归档，用 `git mv` 移回并在本记录追加取代说明，不改写本记录。

## 7. 未纳入本次范围

1. **归档 spec 指向 core doc 的 17 处 `../NN-*` 断链**：修它们等于批量改写历史文档内部链接，值得单独一批并需要逐条核对，本次只记录数量与成因。
2. **归档外的既有断链（约 145 处）**：主要成因是把仓库根路径当作相对链接写（`apps/desktop/...`）、以及 `docs/review/` 历史归档使用 `docs/review/...` 全路径。其中 `docs/superpowers/**` 里的 `apps/desktop/...` 形态是**源码引用**而非文档链接，不构成实际缺陷。
3. **`docs/review/` 未做归档**：其记录仍被 doc 16、doc 10、doc 12 与各决策记录直接引用，且是「阶段 3～7 无 final report」时的结论来源，暂不具备归档条件。
