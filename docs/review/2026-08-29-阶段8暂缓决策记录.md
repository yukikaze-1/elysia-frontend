# 阶段 8 暂缓决策记录

> 决策日期：2026-08-28
> 记录日期：2026-08-29
> 决策状态：生效中
> 影响范围：doc 09、doc 10、doc 12、doc 16、阶段 8 的 make / E2E / 打包 / 签名 / 跨平台 / Demo 工作

## 1. 背景

阶段 7 四个批次已经完成真实 Windows Electron 联调，阶段 1～7 修缮批次也已完成真实前后端复核。阶段 8 的目标不是继续修补阶段 7，而是建立可分发产物、跨平台验收、签名与完整 Demo 证据。

现有 H 组输入尚不足以定义阶段 8 的验收对象。若直接开工，会导致“先实现再决定支持平台、签名主体和 Demo 成功标准”，无法形成稳定的 Definition of Done。

## 2. 决策

阶段 8 状态确定为 **暂缓、尚未进入**。

暂缓期间：

- 不把 `make`、`test:e2e`、签名或跨平台产物工作标记为阶段 8 已开发；
- 不用阶段 7 已通过替代阶段 8 的产品和发布输入；
- 可继续进行有独立范围、独立验收的修缮任务，但必须明确它不是阶段 8 开工；
- README、CLAUDE.md、doc 10 和 doc 12 不维护另一份当前状态，统一指向 doc 16。

## 3. 阻塞项

| ID | 决策问题 | 必须形成的输出 |
|---|---|---|
| H-01 | 主验收平台是什么 | 主平台、版本、优先级和真机证据要求 |
| H-02 | Windows 10 / Windows 11 / Ubuntu 的支持范围 | 最低版本、支持层级和允许豁免 |
| H-04 | 使用何种签名证书和发布身份 | 证书主体、保管/调用方式、无证书环境的验收口径 |
| H-07 | Demo 怎样算成功 | P0 场景、脚本、失败判定、证据和时长 |

原 doc 12 使用“H-03～H-09 已确认”作为阶段 8 进入条件，遗漏了实际阻塞的 H-01、H-02，并没有突出 H-04、H-07。本决策将进入条件改为：

1. H-01、H-02、H-04、H-07 全部形成明确决策；
2. H-03、H-05、H-06、H-08、H-09 被复核为已确认、仍适用或显式豁免；
3. doc 09 的发布设计按上述决定更新；
4. doc 12 的阶段 8 启动确认表完成；
5. doc 16 将阶段 8 从“暂缓”改为“已进入”。

## 4. 恢复后的首批工作

阶段 8 恢复后，建议按以下顺序推进：

1. 固化平台矩阵、产物格式、版本和签名策略；
2. 实现 `make`，生成目标平台安装产物；
3. 实现 `test:e2e` 的最小发布链 E2E；
4. 验证安装、首次启动、升级、卸载和重装；
5. 执行秘密、开发配置、Fuses、资源授权和来源完整性检查；
6. 按 H-07 执行完整 Demo，并归档前后端 SHA 与真机证据。

## 5. 与阶段 7 的关系

阶段 7 安全发布清单第 18 项“发布包来源完整性”明确依赖阶段 8 的签名工作，因此它是已知的阶段 8 承接项，不是阶段 7 未完成。

阶段 7 通过证明应用代码达到当前安全、稳定性和性能收敛要求；它不证明安装器、代码签名、跨平台兼容或 Demo 发布链已经完成。
