# 网络失败错误收敛：从 Main 归一，而非 UI 过滤（2026-09-10）

**记录日期：** 2026-09-10

**文档状态：** 生效中

**触发：** 真机联调截图里角色面板出现按钮文案 `Failed to fetch`。

**结论：** 是真实缺陷，但**根因不在显示它的那个组件**，而在 `RealBackend` 的 REST 失败路径：四处 catch 的兜底分支是裸 `throw e`，网络层失败时 `e` 是 `fetch` 的原生 `TypeError`（无错误码），一路穿透到界面。收敛点选在 **IPC 边界（Main）**，不是 UI 过滤。

---

## 1. 现象与来源

`CyCharacterPublicState` 的公开状态卡片渲染 `Failed to fetch`。

排查确认：

- 后端**在运行**（`192.168.1.18` 集群 `127.0.0.1:8765` 监听中），本机有 SSH 隧道（`127.0.0.1:8765` → 远端），隧道可用（无 token 时返回 401 即证明到达后端）；
- Live2D 模型**已安装**（`%APPDATA%\Cyrene\models` 下 haru / lil / wanko 三套），"默认模型" 只是标签，与模型缺失无关；
- Main 的 `app.log` 在最后一次会话里**只记录了启动**，没有 REST 错误——因为裸 `throw e` 不经过任何日志点；
- 该文本**不在本仓任何字符串里**，是 Chromium `fetch` 的原生 `TypeError` 文案。

链路：`restFetch` catch → `throw e`（原生 `TypeError`）→ IPC → `parsePublicError` 得 `code='TypeError'` → `errorMessage` 无此码映射 → 回退原始 `message` → 界面直显。

---

## 2. 修复

### 2.1 主修：Main 侧归一（`real-backend.ts`）

新增 `RealBackend.restFailure(error)`：

```ts
private restFailure(error: unknown): CyreneError {
  return error instanceof CyreneError
    ? error
    : new CyreneError(CyreneErrorCode.NOT_CONNECTED, '无法连接后端：网络请求失败，请检查连接或后端是否在运行')
}
```

并把**四处** REST catch 的兜底从 `throw e` 改为 `throw this.restFailure(e)`（`restFetch`、附件上传、工具附件上传、工具附件读取）。

设计要点：

- **语义正确**：网络层失败意味着请求根本没到达后端，`NOT_CONNECTED` 比 `UNKNOWN` 准确；
- **有错误码** → 契约可映射 → 界面拿到可操作文案；
- **`CyreneError` 恒等透传**：HTTP 404/401、超时、取消等既有业务语义不被这条兜底覆盖；
- **不让 renderer 各渲染点自行过滤**：UI 过滤只能做到「不显示」，而这里能给出**可操作的原因**。

### 2.2 辅修：公开状态卡片的脱敏层（`CyCharacterPublicState.vue`）

该卡片原有的 `safeErrorMessage` 直接放行 `error.message`。现改为**两条链串联**：

1. `errorMessage()`（`utils/error-message`）——集中映射，含「无映射时回退后端已公开说明」；
2. 卡片自身的脱敏检查（长度上限 + `FORBIDDEN_ERROR_CONTENT`）——**保留**，因为它的诉求（公开卡片不得泄露内部状态/prompt/记忆）与 ①（文案可读）不同，且要能拦住**已经过 ① 的**文本。

`FORBIDDEN_ERROR_CONTENT` 同时扩到浏览器/网络层原生文本（`Failed to fetch` / `NetworkError` / `Load failed` / `TypeError`）——这类文本「形态可判但无语义码」，映射器处理不了，在本层收口。

---

## 3. 一次走错方向的记录（重要）

中途曾试图在 `utils/error-message` 里给回退档加条件：**只有带 `backendCode` 的错误才回退原始 message**，理由是「本地发起的错误其 message 是技术细节」。

**该判断是错的**，且被测试当场抓住：

- 后端经 `getCharacterState` 抛出的错误**不带** `backendCode`；
- 渲染层本地构造的错误**反而带**（如 `character-editor.store` 的 `LOCAL:` 系列）。

即 `backendCode` 的语义取决于构造点，**不是「来源」的可靠判据**。该改动导致 3 个文件 5 条既有用例失败（后端可公开说明被吞成兜底句、角色域映射失效）。

已完整回退，并在 `errorMessage` 的注释里写明这个坑。真正的收口放在 `restFailure`——在**产生错误的地方**消除无码异常，而不是在**消费错误的地方**猜测来源。

## 4. 验证

| 门禁 | 结果 |
|---|---|
| `typecheck` / `lint` | 干净 |
| 单元测试 | **212 files / 2656 passed**（+2 用例） |
| 集成测试 | **22 files / 137 passed + 2 skipped** |

新增两条回归（均已确认在缺陷形态下会变红）：

1. `real-backend-character.spec.ts`「网络层失败归一为 NOT_CONNECTED，不得让 fetch 原生文本穿透」——`fetchImpl` 抛 `TypeError('Failed to fetch')`，断言 reject 的 `code === NOT_CONNECTED`、`message` **不含** `Failed to fetch` 且含可操作文案；同时用 404 走真实链路断言 `NOT_FOUND` 仍原样保留（兜底不得覆盖业务语义）。
2. `cy-character-public-state.spec.ts`「底层网络错误（浏览器原生文本）不得原样露出」——遍历 `Failed to fetch` / `NetworkError...` / `Load failed`，断言界面文本不含原文且落到兜底句。

## 5. 残余

- **`CyToolCard.vue:172`** 仍直接渲染 `record.error?.message`。那是后端工具执行结果的原文（非 `PublicError`），语义上属于「外部系统给的可显示文本」，**本次未动**；若将来工具错误也出现原生网络文本，应同样在 Main 的工具调用路径归一。
- 排查中发现客户端与后端之间 **WS 连接在 03:47–03:48 三次连断**（后端日志三次 connect/disconnect）。这是本次错误的**触发条件**（网络抖动），属环境问题而非代码缺陷，未做处置。
