# Live2D 失败态可诊断化（2026-09-10）

**记录日期：** 2026-09-10

**文档状态：** 生效中

**触发：** 真机「模型加载失败」——但界面只显示这四个字，无法判断是「没装模型」「模型损坏」还是「清单读取失败」，排查只能靠复现环境。

**结论：** 这是**诊断能力缺陷**，不是功能缺陷。失败原因其实**早已被捕获**（`live2d.store` 的 `error` ref），但渲染层把它丢掉了。本次把界面自身变成一等排查手段。

---

## 1. 两处静默/丢失

| # | 位置 | 问题 |
|---|---|---|
| 1 | `CyLive2DPanel.vue` 失败态 overlay | 硬编码「模型加载失败」，**不带 `store.error`**。而同文件的 `statusText` 明明已写成 `store.error \|\| '模型加载失败'`——两处行为不一致 |
| 2 | `live2d.store.ts` 清单拉取 | `api.listLive2dModels().catch(() => [])`：**清单读取失败被吞成空数组，不留任何原因**。于是「清单读取失败」与「确实一个模型都没装」在界面上完全同形 |

两处叠加的后果：用户能看到的最强线索只有「模型加载失败」四个字。

---

## 2. 修复

### 2.1 失败态改为三段式（`CyLive2DPanel.vue`）

```
模型加载失败
原因：<store.error>
<模型清单探测结果>
```

清单探测结果分两种，正是排查时必须区分的第一刀：

- `未发现任何已安装模型（检查 userData 的 models 目录：需 manifest.json + integrity.json）`
- `已发现 N 个模型，其中可用 M 个`

新增 `.cy-live-overlay.is-diagnostic` 样式（纵向排布 + `overflow-wrap: anywhere`，防长原因撑破 340px 窄栏）。

### 2.2 清单读取失败留痕（`live2d.store.ts`）

```ts
models.value = await api.listLive2dModels().catch((e: unknown) => {
  error.value = `模型清单读取失败：${e instanceof Error ? e.message : String(e)}`
  return []
})
```

**fail-open 语义不变**（仍不阻塞启动、仍退化为静态头像），只是不再把原因丢掉。

---

## 3. 本次独立排查已排除的因素

诊断能力补齐的同时，这些**已实测排除**（记录以免重走）：

| 项 | 实测结果 |
|---|---|
| 模型是否安装 | **已装 3 套**：`%APPDATA%\Cyrene\models\{haru,lil,wanko}` |
| `manifest.json` / `integrity.json` | **三者齐备**，`manifest.id` 与目录名**一致**，均含 `licenseRef` |
| 完整性哈希 | **全部匹配**：haru 48 项 / lil 13 项 / wanko 18 项，零缺失、零尺寸不符、零哈希不符（逐条重算 SHA-256 比对） |
| `model3.json` | 三者均存在 |
| models 目录解析 | `main/live2d/model-registry.ts` 的 `modelsDir` = `<userData>/models`；`expectedUserDataBase()` = `join(app.getPath('appData'), 'Cyrene')` —— **路径一致** |
| `live2d:list-models` 是否依赖后端 | **不依赖**：`listInstalledModels()` 纯本地读目录，与后端连通性无关 |

因此「模型加载失败」**不是模型数据问题**，也不是后端问题；剩余可能集中在运行时（清单 IPC 未接通 / 索引与目录不一致 / WebGL 初始化）。这正是本次诊断输出要回答的。

## 4. 验证

| 门禁 | 结果 |
|---|---|
| `typecheck` / `lint` | 干净 |
| 单元测试 | **212 files / 2659 passed**（+3 用例） |
| `docs:check` | 通过 |

新增 3 条用例（`live2d-panel.spec.ts`，`makeFakeController` 增加 `status` 参数以构造 failed 态）：

1. 清单为空 → 断言提示「未发现任何已安装模型」且含 `manifest.json` 目录要求；
2. 清单拉取 reject → 断言界面出现「模型清单读取失败」**及底层原因**（此前必然丢失）；
3. 清单有模型但均 `available:false` → 断言报出「已发现 2 个模型 / 可用 0 个」，用于区分完整性失败。

---

## 5. 残余

**根因尚未定位。** 本次交付的是**诊断能力**，不是修复——因为独立可验证的因素（§3）已全部排除，剩下的必须靠运行时状态说话。界面现在会直接报出原因与清单探测结果，下一次复现即可定位。

> 排查过程中的教训：我曾三次尝试用探针读运行时状态，均因环境问题失败（应用占用单实例锁、`_electron.launch` 的 `--inspect=0` 导致 Electron 以调试模式启动后退出）。**与其继续搭更复杂的探针，不如让产品自身的失败态具备可诊断性**——后者的收益是持久的，且不依赖任何一次性环境。
