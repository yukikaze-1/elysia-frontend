## 1. 结论摘要

代码本身的质量高于同类 Electron/Vue 项目的常见水平（手写生产代码零 `TODO`/`FIXME`、零 `any`/`eslint-disable`、全仓无 `.only`、死代码仅一个 3 行 barrel、循环依赖 3 个且 2 个良性）。

**真正失效的是验证体系，而且失效方式使它长期不可见。** 评估得到的最重要一条事实是：

> **2026-09-10 验收后热修修复的那个渲染崩溃（`DataCloneError`），在 CI 里已经连续失败了至少 4 次推送、横跨 4 天，每次都留下 54～58 行断言失败；因为 CI 早已是「已知红」，没有人再看它。**

也就是说：该缺陷本可以在提交阶段被现有测试拦住，它却一路走到了真机 Stage H 验收、闭账之后才被手工发现。这不是「缺少测试」，是**测试结果被丢弃**。

### 2.2 两处「绿灯掩盖未验证」

- **`check:contract`**：默认后端路径是硬编码的 Linux 家目录 `/home/yomu/elysia-agent/frontend_contract`。在 Windows 开发机上该路径不存在，脚本打印一行「后端仓库未挂载,跳过」后以 **0** 退出。而 doc 12 与阶段决策记录把 `check:contract` 的 WS/REST 计数当作跨仓契约门禁证据（D-8、阶段 4/6 多处）。README 已写「后端契约在本机可用时执行」，但退出码与「通过」不可区分。
- **`verify:sensitive`**：规则 `base64-long-string` 的字符类 `[A-Za-z0-9+/]{40,}` 把 `/` 也算作 base64 字符，于是**任何 40 字符以上的相对 import 路径、camelCase 标识符串、词表串、40/64 位 hex 摘要**都命中（全仓实测 1671 行 / 221 文件）。这些命中全靠「类别级 allowlist + 逐文件人工核对」承接（最后一次核对 2026-08-22），每新增一个含长路径的文件就必然变红——allowlist 在两周内即腐烂：39 条路径因归档失效、大量新文件无条目。**门禁长期全红、事实失效。**

### 2.3 文档面缺少「门禁健康」这一栏

doc 16 作为当前状态唯一事实源，对**阶段状态**极其诚实（明确写着「本轮只执行真实 Stage H 定向联调，未重跑前端全量单元测试；不得沿用 2026-09-08 的测试数字冒充本轮结果」），但它**没有任何字段记录自动门禁是否绿**，全文不提 CI。于是「阶段已完成」与「门禁全红」可以同时成立而无人察觉。本次整改在 doc 16 §3 增加「自动门禁」行（见 §6）。

## 3. 同一 commit、三个环境、三种结果

| 环境 | 单测结果 |
|---|---|
| 本机 Windows | 193 files / **2515 passed / 0 failed** |
| CI Windows | 192 files / 2510 passed / **3 failed**（`tool-executors.spec.ts` 的 `desktop.file.select`） |
| CI Linux | 192 files / 2529 passed / **2 failed**（`character-draft-store.spec.ts`） |

三处都是测试对宿主环境的隐式依赖，生产代码无缺陷——但这也意味着**没有任何一个环境能单独证明门禁通过**。三处根因：

1. **`tool-executors`（Windows CI）**：`desktop.file.select` 复核把候选路径 `realpathSync.native` 解析为长名，而夹具注入的 `allowRoots` 在 CI runner 上是 8.3 短名（`C:\Users\RUNNER~1\…`）→ `path.relative` 得到 `..` → `isPathWithinRoot` 判否 → 黑名单（`~\AppData\Local\Temp` 是 Windows 默认黑名单项）不被 allowRoots 放宽 → 伪装取消。本机 tmpdir 恰为长名故此前只在 CI 红。**这与仓库此前在 `safe-open.ts`、`atomic-write.ts` 已修过两次的 8.3 短名问题同源。**
2. **`character-draft-store`（Linux CI）**：夹具用裸 `writeFile` 写根文件（POSIX 下 umask 022 → 0644），而 `load()` 走 `openSafeFile(purpose:'read')`，其 POSIX 分支要求 `(mode & 0o400) === 0o400` 且 `(mode & 0o077) === 0`（`checkModeMask`，Windows 恒 false）→ 0644 被判「权限不正确」→ **全量草稿丢弃**。生产写入经 `atomicWriteFile → openSafeFile(mode:'create')` 固定 0600，故真实文件满足判据——属夹具与生产契约不符。
3. **`perf-gate`（两个平台）**：`join(process.env.HOME!, '.config/Cyrene/models')` 在**模块收集期**求值，Windows 上 HOME 未定义、`path.join(undefined, …)` 抛 `TypeError` → **整个文件加载失败、该 spec 4 个用例（含 2 个硬门禁）从未执行**；`!` 非空断言恰好把类型检查挡在外面。

### 3.1 两个缺陷互相掩盖

`perf-gate` 的收集期崩溃（缺陷 3）与它在 `c2d92c2`「QQ 风格聊天界面重构」后失效的选择器（见 §4.2）**互相掩盖**：一个从没执行，一个执行即失败。两者叠加的结果是「长期无人发现」。这是本次评估里最具一般性的教训：**红灯之间会互相掩护，红灯总数本身就是一种掩盖。**

## 5. 唯一的真缺陷：mock 模式 TTS 自动朗读静默失效

**根因**：Stage H 的「按角色围栏」（`voice.store belongsToActiveCharacter`，提交 `017ad08`）要求 `audio.session.started/ready/cancelled` 携带 `conversationId` + `characterId/InstanceId/Revision`。契约里这三个事件确实 `extends CharacterEventIdentity`（`shared/contracts/events.ts`），**但 MockBackend 只给夹具路径的 `generation.started/completed/failed` 盖了戳**，`audio.session.*` 仍只走 `stamp()`（仅 `eventId/sequence`）。

mock 的 `features.characterProfiles` 恒为 true（`MockCharacterBackend.features`），于是围栏生效而 `e.conversationId === undefined` 恒不等 → **三帧被整帧丢弃**：`ttsReadySeen` 恒 false、`<audio>` 永不置 src、口型链永不 attach，**且没有任何用户可见错误**。

**定界**：真实后端这几帧带身份（围栏正是为它加的），故真实链路不受影响；受影响的是 `CYRENE_BACKEND=mock` 的演示/开发形态，以及依赖该形态的集成验证能力。

**修复**：`MockBackend` 新增 `characterEventStamp()`，夹具路径的 TTS 三帧复用本代已捕获的 `characterIdentity` + `conversationId`。修复后 `electron-voice` 16/16、`electron-live2d` C1 转绿。

**顺带记录的健壮性问题（本次不改，未定级）**：围栏对「缺失身份」零容忍——任何不带该三元组的 `audio.session.*` 都会被静默丢弃。fail-closed 方向是对的，但它**静默**，与 §2.1 的失效模式同类。是否要为「缺失身份」单独产出可观测诊断（例如计入诊断页计数）需要单独决策。

### 6.1 收窄规则后的检出保真度（实测，非估计）

## 8. 未完成与残余风险（诚实边界）

1. **第三方资产授权与来源**：已立为显式阻塞项 `EXT-01`，见[决策记录](2026-09-10-第三方资产授权与来源立为阻塞项-决策记录.md)。仓库内无判定手段，本轮**不尝试**给出许可结论。
2. **Live2D 集成 spec 的偶发性**：**根因已定位为宿主级负载敏感，且找到了这台机器上具体的持续负载源。**
   证据链：
   - 排除并行文件竞争：`vitest.integration.config.mts` 为 `fileParallelism: false`（各文件串行）。
   - 排除正常关闭路径泄漏：实测「启动 + `closeApp`」一轮后 Electron 进程数 **0 → 0**，`closeApp` 不漏。
   - **但发现孤儿进程**：一次完整运行前后采样（每 5s，96 样本）显示 Electron 进程数存在 **8 的恒定地板**（≈750 MB），
     运行结束后仍为 8；收工时实际列出**两个完整的应用实例**（各 main + gpu-process + utility + renderer），
     启动时间 21:31:23 / 21:32:04，命令行带 `--inspect=0 --remote-debugging-port=0`（Playwright 启动特征），
     `--user-data-dir` 为 `…\Temp\cy-int-ud-DigFoZ` / `…cy-int-ud-lcYCQ1`——即**被中断的运行留下的测试应用从未退出**。
   - 相关性：本机三轮全量运行中，失败的用例每轮不同（C3.1@825 / 7D@951 / C3.2@849），失败点全部落在
     启动/连接后的**首次交互**等待；带并发负载的那轮（同时跑全量单测 + typecheck）失败 4 项，
     无并发负载的一轮 0 项。清理孤儿后的完整运行 **22 files / 136 passed / 2 skipped 全绿**。
   - 结论：**不是产品缺陷，也不是并行调度问题**，而是「首交互等待预算（该 spec `POLL = 8000ms`）
     在宿主被额外 Electron 实例占用 GPU/CPU 时不够」；孤儿来自被 `Ctrl-C`/被杀掉的运行，
     会**跨运行长期驻留**并持续占用 ~750 MB 与 GPU 进程。
   - 维护含义：**诊断 Live2D 偶发前，先 `Get-Process electron` 看有没有孤儿**。CI 使用一次性 runner，
     不存在该机制，因此 Linux CI 未观察到同类偶发（样本量仍为小）。
   - 记录为已知限制；建议的加固（尚未实施，见 §10）为「套件启动时清理签名匹配的孤儿测试应用」。
3. **`openSafeFile` 的非 0600 语义（Linux）**：POSIX 上根文件权限一旦不是 0400/0600（备份恢复、同步工具改写、旧版本遗留），store 会**静默丢弃全部草稿、列表返回空且无可见错误**——为保密性检查牺牲可用性且不告知。本轮只新增用例把该语义**显式钉住**（`character-draft-store.spec.ts`），**未改安全策略**；是否改为「拒绝读取 + 显式告知 + 隔离现场」需单独决策。
4. **`allowRoots` 是 mock/测试注入面**：真实模式不注入（`main/index.ts` 由 `CYRENE_MOCK_TOOL_ALLOW_ROOT` env 桥提供）。本次只修夹具归一化，未触碰产品黑名单语义。
5. **`electron-tools.spec.ts` 的 `FIXTURE_ROOT = '/tmp/cyrene-fixtures'`**：Windows 上解析为 `C:\tmp\cyrene-fixtures`，其「fixture 在 `/tmp` 黑名单内 → 需 allowRoots 放宽」的前提在 Windows 是空转的——即 Windows 上并未真正验证 allowRoots 放宽路径。本次未改（改夹具根可能牵动多处断言），记录为覆盖缺口。

### 8.1 补断言过程中新发现的产品问题（**未修复**，均非本次范围）

补齐阶段 H 组件层与附件链断言（`8f1e613`）时，新测试暴露出 3 项既有产品问题。它们不是门禁问题，按纪律**只记录、不夹带修复**：

1. **角色编辑器「主动间隔」清空会让保存静默失效**（`CyCharacterPresentationFields.vue:23-26`）：
   空串走 `Number('') === 0` 且 `isFinite(0)` 为真 → emit `intervalSeconds=0`，而非注释意图的回退 3600。
   该输入框自身 `min="60"`（同文件 `:77`）且位于 `CyCharacterEditor.vue:190` 的 `<form>`（190–252 行，
   `@submit.prevent="save"`）内，`CyCharacterPresentationFields` 在 `:212` 渲染于该 form 中，
   唯一的保存入口是 `:247` 的 `<button type="submit">`。
   **2026-09-10 真 Chromium 实测确认**（`tmp/probe-form-validation.mjs`，Playwright chromium 复刻同结构）：
   点击 submit 后 `submit` 事件**一次都没触发**（`submits: 0`），
   且 Chrome **既没有展开闭合的 `<details>`，也没有把焦点移到无效控件**（`activeElement` 仍是提交按钮）——
   即无效字段一直藏在折叠的「高级：主动对话」里。把值改为合法（≥60）后 `submits: 1`，行为恢复。
   **用户表现：清空该字段后点「保存角色」没有任何反应，界面上也没有任何提示。**
   证据：`cy-character-presentation-fields.spec.ts` 中标注「（锁定现状）」的用例断言 emit 0。
2. **附件媒体恢复路径与占位重试路径语义不一致**（`CyAttachmentMedia.vue:37-45`）：
   媒体元素 error 后把 `mediaStatus` 置为 `attachments:check` 的 status；返回 `ok` 时**不换 URL、也不重挂载**，
   而同文件占位重试路径（`:49-57`）会 `retryNonce++` 换 URL（Main 重新 resolve/重签）。
   **2026-09-10 复核更正**：本条初版记为「形成 error→check→ok→重挂载的无退避循环」，**该结论错误**——
   探针实测（`error` 前后 DOM 节点同一、`src` 不变、`attachmentsCheck` 调用次数恰等于手动触发次数）证明
   `mediaStatus` 从 `loading` 变 `ok` 时两者都落在媒体分支内，子组件**不重挂载**，因此不存在自循环。
   真实缺陷是另一回事且更隐蔽：元素已损坏却把状态置为 `ok` → **占位永不出现** → 用户面对一个
   静默损坏的媒体元素，既无解释也无法重试；而其他所有失败路径（expired/not_found/revoked/error）
   都会给出带文案的占位。触发场景现实存在：媒体字节存在但浏览器无法解码（截断图片、容器/编解码不受支持）
   时 `attachmentsCheck` 返回 `ok` 而元素渲染失败。
3. **次要**：`CyAttachmentMedia.vue:38` 的 `if (!props.attachmentId) { mediaStatus = 'error' }`
   分支实际不可达（无 attachmentId 时子组件不渲染媒体元素，无法触发 error），属死代码；
   `CyCharacterCatalog.vue:59/64` 直接调用 `window.confirm`，未像 `CyCharacterEditor.vue:117-119`
   那样做 `typeof` 守卫（真实 Electron 下无影响，仅健壮性不一致）。
