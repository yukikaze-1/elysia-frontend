## 一、AUD-01 零客户端 WS 存活检测（报告 P1-3）

### 已核事实（本轮复核，与报告一致）

- 前端**没有任何周期探测**：`real-backend.ts` 全文件无 ping/keepalive/`setInterval` 心跳源；唯一状态来源是 socket 的
  `close`/`error`（`:985-986`）。half-open（NAT 超时、休眠唤醒、对端 SIGKILL 未发 FIN）不会触发它们。
- ⚠️ **协议两侧都没有 `ping`/`pong` 帧**：前端全仓 + 权威后端（X99 `10acc315`）grep **均 0 命中**。
  ⇒ **报告建议的"复用既有帧发廉价 ping"没有现成帧可复用**，这一条前提本轮被推翻。
- 帧类型白名单在 `apps/desktop/scripts/check-backend-contract.mjs:41`（当前 **37 型**）。
- **已有可复用的重连机制**（不要新造状态机）：`RECONNECT_BASE_DELAY_MS=1000` / `RECONNECT_MAX_DELAY_MS=30000` /
  `RECONNECT_MAX_ATTEMPTS=6`（`:204-206`），收敛入口 `onSocketClosed(ws, incarnation, …)`（`:1018`，被 `:985/:986` 调用）。
- **现成可当探针的廉价 REST**：`GET /api/me`（`:1343`，只读、无副作用）。

### 选项与代价

| 选项 | 做法 | 代价 | 得到什么 | 风险/局限 |
|---|---|---|---|---|
| **A 只开 TCP keepalive** | 连接后 `socket.setKeepAlive(true, 30s)` | **最低**：一处调用。无协议/后端改动 | 把"永不发现"变成"最慢几分钟发现"，随后走既有重连 | 探测次数系统相关（Linux 默认 10 次 ⇒ 约 5 分钟；Windows 不可配更差）；要碰 `ws` 的私有 `_socket` |
| **B 客户端静默看门狗 + 在途复核**（推荐） | 新增纯模块（注入时钟，可单测）记录"最后一次收到帧"；**仅在**两种情况复核：① 有在途请求超阈值仍无 ACK/无帧；② 连续 N 分钟完全无帧。复核用 `GET /api/me` 判宿主可达；判失活即主动 `close` 现有 socket，**复用既有 `onSocketClosed`/重连** | **中低**：1 个纯模块 + 1 处接线 + 单测（真实 `WebSocketServer` 静默挂起夹具，仓内已有先例） | 正面消除用户可见症状（假 `connected` + 静默吞消息 + 误报 `TIMEOUT`），并把恢复自动化 | REST 成功只证明**宿主**活着，不证明**这条 socket** 活着 ⇒ 判据必须是"宿主可达 **且** 本 socket 长期静默"，结论是**强制重建**而非"等对端回话" |
| **C 新增 `ping`/`pong` 帧** | 后端加帧类型 + 前端 raw schema/type + 契约镜像 + 白名单 37→39 + doc 02 | **高（跨仓）**：需后端配合；契约门禁还要求后端 traces 含该帧才可能 exit 0 | 语义最干净：能区分"对端活着但空闲"与"链路已死"，探测最快最准 | 跨仓排期不受本仓控制；在对方落地前前端只能空等 |
| **D 只在文档声明不做** | 写明"无存活检测" | 0 | 诚实 | 缺陷原样保留 |

### 推荐

**B 先做，A 作为廉价附加；C 记为跨仓请求**（与 doc 18 已有的其它跨仓请求同路，不阻塞本仓）。
理由：B 不需要后端配合、能自证（单测可确定性驱动）、且复用既有重连路径；**关键设计点是"空闲不重连"**——
后端空闲时本来就不发东西，若无条件按静默判死会造成无谓连接抖动。

## 二、AUD-02 real 装配在 Electron 层的端到端覆盖（报告 P1-4）

### 已核事实（本轮复核，并补了报告未提的一条硬约束）

- harness 把 `CYRENE_BACKEND: 'mock'` 写在 `...(opts.env ?? {})` **之后** ⇒ 调用方不可覆盖（`tests/integration/helpers/app.ts:143-154`）；
  打包形态恒 real（`config/backend-mode.ts`）⇒ **用户唯一会运行的形态在 Electron 层零覆盖**。
- **connect 需要"已存 token + origin 绑定"**：`chat-service.ts:53-59` 在 `requireToken !== false` 时要求 endpoint、
  binding origin 匹配、token 存在，否则 `CREDENTIAL_UNAVAILABLE`。
- 🔴 **报告未提、但决定方案可行性的硬约束**：**CI 里跑 Electron 的 runner 是 Linux + xvfb**（`ci.yml` 的
  `integration` job，`runs-on: [self-hosted, Linux, X64, fe-linux]`），在那里 `safeStorage` 是 `basic_text`
  ⇒ 判不可用 ⇒ 拒存（fail-closed）；既有凭据往返用例在 `unavailable` 时 **`return { skipped: true }`**
  （`tests/integration/ipc-security.spec.ts:141,157-164`）。
  ⇒ **任何依赖凭据的 real 冒烟，都会在 CI 唯一跑 Electron 的那台 runner 上被静默跳过**——那正是报告
  S-4「绿灯含义被高估」的同型陷阱，**必须避免重犯**。
- `windows-runtime.yml` 只有 `workflow_dispatch`（手动）⇒ Windows 侧无自动运行时信号。
- 已有可复用夹具先例：`tests/unit/real-backend*.spec.ts` 用真实 `http.createServer` + `new WebSocketServer({ server, path:'/ws' })`
  （如 `real-backend.spec.ts:48,57`）。

### 选项与代价

| 选项 | 做法 | 代价 | 得到什么 | 局限 |
|---|---|---|---|---|
| **A 放开覆盖 + 3 条免凭据 real 冒烟**（推荐先做） | ① 打包/直启下 `mode` 报 real、装配确为 real；② **无 token 时 connect 必须 fail-closed 为 `CREDENTIAL_UNAVAILABLE`**（真实装配的错误面，mock 永不走到）；③ 断开/重连状态机在 real 装配下的可见状态 | **低**：`helpers/app.ts` 一处顺序调整 + 1 个新 spec + 进既有 `integration` job 的 shard | real 装配在真实 Electron 中**确被启动过**，且它的 fail-closed 面被断言 | **不需要凭据 ⇒ 在 Linux CI 真跑、不会被 skip**（这是关键优点）；但不覆盖帧解析/重连/取消终态，因为连不上 |
| **B 本地 ws/http 夹具 + 真实连接** | 起最小夹具并真连上 | **中高**：需 `requireToken:false` 之类的注入才免凭据，与"生产代码不放测试专用分支"冲突；或只在 Windows 手动 job 跑 | 真正的端到端 real 覆盖（帧解析、reconnect、cancel 终态） | 若落在自动 CI 会**被 skip**（见上）；落点应是 **Windows 手动 job + 真实后端（X99）** |
| **C mock/real 共享契约测试** | 同一输入序列喂两实现，断言产出**同构领域事件** | **中**：抽共享套件 + 两侧适配 | 直接回答"两实现是否可互换"这个**至今零证据**的核心不变量 | 不碰 Electron/preload；但**不需要 Electron、不需要凭据 ⇒ 可进 unit 层 CI，判别力最强** |
| **D 只在文档声明** | 写明缺口 | 0 | 诚实 | 缺口保留 |

### 推荐

**A + C**（两者都能在 CI 真跑且不被 skip）；**B 单列为手动取证路径**（可顺带把 `windows-runtime` 从纯手动改成定期/或与
`linux-runtime` 取证 workflow 合并）。理由：先把"能在 CI 真红"的那两层补上，再谈需要真机/真后端的那层。

## 三、Linux 生产构建的 GPU 回退（报告 P2，产品侧缺口）

### 已核事实

- 崩溃机制已由 X99 取证：无 DRI 的 Mesa 软件光栅器**确定性段错误** ⇒ Chromium 重试耗尽后
  `FATAL: GPU process isn't usable. Goodbye.` **主动杀掉整个应用**；最小复现里 `--no-sandbox` /
  `GALLIUM_DRIVER=llvmpipe|softpipe` / `LIBGL_ALWAYS_SOFTWARE=1` **全部无效**，`--disable-gpu` 与 SwiftShader 有效。
- `--disable-gpu` 目前**只在** `tests/integration/helpers/app.ts` 与 `scripts/verify-artifact.cjs`；
  `src/main/**` 零命中，`disableHardwareAcceleration` 全仓 **0 命中** ⇒ **产品侧没有任何回退**。
- 启动早期有既成落点：`index.ts` 在 `app.whenReady()`（`:157`）**之前**设 commandLine 开关（先例 `:131`
  `enable-precise-memory-info`）——**GPU 开关必须落在同一区段**。
- `runtime-environment.ts` 已是"从 env/平台解析一次"的既有范式，适合承载这次判定。
- ⚠️ **`app.getGPUFeatureStatus()` 只在 ready 之后可用**，而崩溃发生在 GPU 进程初始化期 ⇒ **不能靠它决策**，
  否则只能检测完再重启（体验差）。

### 选项与代价

| 选项 | 做法 | 代价 | 得到什么 | 风险 |
|---|---|---|---|---|
| **A 启动期启发式回退** | Linux 且**无可用 GPU 设备节点**（如 `/dev/dri` 不存在）⇒ ready 前 `appendSwitch('disable-gpu')`，并写一条诊断日志说明"因无 GPU 设备节点而回退" | **低**：`runtime-environment.ts` 一处判定 + `index.ts` 早段应用 + 单测（注入假 fs） | xvfb / 容器 / 无 3D VM **不再崩**；有 `/dev/dri` 的桌面**行为不变** | 启发式可能误判（少数有 DRI 但驱动仍崩的环境）⇒ 需允许 env 覆盖（如 `CYRENE_GPU_MODE=auto\|disable`）便于现场自救 |
| **B 明确不支持并写进文档** | 声明"仅支持有硬件 GL 的 Linux 桌面"；测试侧开关不算产品能力 | **0 代码** | 诚实 | 无 GPU 的 Linux 用户拿到崩溃且**无自救路径** |
| **C A + B（推荐）** | 做 A 的回退，同时把支持边界按 B 写清 | 低 | 既不崩、也不夸大支持范围 | 同 A |
| **D ready 后检测再重启** | `getGPUFeatureStatus()` 检测 → 重启应用 | 高 | 检测最准 | 启动闪一次；复杂且易出错，**不推荐** |

### 推荐

**C**。理由：A 的判据在**崩溃发生之前**就能取到（设备节点存在性），代价低且对桌面用户零影响；
B 把"我们支持什么"写实，避免又一次"测试侧修复被读成产品能力"（本仓已有 Linux GPU 那条前科）。
